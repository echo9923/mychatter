## 详细组件分析

### 组件A：LogicSystem::GetUserThreadsHandler 与 GetUserThreads
- 职责
  - 解析请求 JSON（uid、thread_id）
  - 设置 Defer 确保响应发送
  - 调用 GetUserThreads 完成分页查询
  - 组装响应体（error、uid、threads、load_more、next_last_id）
- 关键点
  - 固定 page_size=10
  - 使用 lastId 作为游标，避免偏移量分页的性能问题
  - 通过 load_more 控制是否继续加载
- 错误处理
  - 若用户无效，返回 UidInvalid

```mermaid
flowchart TD
Start(["进入 GetUserThreadsHandler"]) --> Parse["解析请求 JSON<br/>提取 uid, thread_id"]
Parse --> SetDefer["设置 Defer 回包"]
SetDefer --> CallGet["调用 GetUserThreads(uid,lastId,page_size)"]
CallGet --> CheckRes{"查询成功?"}
CheckRes --> |否| Err["设置 error=UidInvalid"]
CheckRes --> |是| BuildResp["组装响应<br/>threads, load_more, next_last_id"]
BuildResp --> Send["发送 ID_LOAD_CHAT_THREAD_RSP"]
Err --> Send
Send --> End(["结束"])
```

### 组件B：MysqlDao::GetUserThreads（分页查询与加载更多）
- 职责
  - 使用 CTE 合并私聊与群聊记录
  - 按 thread_id 升序排序
  - 取 pageSize+1 条判断是否还有更多
  - 计算 nextLastId 用于下一次查询
- 关键点
  - 私聊表 private_chat(user1_id, user2_id, thread_id)
  - 群聊成员表 group_chat_member(user_id, thread_id)
  - LIMIT N+1 模式避免二次查询判断是否有下一页
- 异常处理
  - 捕获 SQLException，输出错误信息并返回失败

## 性能考虑
- 分页策略：采用 LIMIT N+1 游标分页，避免 OFFSET 在大偏移时的性能退化
- 连接池：MysqlPool 自动健康检查与重连，降低连接失效影响
- 缓存策略：用户基础信息优先查 Redis，减少数据库压力（适用于用户信息查询，线程列表可考虑热点线程缓存）
- 查询优化：CTE + UNION ALL 合并私聊与群聊，单 SQL 完成聚合，减少多次往返
- 网络传输：响应体精简，仅返回必要字段，减少带宽占用

- 常见问题

- 恢复措施

  - 连接恢复：MysqlPool 自动检测并重连

## 结论
ChatServer 的线程管理模块以 LogicSystem 为核心，结合 MysqlDao 的高效分页查询，实现了稳定的聊天线程列表获取与加载更多能力。通过 CTE + UNION ALL 的 SQL 设计，兼顾了私聊与群聊的统一查询。客户端通过 UserMgr 维护线程数据缓存，配合 UI 渲染与加载更多逻辑，形成完整的用户体验闭环。未来可扩展置顶、搜索过滤与热点缓存以提升性能与可用性。
