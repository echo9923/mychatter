server 目录采用多进程微服务架构，每个子目录是一个独立的可执行服务，共享相同的工程模板：
- 目录结构统一为 include/src/config/CMakeLists.txt，include 存放头文件，src 存放实现，config 存放运行时配置文件。
- 顶层 CMakeLists.txt 使用 Ninja Multi-Config 生成器，通过 add_subdirectory 聚合 GateServer、StatusServer、ChatServer、ResourceServer 四个 C++ 服务，并设置 VCPKG 依赖路径。
- 每个服务的 CMakeLists.txt 调用自定义函数 llfc_find_server_dependencies() 和 llfc_ensure_*_proto() 来发现依赖并生成对应 proto 文件（chat/control/resource），最终链接到 llfc_chat_proto、llfc_control_proto、llfc_resource_proto 目标。
- 网络层统一基于 Boost.Asio + Beast 构建 TCP 服务器（CServer + AsioIOServicePool 线程池），会话管理由 CSession 负责；gRPC 服务通过 StatusServiceImpl / ChatServiceImpl 等类实现 protobuf 定义的 Service。
- 数据访问层由 MysqlMgr/MysqlDao（MySQL）、RedisMgr（hiredis）、DistLock（分布式锁）组成，各服务通过 GrpcClient（ChatGrpcClient、VerifyGrpcClient、StatusGrpcClient、ChatServerGrpcClient）进行跨服务通信。
- VarifyServer 是独立的 Node.js 服务（package.json 声明 @grpc/grpc-js、ioredis、nodemailer），通过 message.proto 提供验证码服务，被其他 C++ 服务以 gRPC 客户端调用。
- 依赖方向：业务逻辑层（LogicSystem/UserMgr/FileWorker 等）→ 基础设施层（MysqlMgr/RedisMgr/DistLock）→ 网络层（AsioIOServicePool/CServer/CSession）→ gRPC 客户端/服务端。
