# 客户端与服务端数据库重构方案

## 1. 设计范围

本文只覆盖当前项目已经实现的业务：

- 用户注册、登录、密码哈希、用户搜索和个人资料。
- 发起好友申请、同意好友申请、拒绝好友申请、好友列表。
- 一对一私聊和私聊历史分页。
- 文本、图片、普通文件消息。
- 资源元数据创建、断点上传、下载和超时失败。
- 1701 实时通知和 1405/1406 连续增量同步。
- 客户端 SQLite 离线缓存和文本/资源发送 outbox。

明确不设计以下当前不存在或本轮明确不要的功能：

- 群聊、群成员、群角色。
- 好友申请撤销。
- 好友或联系人备注。
- 消息编辑、撤回、逻辑删除和服务端已读回执。
- 多附件、对象存储后端、多设备同步和事件归档。

本方案不兼容现有数据库。服务端重新建 MySQL 空库，客户端删除旧 `chat.db` 后重建，不编写旧数据迁移。

## 2. 为什么服务端仍需要 `user_events`

好友申请从消息表拆出后，当前 1405/1406 仍然必须把以下内容按一个连续序号同步给用户：

- 文本消息。
- 图片消息。
- 文件消息。
- 好友申请。
- 好友申请已同意。
- 好友申请已拒绝。

因此服务端需要一张很薄的 `user_events` 排序表。它不是未来功能预留，只负责给上述已实现业务分配统一、连续的接收顺序。

`user_events` 不保存 JSON，不复制消息正文和用户资料，只保存接收者、连续序号、事件类型以及指向业务表的 ID。

## 3. 统一命名和类型

| 项目 | 约定 |
|---|---|
| 表名 | 小写复数 snake_case |
| 用户 ID | `user_id` |
| 私聊 ID | `thread_id` |
| 消息 ID | `message_id` |
| 好友申请 ID | `friend_request_id` |
| 发送者 | `sender_user_id` |
| 好友申请双方 | `requester_user_id`、`target_user_id` |
| 客户端消息幂等键 | `client_message_id` |
| 客户端好友申请幂等键 | `client_request_id` |
| 文件大小 | `file_size_bytes`，数据库中使用整数 |
| 文件哈希 | `sha256`，64 位小写十六进制 |
| 服务端时间 | MySQL `DATETIME(3)`，使用 UTC |
| 客户端时间 | SQLite `INTEGER`，UTC epoch milliseconds |
| 线协议 64 位 ID | JSON 十进制字符串，禁止 JSON number |

### 3.1 消息和事件类型

沿用当前 `ChatMsgType` 数值，避免无关协议改号：

| 值 | 名称 | 业务表 |
|---:|---|---|
| 0 | `TEXT` | `chat_messages` |
| 1 | `IMAGE` | `chat_messages + message_resources` |
| 3 | `FILE` | `chat_messages + message_resources` |
| 10 | `FRIEND_REQUEST` | `friend_requests` |
| 11 | `FRIEND_ACCEPTED` | `friend_requests` |
| 12 | `FRIEND_REJECTED` | `friend_requests` |

### 3.2 服务端消息状态

| 值 | 名称 | 含义 |
|---:|---|---|
| 0 | `PENDING` | 资源元数据已创建，文件未上传完成 |
| 1 | `PUBLISHED` | 消息已发布，可进入历史和接收方事件流 |
| 2 | `FAILED` | 资源上传失败或超时 |

文本消息创建时直接为 PUBLISHED。图片和文件先为 PENDING，完整性校验成功后变为 PUBLISHED。

### 3.3 好友申请状态

| 值 | 名称 | 含义 |
|---:|---|---|
| 0 | `PENDING` | 待目标用户处理 |
| 1 | `ACCEPTED` | 已同意 |
| 2 | `REJECTED` | 已拒绝 |

### 3.4 客户端发送状态

| 值 | 名称 | 含义 |
|---:|---|---|
| 0 | `SENDING` | 本地已提交，服务端终态未确认 |
| 1 | `SENT` | 服务端已确认；资源消息已完成发布 |
| 2 | `FAILED` | 幂等冲突、源文件丢失或其他终态失败 |

### 3.5 协议消息 ID 精简结果

#### 3.5.1 当前使用情况

按客户端实际发送、客户端回包注册、ChatServer/ResourceServer handler 注册和集成测试交叉检查，`proto/protocol_ids.h` 当前定义的 ID 都仍有用途，不能直接删除其中任何一项：

- `1401/1402` 仍用于客户端第一次创建本地库时分页拉取会话摘要，不是废弃接口。
- `1403/1404` 仍用于打开会话后向前分页加载历史消息。
- `1601/1602` 仍用于上传头像，`1603/1604` 仍用于下载自己、联系人和会话列表中的头像。
- `1701` 是文本、资源和好友事件共用的唯一实时通知，不存在响应包。

旧分类通知和接收方 ACK 已经删除；它们的旧数值不再保留。当前 ID 是否有效只看下面的完整表，未列出的数字没有协议语义。

#### 3.5.2 重排后的完整 ID 表

1001 至 1005 只是客户端 HTTP 回调路由 ID，不写入 TCP 帧；其余 ID 才是 ChatServer 或 ResourceServer 的 TCP 消息 ID。

| 功能域 | ID | 符号 | 当前业务用途 |
|---|---:|---|---|
| HTTP | `1001` | `MSG_GET_VARIFY_CODE` | 获取邮箱验证码 |
| HTTP | `1002` | `MSG_REG_USER` | 注册用户 |
| HTTP | `1003` | `MSG_RESET_PWD` | 重置密码 |
| HTTP | `1004` | `MSG_LOGIN_USER` | 登录并获取服务器地址和 token |
| HTTP | `1005` | `MSG_REASSIGN_CHAT` | 断线后复用 token 重新分配 ChatServer |
| 连接 | `1101/1102` | `MSG_CHAT_LOGIN` / `MSG_CHAT_LOGIN_RSP` | ChatServer 登录和登录快照 |
| 连接 | `1103/1104` | `MSG_HEART_BEAT_REQ` / `MSG_HEARTBEAT_RSP` | 心跳 |
| 连接 | `1105` | `MSG_NOTIFY_OFF_LINE` | 服务端通知当前连接被踢下线；无响应 |
| 好友 | `1201/1202` | `MSG_SEARCH_USER_REQ` / `MSG_SEARCH_USER_RSP` | 搜索用户 |
| 好友 | `1203/1204` | `MSG_ADD_FRIEND_REQ` / `MSG_ADD_FRIEND_RSP` | 发起好友申请 |
| 好友 | `1205/1206` | `MSG_HANDLE_FRIEND_REQ` / `MSG_HANDLE_FRIEND_RSP` | 同意或拒绝好友申请 |
| 私聊 | `1301/1302` | `MSG_TEXT_CHAT_REQ` / `MSG_TEXT_CHAT_RSP` | 发送文本消息 |
| 私聊 | `1303/1304` | `MSG_CREATE_PRIVATE_CHAT_REQ` / `MSG_CREATE_PRIVATE_CHAT_RSP` | 创建或取得双方唯一私聊会话 |
| 历史同步 | `1401/1402` | `MSG_LOAD_CHAT_THREAD_REQ` / `MSG_LOAD_CHAT_THREAD_RSP` | 首次本地初始化时分页拉取会话摘要 |
| 历史同步 | `1403/1404` | `MSG_LOAD_CHAT_MSG_REQ` / `MSG_LOAD_CHAT_MSG_RSP` | 分页加载一个会话的历史消息 |
| 历史同步 | `1405/1406` | `MSG_SYNC_USER_MESSAGE_REQ` / `MSG_SYNC_USER_MESSAGE_RSP` | 按连续事件序号增量同步 |
| 资源 | `1501/1502` | `MSG_RESOURCE_LOGIN_REQ` / `MSG_RESOURCE_LOGIN_RSP` | ResourceServer 登录鉴权 |
| 资源 | `1503/1504` | `MSG_CREATE_RESOURCE_REQ` / `MSG_CREATE_RESOURCE_RSP` | 创建图片或文件消息元数据 |
| 资源 | `1505/1506` | `MSG_RESOURCE_CHUNK_UPLOAD_REQ` / `MSG_RESOURCE_CHUNK_UPLOAD_RSP` | 上传资源分片 |
| 资源 | `1507/1508` | `MSG_RESOURCE_UPLOAD_PROGRESS_REQ` / `MSG_RESOURCE_UPLOAD_PROGRESS_RSP` | 查询上传进度并恢复上传 |
| 资源 | `1509/1510` | `MSG_RESOURCE_DOWN_INFO_REQ` / `MSG_RESOURCE_DOWN_INFO_RSP` | 查询资源下载信息和权限 |
| 资源 | `1511/1512` | `MSG_RESOURCE_CHUNK_DOWN_REQ` / `MSG_RESOURCE_CHUNK_DOWN_RSP` | 下载资源分片 |
| 头像 | `1601/1602` | `MSG_UPLOAD_HEAD_ICON_REQ` / `MSG_UPLOAD_HEAD_ICON_RSP` | 上传头像 |
| 头像 | `1603/1604` | `MSG_DOWN_LOAD_FILE_REQ` / `MSG_DOWN_LOAD_FILE_RSP` | 下载头像 |
| 用户事件 | `1701` | `MSG_NOTIFY_USER_MESSAGE` | 实时推送文本、资源和好友事件；无响应 |

数值只在 `proto/protocol_ids.h` 定义，各端枚举壳统一引用该文件。客户端、ChatServer、ResourceServer 必须同批发布。SQLite outbox 保存业务操作和 JSON 请求，不保存 TCP 消息 ID。

#### 3.5.3 当前最小 JSON 字段

发送者身份一律取已认证 session，业务请求不再重复携带 `sender_user_id`、`uid` 或 `fromuid`。

| ID | 请求字段 | 成功响应字段 |
|---:|---|---|
| `1103/1104` | 空对象 `{}` | `error` |
| `1203/1204` | `target_user_id`、`client_request_id`、`request_message` | `error` 加好友申请字段 |
| `1205/1206` | `friend_request_id`、`action` | `error` 加处理后的好友申请字段 |
| `1301/1302` | `target_user_id`、`thread_id`、`client_message_id`、`text_content` | `error` 加消息 envelope |
| `1303/1304` | `target_user_id` | `error`、`target_user_id`、`thread_id` |
| `1405/1406` | `after_event_seq`、`limit` | `error`、`events`、`next_event_seq`、`has_more` |
| `1503/1504` | `target_user_id`、`thread_id`、`client_message_id`、`message_type`、`original_file_name`、`file_size_bytes`、`sha256`、`mime_type` | `error` 加资源消息 envelope |

`message_id`、`friend_request_id`、`thread_id`、`event_seq`、`after_event_seq`、`next_event_seq` 和 `file_size_bytes` 在 TCP JSON 中均使用十进制字符串。

## 4. 服务端 MySQL 表设计

服务端只使用 7 张业务表：

1. `users`
2. `friendships`
3. `private_chats`
4. `chat_messages`
5. `message_resources`
6. `friend_requests`
7. `user_events`

### 4.1 `users`

保存账户、公开资料和当前项目统一接收序号头。

| 字段 | 类型 | 约束 | 含义 |
|---|---|---|---|
| `user_id` | `BIGINT UNSIGNED` | PK, AUTO_INCREMENT | 唯一用户 ID；不再同时保留 `id` 和 `uid` |
| `username` | `VARCHAR(64)` | NOT NULL, UNIQUE | 登录用户名 |
| `email` | `VARCHAR(254)` | NOT NULL, UNIQUE | 登录和找回密码邮箱 |
| `password_hash` | `VARBINARY(255)` | NOT NULL | PBKDF2 自描述哈希，禁止明文 |
| `nickname` | `VARCHAR(64)` | NOT NULL DEFAULT `''` | 显示昵称 |
| `profile_bio` | `VARCHAR(255)` | NOT NULL DEFAULT `''` | 个人简介 |
| `gender` | `TINYINT UNSIGNED` | NOT NULL DEFAULT 0 | 当前客户端使用的性别枚举 |
| `avatar_key` | `VARCHAR(255)` | NOT NULL DEFAULT `''` | 默认头像资源名或上传头像文件名 |
| `last_event_seq` | `BIGINT UNSIGNED` | NOT NULL DEFAULT 0 | 已为该用户分配的最大接收事件序号 |

索引：

- `PRIMARY KEY (user_id)`。
- `UNIQUE KEY uk_users_username (username)`。
- `UNIQUE KEY uk_users_email (email)`。

分配接收序号时锁定目标用户行：

```sql
SELECT last_event_seq FROM users WHERE user_id = ? FOR UPDATE;
UPDATE users SET last_event_seq = last_event_seq + 1 WHERE user_id = ?;
```

`last_event_seq` 是服务端序号头，不是客户端消费进度。

### 4.2 `friendships`

当前不做联系人备注，因此一对好友只保存一行无方向关系。

| 字段 | 类型 | 约束 | 含义 |
|---|---|---|---|
| `lower_user_id` | `BIGINT UNSIGNED` | PK(1), FK | 两个用户 ID 中较小者 |
| `higher_user_id` | `BIGINT UNSIGNED` | PK(2), FK | 两个用户 ID 中较大者 |

约束和索引：

- `PRIMARY KEY (lower_user_id, higher_user_id)`。
- `CHECK (lower_user_id < higher_user_id)`。
- `KEY idx_friendships_higher (higher_user_id, lower_user_id)`，使两个方向查询都能使用索引。
- 接受好友申请时使用 `LEAST/GREATEST` 生成固定顺序并插入一行。

### 4.3 `private_chats`

当前项目只有私聊，不保留通用 `chat_threads`、群聊表或成员表。

| 字段 | 类型 | 约束 | 含义 |
|---|---|---|---|
| `thread_id` | `BIGINT UNSIGNED` | PK, AUTO_INCREMENT | 私聊会话 ID |
| `lower_user_id` | `BIGINT UNSIGNED` | NOT NULL, FK | 两个成员中 ID 较小者 |
| `higher_user_id` | `BIGINT UNSIGNED` | NOT NULL, FK | 两个成员中 ID 较大者 |

约束和索引：

- `CHECK (lower_user_id < higher_user_id)`。
- `UNIQUE KEY uk_private_chats_pair (lower_user_id, higher_user_id)`，并发创建同一私聊时由唯一键收敛。
- `KEY idx_private_chats_higher (higher_user_id, thread_id)`。
- 历史读取、发送消息、创建资源和下载资源，都通过本表校验当前用户是否为两个成员之一。

### 4.4 `chat_messages`

只保存真正进入私聊时间线的文本、图片和文件，不保存好友申请、同意或拒绝。

| 字段 | 类型 | 约束 | 含义 |
|---|---|---|---|
| `message_id` | `BIGINT UNSIGNED` | PK, AUTO_INCREMENT | 服务端消息 ID，也是历史分页游标 |
| `thread_id` | `BIGINT UNSIGNED` | NOT NULL, FK | 所属私聊 |
| `sender_user_id` | `BIGINT UNSIGNED` | NOT NULL, FK | 发送者 |
| `client_message_id` | `VARCHAR(64)` | NOT NULL | 客户端幂等键 |
| `message_type` | `TINYINT UNSIGNED` | NOT NULL | 只允许 0、1、3 |
| `text_content` | `TEXT` | NULL | 仅文本消息使用 |
| `status` | `TINYINT UNSIGNED` | NOT NULL | PENDING、PUBLISHED、FAILED |
| `created_at` | `DATETIME(3)` | NOT NULL | 服务端创建时间，也是聊天显示时间 |

约束和索引：

- `UNIQUE KEY uk_chat_messages_client (sender_user_id, client_message_id)`，实现 1301/1503 幂等。
- `KEY idx_chat_messages_history (thread_id, status, message_id)`，历史只查询 PUBLISHED。
- `KEY idx_chat_messages_pending (status, message_type, created_at)`，资源超时清理使用。
- `CHECK (message_type IN (0,1,3))`。
- 文本要求 `text_content IS NOT NULL` 且没有资源扩展行。
- 图片、文件要求 `text_content IS NULL` 且有一条资源扩展行。
- 不保存 `recipient_user_id`：根据 `private_chats` 的两名成员和发送者即可得到接收者。
- 不保存 `recv_seq`：接收顺序只在 `user_events` 中保存。
- 不保存服务端已读状态、客户端发送状态或上传偏移。

### 4.5 `message_resources`

图片和文件共用一张一对一资源扩展表。

| 字段 | 类型 | 约束 | 含义 |
|---|---|---|---|
| `message_id` | `BIGINT UNSIGNED` | PK, FK | 对应 `chat_messages.message_id` |
| `original_file_name` | `VARCHAR(255)` | NOT NULL | 清洗后的原始文件名，仅展示 |
| `file_size_bytes` | `BIGINT UNSIGNED` | NOT NULL | 完整文件字节数 |
| `sha256` | `CHAR(64)` | NOT NULL | 完整文件 SHA-256 小写 hex |
| `mime_type` | `VARCHAR(128)` | NOT NULL | MIME 类型 |

规则：

- 服务端文件路径仍由 `<sender_user_id>/<message_id>` 推导，不在表中重复保存。
- 进行中文件使用 `.part` 后缀。
- 上传进度以 `.part` 实际长度为真值，不建进度字段。
- 资源是否已发布只看 `chat_messages.status`，不在本表重复保存状态。

### 4.6 `friend_requests`

好友申请、同意和拒绝的权威状态，不再借用聊天消息行。

| 字段 | 类型 | 约束 | 含义 |
|---|---|---|---|
| `friend_request_id` | `BIGINT UNSIGNED` | PK, AUTO_INCREMENT | 好友申请 ID |
| `requester_user_id` | `BIGINT UNSIGNED` | NOT NULL, FK | 发起申请的用户 |
| `target_user_id` | `BIGINT UNSIGNED` | NOT NULL, FK | 处理申请的用户 |
| `client_request_id` | `VARCHAR(64)` | NOT NULL | 发起端幂等键 |
| `request_message` | `VARCHAR(255)` | NOT NULL DEFAULT `''` | 好友验证消息 |
| `status` | `TINYINT UNSIGNED` | NOT NULL DEFAULT 0 | PENDING、ACCEPTED、REJECTED |
| `thread_id` | `BIGINT UNSIGNED` | NULL, FK | 接受后创建或复用的私聊 ID |
| `created_at` | `DATETIME(3)` | NOT NULL | 申请时间 |

约束和索引：

- `CHECK (requester_user_id <> target_user_id)`。
- `UNIQUE KEY uk_friend_requests_client (requester_user_id, client_request_id)`，实现申请幂等和冲突判断。
- `KEY idx_friend_requests_target (target_user_id, status, created_at)`，登录申请列表使用。
- `KEY idx_friend_requests_requester (requester_user_id, status, created_at)`。
- 新建申请事务先锁定目标 `users` 行，再检查同方向是否已有 PENDING，避免并发插入重复待处理申请。
- 接受某条申请时，按当前业务把双方所有 PENDING 申请更新为 ACCEPTED 并写入 `thread_id`。
- 拒绝只更新被处理的那条申请。

### 4.7 `user_events`

只负责当前 1701 和 1405/1406 所需的接收顺序，不保存业务正文。

| 字段 | 类型 | 约束 | 含义 |
|---|---|---|---|
| `recipient_user_id` | `BIGINT UNSIGNED` | PK(1), FK | 事件接收者 |
| `event_seq` | `BIGINT UNSIGNED` | PK(2) | 接收者维度连续序号 |
| `event_type` | `TINYINT UNSIGNED` | NOT NULL | 0、1、3、10、11、12 |
| `message_id` | `BIGINT UNSIGNED` | NULL, FK | 文本/图片/文件事件对应消息 |
| `friend_request_id` | `BIGINT UNSIGNED` | NULL, FK | 好友事件对应申请 |

约束和索引：

- `PRIMARY KEY (recipient_user_id, event_seq)`，直接支持增量查询。
- `CHECK ((message_id IS NOT NULL) <> (friend_request_id IS NOT NULL))`，两种业务引用必须且只能出现一个。
- 消息事件要求 `event_type IN (0,1,3)` 且 `message_id` 非空。
- 好友事件要求 `event_type IN (10,11,12)` 且 `friend_request_id` 非空。
- `UNIQUE KEY uk_user_events_message (recipient_user_id, event_type, message_id)`。
- `UNIQUE KEY uk_user_events_friend (recipient_user_id, event_type, friend_request_id)`。

1405/1406 查询：

```sql
SELECT recipient_user_id, event_seq, event_type, message_id, friend_request_id
FROM user_events
WHERE recipient_user_id = ? AND event_seq > ?
ORDER BY event_seq ASC
LIMIT ?;
```

查询事件行后，根据 `event_type` 批量读取 `chat_messages + message_resources` 或 `friend_requests + users`，构造现有统一 envelope。好友申请事件附带申请人资料；同意、拒绝事件附带目标用户资料，使接收方拿到的始终是“对方资料”。

## 5. 客户端 SQLite 表设计

客户端每个用户一个 `AppDataLocation/user/<user_id>/chat.db`，只由 LocalChatWorker 的 QSQLITE 命名连接访问。

客户端使用 7 张表：

1. `messages`
2. `message_resources`
3. `conversations`
4. `friend_requests`
5. `contacts`
6. `outbox`
7. `sync_state`

### 5.1 `messages`

只保存聊天气泡需要的文本、图片和文件，不保存好友申请及处理结果。

| 字段 | SQLite 类型 | 约束 | 含义 |
|---|---|---|---|
| `local_message_id` | `INTEGER` | PK AUTOINCREMENT | 本地主键，供资源表引用 |
| `message_id` | `INTEGER` | NULL, UNIQUE | 服务端消息 ID；发送确认前为 NULL |
| `client_message_id` | `TEXT` | NULL, UNIQUE | 本端发送幂等键；接收消息为 NULL |
| `thread_id` | `INTEGER` | NOT NULL | 所属私聊 |
| `sender_user_id` | `INTEGER` | NOT NULL | 发送者 |
| `message_type` | `INTEGER` | NOT NULL | 只允许 0、1、3 |
| `text_content` | `TEXT` | NULL | 仅文本消息使用 |
| `send_status` | `INTEGER` | NOT NULL | SENDING、SENT、FAILED |
| `created_at` | `INTEGER` | NOT NULL | UTC epoch milliseconds |

约束和索引：

- `CHECK (message_id IS NOT NULL OR client_message_id IS NOT NULL)`。
- `CHECK (message_type IN (0,1,3))`。
- `INDEX idx_messages_history (thread_id, message_id)`。
- `INDEX idx_messages_local_order (thread_id, created_at, local_message_id)`，用于包含待确认消息的当前会话排序。
- 接收消息只用 `message_id` 去重，不再生成 `server-<message_id>` 伪 client ID。
- 不保存 `receiver_user_id`，对方由 `conversations.peer_user_id` 推导。
- 不保存 `event_seq`，统一游标只属于 `sync_state`。

### 5.2 `message_resources`

| 字段 | SQLite 类型 | 约束 | 含义 |
|---|---|---|---|
| `local_message_id` | `INTEGER` | PK, FK | 对应本地图片或文件消息 |
| `original_file_name` | `TEXT` | NOT NULL | 原始文件名 |
| `local_file_path` | `TEXT` | NULL | 发送端源文件或接收端完整缓存路径 |
| `file_size_bytes` | `INTEGER` | NOT NULL | 完整文件字节数 |
| `sha256` | `TEXT` | NOT NULL | 完整文件 SHA-256 |
| `mime_type` | `TEXT` | NOT NULL | MIME 类型 |

规则：

- `FOREIGN KEY (local_message_id) REFERENCES messages(local_message_id) ON DELETE CASCADE`。
- 下载中的 `.part` 路径由 `message_id` 和原文件名推导，不增加字段。
- 上传和下载实时状态仍由 FileTcpMgr/FileBubble 运行时对象管理，不放入 SQLite。

### 5.3 `conversations`

只服务当前私聊列表和历史分页。

| 字段 | SQLite 类型 | 约束 | 含义 |
|---|---|---|---|
| `thread_id` | `INTEGER` | PK | 私聊 ID |
| `peer_user_id` | `INTEGER` | NOT NULL | 当前用户之外的另一名成员 |
| `last_message_id` | `INTEGER` | NULL | 最近一条已确认的服务端消息 ID |
| `oldest_loaded_message_id` | `INTEGER` | NULL | 当前已加载历史中的最小消息 ID |
| `history_complete` | `INTEGER` | NOT NULL DEFAULT 0 | 是否已经加载到历史起点 |
| `updated_at` | `INTEGER` | NOT NULL | 会话列表排序时间 |

索引和规则：

- `INDEX idx_conversations_updated (updated_at DESC, thread_id DESC)`。

### 5.4 `friend_requests`

客户端好友申请界面投影，不与 `messages` 共用 DTO 或表。

| 字段 | SQLite 类型 | 约束 | 含义 |
|---|---|---|---|
| `friend_request_id` | `INTEGER` | PK | 服务端好友申请 ID |
| `requester_user_id` | `INTEGER` | NOT NULL | 申请人 |
| `target_user_id` | `INTEGER` | NOT NULL | 目标用户 |
| `request_message` | `TEXT` | NOT NULL DEFAULT `''` | 验证消息 |
| `status` | `INTEGER` | NOT NULL | PENDING、ACCEPTED、REJECTED |
| `thread_id` | `INTEGER` | NULL | 同意后私聊 ID |
| `peer_username` | `TEXT` | NOT NULL DEFAULT `''` | 对方用户名快照 |
| `peer_nickname` | `TEXT` | NOT NULL DEFAULT `''` | 对方昵称快照 |
| `peer_avatar_key` | `TEXT` | NOT NULL DEFAULT `''` | 对方头像快照 |
| `peer_gender` | `INTEGER` | NOT NULL DEFAULT 0 | 对方性别快照 |

规则：

- 不保存 `direction`，根据当前数据库用户与申请双方推导。
- 不保存备注字段。
- 收到申请时 peer 是申请人；自己发起申请时 peer 是目标用户。
- 好友申请验证消息就是当前 ApplyInfo 使用的 `_desc`，不额外保存申请人个人简介。
- 好友同意时把本地双方 PENDING 申请一起更新为 ACCEPTED；拒绝只更新对应申请。
- 好友同意和拒绝只更新本表；不再向 `messages` 插入系统文本。

### 5.5 `contacts`

| 字段 | SQLite 类型 | 约束 | 含义 |
|---|---|---|---|
| `user_id` | `INTEGER` | PK | 联系人用户 ID |
| `thread_id` | `INTEGER` | NOT NULL | 对应私聊 ID |
| `username` | `TEXT` | NOT NULL DEFAULT `''` | 用户名快照 |
| `nickname` | `TEXT` | NOT NULL DEFAULT `''` | 昵称快照 |
| `avatar_key` | `TEXT` | NOT NULL DEFAULT `''` | 头像键快照 |
| `gender` | `INTEGER` | NOT NULL DEFAULT 0 | 性别快照 |

规则：

- 不保存联系人备注。
- 登录好友列表快照和好友接受事件都使用 UPSERT 更新本表。
- 好友接受事务同时 UPSERT `contacts` 和 `conversations`。

### 5.6 `outbox`

只覆盖当前已经实现可靠发送的文本、图片和文件。

| 字段 | SQLite 类型 | 约束 | 含义 |
|---|---|---|---|
| `operation_id` | `INTEGER` | PK AUTOINCREMENT | 冷启动恢复和首次派发顺序 |
| `client_message_id` | `TEXT` | NOT NULL, UNIQUE | 对应待发送消息，也是服务端幂等键 |
| `operation_type` | `TEXT` | NOT NULL | `SEND_TEXT` 或 `SEND_RESOURCE` |
| `stage` | `TEXT` | NOT NULL DEFAULT `''` | 文本为空；资源为 `metadata` 或 `uploading` |
| `payload_json` | `TEXT` | NOT NULL | 已提交的 1301 或 1503 请求快照 |

规则：

- 删除当前重复表达同一键的 `dedup_key` 和 `request_id`，Dispatcher 直接使用 `client_message_id`。
- 不保存 `retry_count` 和 `next_retry_at`。
- `FOREIGN KEY (client_message_id) REFERENCES messages(client_message_id) ON DELETE CASCADE`。
- `messages + message_resources + outbox` 首次写入处于同一 SQLite 事务。
- 1302 成功时同事务更新消息为 SENT 并删除 outbox。
- 1504 成功时同事务写回 `message_id` 并将 stage 改为 `uploading`。
- 1506 完成时同事务更新消息为 SENT 并删除 outbox。
- 只有上述本地事务提交成功后，Dispatcher 才移除内存登记项。

### 5.7 `sync_state`

| 字段 | SQLite 类型 | 约束 | 含义 |
|---|---|---|---|
| `singleton_id` | `INTEGER` | PK, 固定为 1 | 单行表主键 |
| `last_event_seq` | `INTEGER` | NOT NULL DEFAULT 0 | 已完整应用的最大连续事件序号 |
| `bootstrap_complete` | `INTEGER` | NOT NULL DEFAULT 0 | 登录基线是否已建立 |

约束和规则：

- `CHECK (singleton_id = 1)`。
- `CHECK (last_event_seq >= 0)`。
- 收到聊天或好友事件后，业务表写入和游标推进必须处于同一 SQLite 事务。
- 业务请求回包携带的对端序号不能推进本端游标。
- 收到 `event_seq <= last_event_seq` 直接忽略。
- 收到 `event_seq > last_event_seq + 1` 先暂存并立即发起 1405 补洞。

## 6. 服务端事务

### 6.1 文本消息

1. 根据 `private_chats` 校验发送者和接收者属于该私聊。
2. 按 `(sender_user_id, client_message_id)` 做幂等和冲突检查。
3. 插入 `chat_messages(status=PUBLISHED)`。
4. 锁定接收者 `users` 行，分配下一个 `event_seq`。
5. 插入 `user_events(event_type=TEXT, message_id=...)`。
6. 消息、序号头和事件同事务提交。
7. 提交后回复 1302，再尝试 1701；推送失败不回滚。

### 6.2 资源消息

1503 创建元数据事务：

1. 校验私聊成员、消息类型、文件名、大小、SHA-256 和 MIME。
2. 插入 `chat_messages(status=PENDING)`。
3. 插入 `message_resources`。
4. 不分配事件序号，接收方不可见。

上传完成事务：

1. 校验 `.part` 分片和整文件 SHA-256，原子改名为最终文件。
2. 锁定 PENDING 消息并更新为 PUBLISHED。
3. 为接收者分配 `event_seq` 并插入 `user_events`。
4. 提交后才发送 1701。

超时资源只把消息改为 FAILED，不分配序号、不通知接收者。

### 6.3 好友申请

1. 锁定目标用户行并校验双方用户、不能申请自己、当前不是好友。
2. 按 `(requester_user_id, client_request_id)` 做幂等和冲突检查。
3. 检查同方向是否已有 PENDING 申请。
4. 插入 `friend_requests(status=PENDING)`。
5. 使用已经锁定的目标用户行分配 `event_seq`。
6. 插入 `user_events(event_type=FRIEND_REQUEST, friend_request_id=...)`。
7. 同事务提交后回复申请人并尝试向目标用户发送 1701。

### 6.4 同意好友申请

1. 锁定申请行，校验当前用户是目标用户且状态为 PENDING。
2. 查找或创建双方唯一 `private_chats` 行。
3. 插入双方唯一 `friendships` 行。
4. 把双方现有 PENDING 申请更新为 ACCEPTED，并写入 `thread_id`。
5. 锁定原申请人的 users 行并分配 `event_seq`。
6. 插入 `user_events(event_type=FRIEND_ACCEPTED, friend_request_id=...)`。
7. 同事务提交后回复处理人并尝试通知申请人。

客户端收到后更新 `friend_requests + contacts + conversations`，不写 `messages`。

### 6.5 拒绝好友申请

1. 锁定申请行并校验处理权限和 PENDING 状态。
2. 更新为 REJECTED。
3. 为申请人分配序号并插入 `FRIEND_REJECTED` 事件。
4. 同事务提交后回复处理人并尝试通知申请人。

## 7. 客户端同步事务

1406 页面和连续 1701 都进入同一个应用入口：

```text
BEGIN IMMEDIATE
  TEXT/IMAGE/FILE   -> messages + message_resources + conversations
  FRIEND_REQUEST    -> friend_requests
  FRIEND_ACCEPTED   -> friend_requests + contacts + conversations
  FRIEND_REJECTED   -> friend_requests
  UPDATE sync_state.last_event_seq
COMMIT
提交后发送分类后的 GUI 信号
```

任一事件解析或 SQL 写入失败都整体回滚，不能跳过坏事件后继续推进游标。

登录快照只包含当前好友申请、好友列表、私聊列表和服务端 `users.last_event_seq` checkpoint。全新客户端先落快照并设置 checkpoint，旧聊天正文按会话历史接口懒加载。已有数据库重连不能直接跳游标，仍从本地 `last_event_seq` 增量追平。

## 8. 历史和资源权限

### 8.1 历史消息

历史查询必须先检查请求用户等于 `private_chats.lower_user_id` 或 `higher_user_id`，再执行：

```sql
SELECT ...
FROM chat_messages
WHERE thread_id = ?
  AND status = 1
  AND message_id < ?
ORDER BY message_id DESC
LIMIT ?;
```

客户端收到历史页时只写 `messages/message_resources` 和历史游标，不增加未读、不修改 `sync_state`。

### 8.2 资源下载

下载前根据资源消息的 `thread_id` 查询 `private_chats` 并校验请求者是成员。只有 `chat_messages.status=PUBLISHED` 的资源允许下载。

## 9. DTO 拆分

客户端按当前业务边界使用以下 DTO：

| DTO | 对应内容 |
|---|---|
| `UserEventDTO` | `event_seq/event_type/message_id/friend_request_id` |
| `LocalMessageDTO` | 客户端 `messages` |
| `LocalMessageResourceDTO` | 客户端 `message_resources` |
| `LocalConversationDTO` | 客户端 `conversations` |
| `LocalFriendRequestDTO` | 客户端 `friend_requests` |
| `LocalContactDTO` | 客户端 `contacts` |
| `OutboxEntryDTO` | 客户端 `outbox` |

拆 DTO 不拆数据库线程。所有客户端写入继续由 LocalChatWorker 的一个 QSQLITE 连接完成。

## 10. 必测场景

### 服务端

- 文本、图片、文件相同幂等键同内容返回原 ID，异内容返回冲突。
- PENDING 资源不出现在历史和 `user_events`；完成后只产生一次事件。
- 好友申请重复请求、并发同方向申请、接受、拒绝全部幂等。
- 接受申请时 `friendships`、`private_chats`、申请状态和用户事件全部提交或全部回滚。
- 文本、资源完成、好友申请和处理结果共享的 `event_seq` 连续且唯一。
- 非私聊成员不能发送、读取历史或下载资源。

### 客户端

- 首次发送时 `messages/resources/outbox` 原子提交。
- 1302、1504、1506 只有本地事务成功后才推进 Dispatcher 内存状态。
- 混合 1406 页面能分别写入聊天表和好友表，并只在全部成功后推进游标。
- 好友同意和拒绝不进入 `messages`，不生成聊天气泡和消息未读。
- 重复 1701/1406 不重复消息、好友申请、联系人或未读计数。
- 事件缺口不会越过缺口推进 `last_event_seq`。
- 历史回填不增加未读，也不推进统一事件游标。

## 11. 最终不变式

1. `chat_messages` 只保存文本、图片和文件。
2. `friend_requests` 只保存申请、同意和拒绝状态。
3. `user_events` 只保存当前统一同步需要的顺序和业务引用，不保存 JSON 正文。
4. PENDING/FAILED 资源不会进入历史或接收方事件流。
5. 服务端业务写入、`users.last_event_seq` 和 `user_events` 同事务。
6. 客户端业务投影和 `sync_state.last_event_seq` 同事务。
7. 客户端 outbox 是未完成发送的唯一持久化真值。
8. 所有历史和资源操作先通过 `private_chats` 校验成员。
