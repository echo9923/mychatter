# 当前用户事件链路

## 核心模型

聊天消息、资源元数据和好友申请不再共用一张大表：

- `chat_messages` 只保存文本、图片和文件消息。
- `message_resources` 只保存图片和文件的资源元数据，以 `message_id` 一对一关联聊天消息。
- `friend_requests` 保存好友申请及其 `PENDING/ACCEPTED/REJECTED` 状态。
- `user_events` 只保存接收者顺序和业务引用，不保存聊天正文或好友资料。
- `users.last_event_seq` 是服务端为该用户分配过的最大事件序号，不是客户端消费进度。
- 客户端 `sync_state.last_event_seq` 是已经完整应用的最大连续事件序号。

可靠性不依赖接收方 ACK。业务事务提交即成功；`1701` 只是低延迟通知，登录、重连、缺口检测和 30 至 60 秒随机周期同步通过 `1405/1406` 补齐。

## 文本消息

1. 客户端用一个 SQLite 事务写入 `messages + outbox`，随后发送 `1301`。
2. `1301` 只发送 `client_message_id`、`thread_id`、`target_user_id` 和 `text_content`。发送者取认证 Session。
3. ChatServer 校验发送者和目标用户是该 `private_chats` 行的两名成员。
4. DAO 按 `(sender_user_id, client_message_id)` 判断幂等或内容冲突。
5. 新消息事务插入 `chat_messages`，锁定接收者 `users` 行，递增 `last_event_seq`，再插入引用该消息的 `user_events`。
6. ChatServer 提交后先返回 `1302`，再尝试用 `1701` 推送完整用户事件。跨服推送失败不会回滚数据库。
7. 客户端收到成功 `1302` 后，在一个 SQLite 事务中写入服务端 `message_id`、标记 `SENT` 并删除 outbox。

相同 `client_message_id` 和相同内容重试返回原 `message_id`；相同键但内容不同返回 `MESSAGE_CONFLICT`。幂等重试不新增消息或事件序号。

## 资源消息

1. `1503` 发送 `client_message_id`、`thread_id`、`target_user_id`、`message_type`、`original_file_name`、`file_size_bytes`、`sha256` 和 `mime_type`；发送者取认证 Session。
2. ChatServer 在一个事务中插入 `chat_messages(status=PENDING)` 和 `message_resources`。此时不插入 `user_events`，接收者不可见。
3. 客户端先用 `1507` 查询 `.part` 实际长度，再从服务端偏移用 `1505` 上传分片。
4. ResourceServer 收齐并校验整文件 SHA-256 后，锁定资源消息和接收者 `users` 行。
5. 同一事务把 `chat_messages.status` 更新为 `PUBLISHED`，分配 `event_seq` 并插入 `user_events`。
6. 提交后 `1506` 返回 `status/event_seq`，再尝试 `1701` 实时通知。
7. 客户端把发送后的归档路径写入 `message_resources.local_file_path`，标记消息 `SENT` 并删除 outbox。

重复完成返回原事件；失败或过期把消息置为 `FAILED`，不分配事件序号，也不通知接收者。上传进度只以磁盘 `.part` 长度为真值，不进数据库。

## 好友申请

1. 客户端发送 `1203`，字段只有 `target_user_id`、`request_message` 和 `client_request_id`。
2. ChatServer 从 Session 取得申请人，校验双方不是好友、目标用户存在且没有需要复用的同向待处理申请。
3. DAO 插入 `friend_requests(status=PENDING)`，锁定目标用户的 `users` 行，递增 `last_event_seq`，插入引用该申请的 `user_events(event_type=10)`。
4. `1204` 返回 `friend_request_id/event_seq` 和好友申请字段；目标在线时再推送相同内容的 `1701`。

好友申请没有撤销、好友备注、处理备注或拒绝原因字段。好友资料展示字段来自 `users` 查询，不存进服务端好友关系表。

## 同意或拒绝

客户端用 `1205` 发送 `friend_request_id` 和 `action=accept|reject`。关闭处理窗口不发送请求，申请继续保持 `PENDING`。

同意事务：

1. 锁定 `friend_requests` 行，验证当前 Session 用户是 `target_user_id`。
2. 把申请更新为 `ACCEPTED`。
3. 用 `LEAST/GREATEST` 插入唯一一行 `friendships`。
4. 创建或复用唯一一行 `private_chats`，把 `thread_id` 写回申请。
5. 锁定原申请人的 `users` 行，分配 `event_seq`，插入引用原申请的 `user_events(event_type=11)`。
6. 提交后向处理方返回 `1206`，向申请人尝试推送 `1701`。

拒绝事务只把原申请更新为 `REJECTED`，并给申请人插入 `event_type=12` 的 `user_events`；不创建联系人或私聊。

相同动作重试返回原申请状态且不增事件序号；相反动作返回申请已处理；非目标用户按申请不存在处理。

## 增量同步

`1405` 请求：

```json
{"after_event_seq":"42","limit":100}
```

服务端从认证 Session 获取接收者，查询 `user_events` 并按 `event_seq ASC` 返回 `events`、`next_event_seq` 和 `has_more`。每个事件再按引用读取 `chat_messages + message_resources` 或 `friend_requests + users`，构造完整 envelope。游标超过 `users.last_event_seq` 返回 `ERR_SYNC_CURSOR_INVALID`。

客户端收到 `1701` 或 `1406` 页面后统一处理：

- `event_seq <= last_event_seq`：忽略重复。
- `event_seq == last_event_seq + 1`：在一个 SQLite 事务中写入对应业务表并推进游标。
- `event_seq > last_event_seq + 1`：不越过缺口，立即从本地游标发起 `1405`。

聊天事件写 `messages/message_resources/conversations`；好友事件写 `friend_requests/contacts/conversations`。好友事件不会插入聊天 `messages`。

## 登录快照

`1102` 返回 `checkpoint=users.last_event_seq`、好友申请快照和联系人快照。全新客户端先落快照并把本地游标设置为 checkpoint；历史聊天正文随后按私聊历史接口懒加载。已有数据库重连只合并快照，不能直接跳过尚未应用的事件。

## 数据库不变式

- 服务端业务写入、`users.last_event_seq` 和 `user_events` 在同一事务中提交。
- `PRIMARY KEY (recipient_user_id, event_seq)` 保证单用户事件序号唯一。
- `(sender_user_id, client_message_id)` 保证聊天发送幂等。
- `(requester_user_id, client_request_id)` 保证好友申请发送幂等。
- `friendships` 每对用户只有一行；`private_chats` 每对用户只有一行。
- 客户端业务投影和 `sync_state.last_event_seq` 在同一事务中提交。
- 不存在 `recv_seq`、`related_message_id`、好友结果消息、好友备注、好友申请撤销或接收方 ACK。
