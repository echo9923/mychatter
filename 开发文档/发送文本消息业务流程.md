# 统一用户消息链路

## 核心模型

`chat_message` 是唯一用户消息流水，承载文本、图片、文件、好友申请、同意和拒绝结果。每条已经对接收者可见的消息都拥有 `(recv_id, recv_seq)`，其中 `recv_seq` 对单个接收者严格连续。

`user.last_recv_seq` 只是服务端分配序号的头，不记录客户端进度。客户端进度只保存在自己的 SQLite `sync_state.last_recv_seq`。

可靠性不依赖接收方 ACK：事务提交后即为成功；实时推送只是低延迟通道，登录、重连、缺口检测和 30 至 60 秒随机周期同步负责补齐。

## 文本消息

1. 客户端先在 SQLite 的 `messages + outbox` 同一事务中保存待发送消息，然后发送 `1301`。
2. ChatServer 从认证 Session 取得发送者 UID，校验接收者、私聊会话成员关系和 `unique_id`。
3. DAO 开启事务并锁定接收者 `user` 行。
4. DAO 递增 `last_recv_seq`，将新序号写入 `chat_message.recv_seq`，然后提交。
5. `(sender_id, unique_id)` 重试命中原消息时回滚本次临时序号，返回原 `message_id/recv_seq`，因此不会产生序号空洞。
6. ChatServer 先用 `1302` 告知发送方消息已持久化，再尝试推送完整 `1701` envelope。
7. 同服使用 `PostToUser`；跨服仅发送 `to_uid + message_id` 的 `NotifyUserMessage` RPC，目标 ChatServer 回读 MySQL 真值后推送 `1701`。
8. 推送失败不回滚数据库。接收方稍后通过 `1405/1406` 补齐。

## 资源消息

1. `1503` 只创建 `resource_status=UPLOADING` 的元数据行，此时 `recv_seq=NULL`，接收方不可见。
2. 客户端按 `1507 -> 1505` 查询进度并上传分片。
3. ResourceServer 收齐并校验整文件 SHA-256 后开启事务，锁定资源消息和接收者 `user` 行。
4. 同一事务递增 `last_recv_seq`，设置资源 `resource_status=READY` 和 `recv_seq` 后提交。
5. 重复完成直接返回原序号，不重复分配。失败或过期只修改资源状态，不分配序号，也不通知接收者。
6. 提交后通过统一 `NotifyUserMessage` RPC 尝试实时推送，失败由增量同步兜底。

## 好友申请

1. 客户端发送 `1203`，包含目标 UID、描述、备注和本次操作的 UUID。
2. ChatServer 校验双方尚未成为好友。
3. DAO 锁定目标用户序号头；同一 UUID 重试返回原申请，同方向已有 PENDING 申请也返回原申请。
4. 新申请分配目标用户的 `recv_seq`，写入 `FRIEND_APPLY + PENDING` 后提交。
5. `1204` 返回申请消息；目标在线时再推送相同消息的 `1701`。

## 同意或拒绝

客户端用 `1205` 发送 `apply_message_id` 和 `action=accept|reject`。关闭对话框不发送请求，申请继续保持 PENDING。

同意事务：

1. 锁定申请消息，验证当前 Session 用户就是申请接收者。
2. 将申请更新为 ACCEPTED，创建双向好友和唯一私聊会话，并关闭双方其他 PENDING 申请。
3. 锁定申请人的序号头，分配 `recv_seq`。
4. 插入一条 `FRIEND_ACCEPT` 结果消息，关联原申请并带 `thread_id`。
5. 提交后向处理方返回 `1206`，向申请人尝试推送 `1701`。
6. 两端都把这条结果作为“你们已成为好友”的会话系统消息，不复制申请描述。

拒绝事务只把申请更新为 REJECTED，并给申请人插入一条 `FRIEND_REJECT` 消息；不创建联系人或会话，可选拒绝原因保存在 `content`。

相同动作重试返回原结果；相反动作返回申请已处理；非接收者按申请不存在处理，避免泄露申请信息。

## 增量同步与客户端应用

`1405` 请求只有：

```json
{"after_recv_seq":"42","limit":100}
```

服务端从认证 Session 获取 UID，按 `recv_seq ASC` 返回完整消息、`next_recv_seq` 和 `has_more`。游标超过 `user.last_recv_seq` 返回 `ERR_SYNC_CURSOR_INVALID`。

客户端收到 `1701` 时：

- `recv_seq == local + 1`：在一个 SQLite 事务中应用业务数据并推进游标。
- `recv_seq <= local`：忽略重复。
- `recv_seq > local + 1`：暂存消息并立即从 local 游标补拉。

正常连续实时消息不触发拉取。登录、重连、缺口以及 30 至 60 秒随机定时器触发同步，覆盖最后一条实时通知丢失但没有后续消息暴露缺口的情况。

## 登录快照

`1102` 在查询待处理申请和联系人快照前读取 `checkpoint=user.last_recv_seq`。首次本地初始化先覆盖快照，再把本地游标设为 checkpoint，最后同步 checkpoint 之后的消息；已完成 bootstrap 的重连只合并快照，不重置已有游标。重连时，本地仍为 PENDING 但已不在服务端待处理快照中的申请会按联系人快照对账：已有联系人记为 ACCEPTED，否则记为 REJECTED，用于恢复“服务端已提交但 1206 响应丢失”的状态。

## 数据库不变式

- 分配序号、写消息和业务状态必须处于同一事务；失败整体回滚，不留空洞。
- `(recv_id, recv_seq)` 唯一。
- `(sender_id, unique_id)` 保证发送请求幂等。
- `pending_friend_key` 保证同方向最多一条 PENDING 申请，处理完成后自动变为 NULL。
- `related_message_id` 唯一，保证一条申请最多生成一个结果消息。
- 不存在 `friend_apply`、`user_message_sync`、`delivery_status` 或接收方 ACK。
