## 2. P2 实现范围（本轮改动）

### 2.1 存储与并发

- 新增 CAS 布局：`<root>/uploading/<message_id>.part`、`<root>/blobs/<sha[0:2]>/<sha256>`；路径推导唯一真值 `llfc::ResourceUploadingPartPath` / `llfc::ResourceBlobPath`（`server/ResourceServer/src/ResourceUploadFile.cpp`），FileWorker、1507 判定、清理任务共用，不再有第二处拼接。
- 根路径**可配置**：`[Storage] ResourceRoot` → `[Output] ResourceRoot` → 缺省 `<Output.Path>/resource`（`ConfigMgr::InitPath`，`server/ResourceServer/config/config.ini` 已加 `[Storage]` 段与注释）。**同一 CAS 根目录只允许一个 ResourceServer 进程**（互斥是进程内 `std::mutex`）。
- 目录项耐久性：新增 `llfc::EnsureDirectoryDurable`（`ResourceUploadFile.{h,cpp}`）：POSIX 下每次调用都自底向上 fsync **整条祖先条目链直到文件系统根**，不依赖"本次新建了哪些层级"——既覆盖"上次建目录成功但父目录 fsync 失败"的重试（目录已存在，新建集合为空），也覆盖 `ConfigMgr` 启动时已建好 `root/blobs`、其条目在 `root` 里尚未落盘的情况（代价是与路径深度成正比的若干次目录 fsync，位于 CAS/GC 临界区内，**吞吐影响未测量**）。`ConfigMgr::InitPath` 用同一 helper 建 CAS 根与 `uploading`/`blobs`，**创建失败即致命退出**（不再出现"打印错误却继续跑"）。`DurableRename` 在 POSIX 下对目标父目录调用它（Windows 走 `MOVEFILE_WRITE_THROUGH`）。`DurableRename` 的 `already_exists` 出参只在**确认**目标存在时置位，其他错误不与之混淆。
- CAS/GC 互斥：`llfc::BlobInstallGcMutex`（进程级单一互斥）覆盖"blob 安装（no-replace rename）→ 发布事务提交"与"秒传路径的 blob 读取 + 比对 + 发布"，GC 持同一把锁完成"typed 引用查询 + unlink"。**吞吐影响未测量**，文档不做"可忽略"断言，锁只覆盖必需区间。

### 2.2 去重命中的可信度复核

`FileWorker::CompleteResourceUpload`：目标已存在（去重命中）时**不直接当成功**，复核目标精确长度 == DB `file_size_bytes`、整文件 SHA-256 == `message_resources.sha256`、`FlushFileToDisk` 成功；三项全过才删 `.part` 并继续发布。任一不通过 → **保留已校验的 `.part` 与已存在的公开 blob**，回可重试错误 `2104`（`FileWritePermissionFailed`，客户端退避重试）。**不覆盖、不"修复"已有 blob**（可能正被其他已发布消息引用，覆盖即静默损坏已发布内容）。

### 2.3 秒传判定与 1513/1514

- 判定（1507）：消息仍 Pending + 同发送者存在 Published 相同 `sha256`+`file_size_bytes`（`MysqlDao::SenderHasPublishedContent`，联表过滤 `sender_user_id`/`status=1`）+ blob 存在且大小一致 → 下发 `mode:"proof"` 与一次性挑战（`nonce` 16 字节 `RAND_bytes`、`offset` 随机、`length=min(size,64KiB)`、TTL 120s、绑定下发连接、存 `UploadSession`）。查询为 typed 三态：`Transient`（DB 故障）回 `2002` 让客户端重试，**不把"查不到"当"无历史"**。
- 挑战消费顺序：**先**校验归属（本人 Pending 消息、挑战未过期、绑定连接正确）→ 合法持有者消费（一次性）→ **再**做 proof 格式校验（先判 64 位 hex 长度，再常量时间比较）。**非本人（`req_uid != sender`、uid=0、无资源行）回 `ResourceForbidden`（2115）**，不是 2118；挑战不存在/超 TTL/绑定连接不符（未消费挑战）回 `2118` 且**不消费**挑战；只有合法持有者在消费后的格式失败（非 64 hex/摘要长度不为 64/比对不符）才置本会话 `challenge_suppressed`（防伪造者用畸形 proof 打掉真实客户端的挑战）。
- 证明比对通过 → 与普通上传共用 `CompleteResourceUpload` 发布事务 + `UserMessageNotifier`；`Published` 的 1513 重放回**原 `event_seq`**（不新增事件、不发 1701）并清残留 `.part`；普通 1505 写入清除本会话挑战状态。
- 存储侧新增/使用：`llfc::RandomBytes`、`llfc::ConstantTimeEquals`；错误码 `2118 RS_INSTANT_PROOF_INVALID`、消息 ID 1513/1514 仅在 `proto/protocol_ids.h` 定义，三端引用。

### 2.4 孤儿回收

清理任务只扫新 CAS 布局：`uploading/*.part` 超 7 天回收；`blobs/<64 位 hex>` 超 7 天且 `MysqlDao::BlobHasPublishedReference(sha256)` 返回 `No` 才回收——**判定只按 sha256 内容身份，不附加磁盘 `stat` 大小**（`Transient` 一律保留）。查询与 unlink 持 `BlobInstallGcMutex`。旧 `<sender_uid>/<message_id>` 布局与其他残留一律不动，交部署清空。

### 2.5 客户端引擎 proof 状态机

- `transferengine`：`proof_pending` 单飞标记（1513 在途期间丢弃乱序 1508、不对 1514 之外的响应复位控制定时器；`ResumeTransfer`/`ResyncUpload`（经 `BeginQuery`）/`OnConnectionDown` 清位隔离旧阶段）。**暂停只抑制新请求**：`PauseTransfer` 保留 `proof_pending`/`query_sent_ms`（`BeginQuery` 在 `user_paused` 下不发帧），使在途且服务端确实已发布的严格校验 1514 仍能收敛；`HandleTimeout` 在 `user_paused` 时只清计时器、不判连接死亡、不请求重连。
- 1514 仅在 `proof_pending` 为真时采纳，且严格校验 `status == Published`、`server_offset == total_bytes`、`event_seq > 0`；`error==0` 但 `status != Published` 的"无效成功包"按 `ERR_JSON` 坏回包计数（`json_error_count` 累计 → 退避后 1507 重同步 → 达上限转永久失败），不再是"立即无界重同步"。
- 解码层（`resourcecodec`）同步收紧：`error==0` 的 1514 必须带 `status`、`server_offset`，且 `event_seq` 必须是十进制字符串且 `>0`；缺失/JSON 数字/0 一律 `ok=false`，由 engine 按坏回包计数——缺失/wrongtype/mismatch 全部有界。
- 计数归零位置：`json_error_count` **只在普通上传分支清零**（`HandleProgressRsp` 收到普通有效 1508、字段全部通过之后）；`SendInstantProof` **不再清零** `json_error_count`——合法挑战 metadata 只是"新一次证明尝试"，清零会让 `status`/`offset`/`event_seq` 非法的 1514 形成 0→1→0→1 震荡（bad1514 → `ERR_JSON` 计数+1 → 退避 → 1507/1508 合法 proof → 清零 → 再 bad1514），永远到不了 `json_error_limit`；2118 回退后走普通上传分支，由该分支清零。`SendInstantProof` 内仍保留 `publish_retry_count` 原语义（合法 1508/挑战不代表发布重试仍在恶化），`HandleProgressRsp` 的 proof 分支调用后**立即 `return`**、不再触碰可能已被同步回调释放的传输对象；`SendInstantProof` 无返回值，失败与终态都在函数内处理。
- 发送后不得再用裸指针：`_send(1513)` 是同步回调，合法的 Published 1514 可在其中直接派发到 `HandleInstantProofRsp → CompleteTransfer → sig_transfer_finished`，监听者可能 `Reset()`（`_uploads.clear()`）或 `StartUpload` 同 `message_id`（erase + 插入新实例）。因此发送前按 `message_id` 从运行时表取出**同一实例**（`get() == t`）的 `shared_ptr` 握住并缓存 `mid`，发送后只经由该 `shared_ptr` 回看；仅当"表里仍是同一实例 **且** 仍 `proof_pending`"时才 `EmitUpdate`，完成/回滚/Reset/替换一律不再发旧进度（`TransferEngine::SendInstantProof`）。File 线程只读源文件，失败即回退普通上传；`proof_disabled` 与 `2118` 构成闭环。
- 终态同步 emit 前先拷贝 `direction` 再 `emit sig_transfer_finished`（同步 listener 可能重建同 `message_id` 传输 → 原写法是 UAF）。
