# 协议设计知识：消息帧模型与可靠投递

本文解释当前实现。协议号以 `proto/protocol_ids.h` 为准，数据库以 `开发文档/客户端与服务端数据库重构方案.md` 为准。

## 1. 消息 ID 体系

编号规则：

1. 百位表示功能域：10 账户、11 连接、12 好友、13 私聊、14 历史与同步、15 资源、16 头像、17 用户事件。
2. 有回包的 TCP 操作使用奇数请求、相邻偶数响应。
3. `1105` 和 `1701` 是服务端单向通知，没有响应号；未定义数字没有预留语义。
4. 错误码独立使用 20xx/21xx，不与 1xxx 消息 ID 混用。

帧分三类：

| 类型 | 示例 | 发起方是否等待结果 |
|---|---|---|
| 请求 | 1301、1405、1503 | 是 |
| 响应 | 1302、1406、1504 | 结束对应请求的待决状态 |
| 通知 | 1105、1701 | 否 |

## 2. 请求响应和通知的区别

响应的意义是回答一个尚未完成的操作。例如发送方提交文本后，必须等 1302 才知道服务端是否已经持久化；ResourceServer 收到 1505 后必须用 1506 告知分片偏移和状态。

通知没有待决请求。1701 告知客户端“有一个已经提交的用户事件”，客户端不回 ACK。通知可能因断线丢失，但业务不会丢失，因为权威数据和事件顺序已经先写入 MySQL。

为每个通知增加 ACK 会引入新的待确认队列、ACK 重试和服务端送达状态，却不能替代增量同步。当前项目没有已读回执或送达报表业务，所以不保存这些字段。

## 3. TCP 可靠性的边界

TCP 在一条仍然存活的连接内提供有序、无重复字节流。它不保证：

- 对端应用已经解析或持久化一帧；
- 连接断开后在途业务帧能迁移到新连接；
- 发送方能知道断线前最后一条被业务层处理的消息。

因此跨连接可靠性必须由应用层建立。当前项目分别使用两套机制：

- 客户端到服务端：本地 outbox、业务响应和客户端幂等键。
- 服务端到接收者：权威业务表、`user_events` 连续游标和增量同步。

## 4. 客户端到服务端

以文本消息为例：

```text
SQLite 事务写 messages + outbox
  -> 发送 1301
  -> ChatServer 事务写 chat_messages + user_events
  -> 提交成功后返回 1302
  -> 客户端事务标记 SENT + 删除 outbox
```

`1302 error=0` 的含义是服务端业务事务已经提交。它不是 TCP 层的“收到字节”，也不是接收者已经看到消息。

两个常见崩溃窗口都由幂等重试闭合：

1. 服务端提交后、1302 发出前崩溃：客户端仍保留 outbox，重连后用相同 `client_message_id` 重发。
2. 1302 已发出但发送方没有收到：处理方式相同。

服务端唯一键 `(sender_user_id, client_message_id)` 使相同业务重试返回原 `message_id`；相同键但内容不同返回 `MESSAGE_CONFLICT`。客户端只有在本地确认事务提交后才删除 outbox。

资源消息使用同一原则，只是状态机多一个阶段：

```text
1503 元数据 -> 1504 message_id -> SQLite stage=uploading
-> 1507 对齐偏移 -> 1505/1506 分片
-> 服务端 PUBLISHED -> SQLite SENT + 删除 outbox
```

## 5. 服务端到接收者

服务端不是靠 1701 防丢，而是靠以下同一事务：

```text
写业务表
-> 锁定 users 接收者行
-> last_event_seq + 1
-> 写 user_events(recipient_user_id, event_seq, 业务引用)
-> 提交
```

提交后才尝试 1701。同服直接投递到 Session；跨服 gRPC 只携带事件定位信息，目标 ChatServer 回读 MySQL 真值后构造 envelope。推送失败不回滚，客户端随后通过 1405/1406 补齐。

客户端应用规则：

| 条件 | 动作 |
|---|---|
| `event_seq <= last_event_seq` | 重复事件，忽略 |
| `event_seq == last_event_seq + 1` | 同一 SQLite 事务写业务投影并推进游标 |
| `event_seq > last_event_seq + 1` | 不推进游标，从当前游标发起 1405 补洞 |

聊天事件写 `messages/message_resources/conversations`；好友事件写 `friend_requests/contacts/conversations`。好友事件不伪造成系统聊天消息。

## 6. 最后一条通知丢失

仅靠“发现后续序号跳跃”不能发现最后一条通知丢失，因为之后可能长时间没有新事件。因此当前客户端除登录和重连外，还在 30 至 60 秒随机周期执行 1405。服务端返回 `next_event_seq/has_more`，客户端逐页追平。

这套机制没有接收方 ACK，也不需要服务端保存每台客户端的消费进度。每个客户端只在自己的 SQLite 保存 `sync_state.last_event_seq`。

## 7. 好友事件为什么也进入同一游标

好友申请、接受和拒绝都会改变当前 UI 的好友申请或联系人状态。如果它们只靠 1701 和登录快照，在线闪断期间可能长期看不到处理结果。

当前实现把好友正文放在 `friend_requests`，只把引用放入 `user_events`：

- `event_type=10` 引用待处理申请；
- `event_type=11` 引用已接受申请；
- `event_type=12` 引用已拒绝申请。

这样聊天和好友业务仍然分表，但共享一个连续接收顺序。登录快照用于初始化当前状态，事件流用于保证登录后的变化不丢。

## 8. 一页总览

```text
请求方等待结果       -> 成对请求/响应
服务端主动告知       -> 1701 单向通知
发送方跨断线可靠     -> SQLite outbox + client_message_id 幂等
接收方跨断线可靠     -> MySQL 权威表 + user_events + event_seq
实时通知丢失         -> 1405/1406 增量同步
业务投影与游标一致   -> 同一个 SQLite 事务
资源上传恢复         -> 磁盘 .part 长度 + 1507
好友业务存储         -> friend_requests/friendships，不进 chat_messages
```
