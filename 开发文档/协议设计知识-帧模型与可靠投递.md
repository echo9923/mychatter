# 协议设计知识：消息帧模型与可靠投递

> 本文回答一组环环相扣的问题：消息 ID 是怎么编号的、回包和通知有什么本质区别、TCP 已经可靠了为什么还要应用层 ACK、通知不确认会不会丢消息。
> 号码速查见《消息ID速查表.md》，数值唯一来源 `proto/protocol_ids.h`。本文讲的是号码背后的设计逻辑。

---

## 1. 消息 ID 体系（48 个）

### 编号规则三句话

1. **百位 = 功能域**：10 账户 / 11 连接保活 / 12 好友 / 13 聊天 / 14 历史同步 / 15 资源 / 16 头像；17xx 预留群聊、18xx 预留音视频
2. **奇数 = 发起方**（请求或服务端推送通知），**偶数 = 回包**
3. **同一动作连号**：REQ → RSP → NOTIFY（带推送的动作占 3 个号，下一动作跳到下一个奇数，全表仅 1206/1304/1506 为空号）

数量分布口诀：**账户 5、连接 5、好友 8、聊天 5、同步 8、资源 13、头像 4，共 48 个**。

### 帧的三种角色

| 角色 | 奇偶 | 谁发 | 语义 |
|----|----|----|----|
| REQ 请求 | 奇 | **客户端** | 提问：发起一个动作，等待答案才能继续 |
| RSP 回包 | 偶 | **服务端** | 答案：对某个先前请求的响应 |
| NOTIFY 通知 | 奇 | **服务端** | 告知：单向事件转告，不等待任何答案 |

两条结构性事实：

- **客户端永远不发偶数帧**——因为回包的定义是"对请求的响应"，而所有指向服务端的请求都由服务端应答。
- **通知没有配对回包**，且这不是遗漏，是设计（见 §2）。ChatServer 的 `ReqToRspId` 对通知号返回 0，停机兜底时对通知直接关连接而非回错误帧。

容易混淆的一点：**1407 投递 ACK 不是一种特殊帧类型，它就是一个普通的 REQ**（客户端主动发出、有自己的回包 1408）。ACK 不是 REQ/RSP/NOTIFY 之外的第四种帧。

## 2. 回包的本质：不是"收到消息的义务"，是"提问方在等答案"

### 请求 vs 通知：发起方有没有"待决状态"

- **请求（REQ）**：发起方发出后状态机卡住，必须有答案才能走下一步。例：A 发 1301 后要等 message_id（关联本地消息）、等成败判定（删 outbox 条目还是退避重发）、等 chat_time（上屏）。没有 1302，A 什么都做不了——回包是 A 工作流中必须存在的输入。
- **通知（NOTIFY）**：发起方发完后状态机已经走完，没有任何事情在等对方。服务端发 1303 之前工作已全部完成（消息落库、sync 行写入、给 A 的 1302 已回），推送只是"顺手告诉在线的 B 一声"的加速优化。B 的应答不解锁服务端的任何下一步，所以这个应答没有结构性位置。

**反向验证**：如果某次通信真的需要"发送方等接收方确认"，它就该建模为请求而非通知——回包结构自动获得。本项目唯一的确认场景（1407）方向就是反过来的：因为"B 落库了没有"只有 B 自己知道（落库发生在 B 的 SQLite 里），知情方决定谁是请求方。

### 为什么不为每个通知配一个 ACK 号

| 若配对 ACK 会怎样 | 实际设计 |
|----|----|
| 1205/1209/1105 的 ACK 成永不使用的死号 | 这三个通知不需要确认（申请/好友列表有落库+拉取兜底；踢下线后连接都关了） |
| 逐条确认，高频聊天帧数翻倍 | 1407 的 payload 是 message_ids **数组**，N 条消息聚合一帧 |
| ACK 语义退化为"帧到达"（收到即自动回） | 实际语义是"已持久化"——落库事务成功后才生成 ACK 条目 |
| 同步链路（1405 补拉）的消息没有通知可回，还得再造一套 ACK | 一个 1407 统一覆盖"消息从哪条路来的"（实时推送/补拉/同步） |

业界同构：XMPP 已送达回执是独立消息类型、MQTT 的 PUBACK 是独立帧、AMQP 的 basic.ack 独立——业务 ACK 独立于消息帧是 IM 领域通行做法，因为**确认是传输问题，不该和业务消息类型耦合**。

## 3. TCP 可靠性的边界（理解一切上层机制的前提）

### TCP 承诺什么、不承诺什么

常见误解是"TCP 保证消息送达"。准确表述是：**TCP 保证"连接存活期间，字节流不丢、不乱、不重地进入对方内核缓冲区"；连接一旦死亡，承诺终止，且不提供损失清单**。

一条消息从服务端 write() 到"安全"的实际路径：

```
服务端 write() 成功   ← 只说明进了服务端自己的内核发送缓冲区
  → 网络
  → B 的内核接收缓冲区  ← TCP 的保证到这里为止
  → B 的应用 recv 读出  ← 从这里起 TCP 不再提供任何保证
  → 凑齐完整帧（2B id + 2B len + body，可能跨多个 TCP 段）
  → 解析 JSON、校验
  → 写入 SQLite        ← 业务真正关心的终点
```

### 连接死亡的三条结局

服务端 write() 返回后，TCP 数据段面临的可能：

- **结局 A（在途丢失）**：数据段丢失或 ACK 回不去 → TCP 指数退避重传（1s→2s→4s…）→ **重传有上限**（默认约 15 次/十几分钟）→ TCP 放弃并杀掉连接。服务端应用层全程无感，最快到下次写这条连接或心跳超时才发现连接已死。
- **结局 B（到达未读）**：数据进了 B 的内核缓冲区，甚至已被 TCP ACK，但 B 的应用还没读——手机断电/App 被杀，内核缓冲区随进程销毁，数据蒸发，服务端不知情。
- **结局 C**：正常送达并被应用处理——只有这条是直觉里的"TCP 保证"。

### 为什么不能无限重传等对端回来

两个硬约束：对端可能永远不回来（无限重传 = 无限占用服务端资源）；且 NAT 映射几分钟就过期、基站路径改变，旧连接在网络上已经"迷路"，重传到天荒地老也到不了。所以 IM 客户端都有断线重连。

**最关键的事实：重连是一条全新的 TCP 连接**——新的三次握手、新的序列号空间、全新的缓冲区。**旧连接上未送达的数据不会、也不可能迁移到新连接**。从新连接的视角看，那条没送达的帧像从未存在过。

```
TCP 的可靠性承诺边界 = 一条连接的生命周期
    连接活着   → 字节流不丢不乱不重（TCP 全包）
    连接死了   → 在途数据随连接蒸发，无人报告损失清单
    重新连接   → 白纸一张，从零开始
```

**跨连接的可靠性 TCP 天生不负责，只能由应用层建立。**

## 4. 为什么需要应用层 ACK：终点问题

TCP 可靠的终点是"对方内核缓冲区"，业务需要的终点是"对方应用已持久化"。这个差距不是 TCP 的缺陷，而是它管的层级不同——**可靠性是逐层叠加的，每一层的 ACK 只对自己的那一层负责，确认的终点必须由"完成处理的那一层"亲自发出**：

- 链路层有校验重传 → 但你不信任"到达对方网卡"，所以有了 TCP（终点推进到对方内核）
- TCP 有 ACK 重传 → 但你不信任"到达对方内核"，所以有了应用层 ACK（终点推进到对方数据库）

"送到了内核"和"处理了"之间的崩溃窗口（收到帧、未落库、进程死亡）里，到达式确认（TCP ACK）已经发出，服务端却以为送达——这就是为什么本项目的 ACK 必须由**业务层在落库事务成功后**生成，而不是传输层自动回。

## 5. 本项目的可靠投递闭环

### 方向一：客户端 A → 服务端（请求 + 回包 + 幂等重试）

`DealChatTextMsg` 的严格顺序：

```
收到 1301 → 校验 → MySQL 事务（chat_message 行 + 双方 user_message_sync 行）
  ├─ 提交成功 → 回 1302 {error:0, message_id, chat_time} → 再尝试推送 1303 给 B
  └─ 提交失败 → 回 1302 {error:2014}（transient，客户端重传）
```

核心不变式：**1302 的 error=0 严格等价于"已持久化且只持久化了一次"**（回包在事务提交之后才发，顺序不可颠倒——避免 live 推送先于 sender ACK）。

"收到请求必有回包"的完整保障：

- 每个请求号都有配对回包（`ReqToRspId` 12 对映射）；
- 校验失败/落库失败/幂等冲突都有对应错误码回包；
- **停机兜底**：优雅停机、队列拒绝时，服务端按 `ReqToRspId` 直接硬回 `SERVER_BUSY(2016)`；连接死到连错误帧都写不出时才放弃（此时客户端断线重连+重发接管）。

**两个"收不到回包"的例外窗口，由幂等重试闭环**：

1. 落库成功后、回包发出前服务端崩溃 → 客户端超时重发同一 1301（相同 unique_id）→ 服务端幂等去重，返回**原 message_id**，不产生第二行；
2. 回包发出但连接恰好断掉 → 处理方式同上。

客户端规则：**只认回包，永不把"发出去了"当"发送成功"**——outbox 条目要等 error=0 的回包才删除。这就是**至少一次投递 + 幂等去重**模型（TCP 用同样的模型保障内核到内核，这套机制保障应用到应用）。

### 方向二：服务端 → B（通知加速 + 游标兜底）

**防丢失的从来不是通知，而是"服务端权威存储 + B 的同步游标"。通知只是加速器，丢了通知的后果是消息晚到，不是消息没了。**

机制：服务端落库时同时写 `user_message_sync` 流表（B 的一行，带全局递增 `sync_seq`）。B 本地 SQLite 的 `sync_state` 表记着游标 `last_sync_seq`。规则两条：

1. B 每落库一条消息（来源无论是实时通知 1303 还是同步回包 1406），**落库和推进游标在同一个 SQLite 事务里**——不存在"消息进了库但游标没跟上"的窗口；
2. B 每次登录/重连成功，发 1405 `{after_sync_seq: 游标}`，服务端返回流表中**大于游标的所有行**按序补齐。

隧道场景时间线：

```
T0  A 发消息 → 服务端事务提交（B 的 sync 行 seq=500）→ 回 A 成功
T1  服务端推 1303 给 B —— B 的手机进隧道，连接断，通知没送达
T2  B 本地游标停在 499（T1 什么都没发生，游标纹丝不动）
T3  B 出隧道重连（新 TCP 连接）→ 发 1405 {after_sync_seq: 499}
    → 服务端返回 seq=500 → B 落库、游标=500 → 顺带发 1407 确认
```

通知丢得再彻底，**游标记得自己欠着账**。重连后同步到一半又断也没事（断点续传）；服务端多推已有消息则按 message_id 幂等去重。

### 1407/1408 投递 ACK 的精确定位

- B 收到 1303/1505 → **同一 SQLite 事务**写 messages 表 + 生成 DELIVERY_ACK 的 outbox 条目（保证"已发出 ACK" ⇒ "必已落库"）；
- OutboxDispatcher 把多条 message_ids **聚合成一帧**发 1407 → 服务端标记 `delivery_status=1`（送达台账）→ 回 1408 → B 才删除本地 ACK 条目；1408 丢失则重发 1407，服务端幂等（`lost-ack` 场景专门验证）。

注意：**1407 不是防丢主力**。就算某条消息的 1407 永远没送达服务端，B 手里有消息、游标也在，后续一切照旧——丢 ACK 只脏了服务端台账，不丢消息。防丢主力是落库（权威副本）+ 游标（追赶进度）。

### 两种确认的分工

| | ACK（1407/1408） | 游标（sync_seq） |
|----|----|----|
| 回答的问题 | "这一条到了吗" | "我追到哪了" |
| 粒度 | 逐条（可聚合） | 进度 |
| 丢失后果 | 台账不准（无害） | 无（游标与落库同事务，不可能超前） |
| 性质 | 需要重试保护 | 天然幂等、断点续传 |

**Git 类比**：服务端是权威仓库（提交历史永不丢），B 是 clone 方，`last_sync_seq` 就是本地 `HEAD`。1303 相当于 webhook"有新提交了，pull 一下"——webhook 丢了没关系，下次 pull 从 HEAD 增量追上，一个提交都不会少。

## 6. 已知设计取舍：好友申请的实时性缺口

### 为什么申请通知（1205/1209/1105）不需要确认

- 1205 好友申请通知：申请已落 MySQL apply 表，登录回包捎带 `apply_list` 兜底；
- 1209 认证结果通知：好友列表（登录回包捎带 `friend_list`）兜底；
- 1105 踢下线通知：连接即将关闭，确认无处安放。

**可靠 ≠ 实时**：这些通知丢了数据不丢，只是晚看到。好友申请低频、非对话性（晚几分钟无顺序性伤害），不值得为其建 sync 流表。

### 但存在真实的实时性缺口（已查代码确认）

`tcpmgr.cpp` 登录回包（1102）处理中的分支：

```cpp
if (_reconnecting) {
    ...
    emit sig_chat_login_ready();   // 重连：只恢复 outbox 派发与聊天增量同步
    return;                        // ← 不解析 apply_list / friend_list
}
```

- **首次登录**：服务端在 1102 里捎带完整 `apply_list`（主通道之一）；
- **断线重连**：只补聊天消息（1405 增量同步），**不重新拉申请列表**；
- **"新的朋友"页面**（`applyfriendpage.cpp`）：从 `UserMgr` 内存缓存读，不触发网络请求。

叠加结果：**B 在线期间 1205 推送失败（连接闪断/跨服 gRPC 失败/停机——好友链路无重试），只能等下次冷启动完整登录才能看到该申请**。聊天消息有 sync 游标做到"重连必补"，申请没有。

### 改进选项（按代价从小到大）

1. **重连回包捎带**：服务端在重连登录回包里也带 `apply_list`，客户端去掉重连分支的提前 return——无新协议号；
2. **独立拉取号**：在 12xx 段加一对（如 1211/1212），打开"新的朋友"页或重连时拉取——目前协议里没有"拉申请列表"的请求号；
3. **纳入 sync 流**：像聊天消息一样进 `user_message_sync`，重连自动补齐——最彻底但要动表结构与迁移，对低频业务通常过度。

## 7. 一页总览

```
帧分类：  奇数=发起（客户端发 REQ / 服务端发 NOTIFY）  偶数=回包（全由服务端发）
回包本质： 提问方在等答案；通知是告知，没有配对答案
TCP 边界： 保证到对方内核缓冲区为止；连接死亡无损失清单；重连=新连接，在途数据不迁移
A→服务端： 先落库后回包（error=0 ⇔ 已持久化）；崩溃窗口靠 unique_id 幂等重试收口
服务端→B： 落库+sync 流表是保管员（权威副本），1303 通知是加速器，游标是追赶进度
投递 ACK： 1407 聚合确认"已落库"，1408 保护确认本身；是送达台账，不是防丢主力
取舍记录： 好友申请通知不做确认（低频+落库兜底），已知缺口=在线期推送失败要等冷启动登录
```
