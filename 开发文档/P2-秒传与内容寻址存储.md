# P2：发送者范围秒传与内容寻址存储

本文是 P2 阶段的实现说明与部署步骤。协议数值唯一来源仍是 `proto/protocol_ids.h`，完整表格见 `开发文档/消息ID速查表.md`。

## 1. 磁盘布局

| 路径（`<CAS 根>` 见下） | 语义 |
|---|---|
| `<CAS 根>/uploading/<message_id>.part` | 进行中上传（不再按发送者分目录）。活跃上传每写一片就刷新 mtime |
| `<CAS 根>/blobs/<sha256 前 2 位>/<sha256>` | 已发布内容的唯一物理副本（内容寻址） |
| `<CAS 根>/<sender_uid>/<message_id>` | 旧布局，P2 后不再写入；不迁移、不自动删除，由部署流程清空 |
| `<CAS 根>` | 缺省 `<bin>/resource`，可配置（见下） |

根路径可配置：优先 `[Storage] ResourceRoot`，其次 `[Output] ResourceRoot`，缺省 `<Output.Path>/resource`。绝对路径原样使用，相对路径相对进程工作目录解析。`ConfigMgr::InitPath` 用 `llfc::EnsureDirectoryDurable` **耐久创建** CAS 根与 `uploading/`、`blobs/` 两个子目录（目录条目落盘），**创建失败直接致命退出**，不会出现"打印了错误却继续运行"。**一个 CAS 根目录只能由一个 ResourceServer 进程独占**（互斥是进程内 `std::mutex`，不跨进程）。路径推导只有一处真值：`llfc::ResourceUploadingPartPath` / `llfc::ResourceBlobPath`（`ResourceUploadFile.h`），FileWorker、1507 判定与清理任务共用。

**blob 可信性与目录耐久性**：blob 只会在"整文件 SHA-256 校验通过 → `FlushFileToDisk` → `DurableRename(replace=false)` 持久化重命名"之后出现；完成点先用 `FlushFileToDisk` 持久化文件，再由 `DurableRename` 在 POSIX 下对目标父目录调用 `llfc::EnsureDirectoryDurable` 做目录项耐久化（Windows 依赖 `MOVEFILE_WRITE_THROUGH`）；该 helper **每次调用都自底向上 fsync 整条祖先条目链直到文件系统根**，不依赖"本次新建了哪些层级"——`blobs` 由启动期建好、其条目在 CAS 根里可能尚未落盘，重试时目录已存在也不会出现在"新建集合"里，两种情况都必须重新持久化（代价是若干次目录 fsync，与路径深度成正比，位于 CAS/GC 临界区内，**吞吐影响未测量**）。因此不新建 `resource_blobs` 表。但**"同名文件存在"不等于"内容可信"**（截断/位翻转/异物占位都可能留下同名文件），去重命中时必须显式复核，见下节。

## 2. 上传与去重

- 上传完成时把 `.part` 以 **no-replace** 方式改名到 blob 路径：
  - 目标不存在 → 正常发布；不会创建前缀目录以外的残留（`uploading/*.part` 由改名消耗，失败时由清理任务/部署兜底）；
  - 目标已存在（POSIX `link` 返回 `EEXIST`，Windows `MoveFileExW` 报 `ERROR_ALREADY_EXISTS`/`ERROR_FILE_EXISTS`）→ **去重命中**，但"存在"不等于"可信"，必须复核后才复用：目标精确长度 == DB `file_size_bytes`、整文件 SHA-256 == `message_resources.sha256`、且 `FlushFileToDisk` 成功；三项全过才删除本地 `.part` 并照常走发布事务；
  - 复核不通过或无法取证（长度不符/哈希不符/flush 失败）→ **保留已校验的 `.part` 与已存在的公开 blob 原样不动**，回**可重试**错误 `2104`（`FileWritePermissionFailed`，客户端按退避重试，不进永久失败集）。绝不覆盖已有 blob（它可能正被其他已发布消息引用，覆盖即静默损坏已发布内容），也绝不把不可信内容复制回 `.part`——此类"同名不同内容"属运维异常，需人工/部署处置；
  - 其他失败（rename 结果不确定）按"结果不确定"处理：**绝不删除已公开 blob**，仅尝试用可信副本恢复 `.part`（不可行则按磁盘实际长度回退到分片边界）后回可重试错误 `2104`。
- `.part` → blob 安装与 DB 发布事务提交在同一个 `llfc::BlobInstallGcMutex()` 临界区内，清理任务持同一把锁做"孤儿判定查询 + unlink"，因此 GC 不会删掉已安装但尚未提交的 blob。**秒传路径（1513）也持同一把锁**：blob 区段读取 + 常量时间比对 + 发布事务在临界区内，成功回包与 `UserMessageNotifier` 投递放到锁外（失败回包在锁内是安全的：`CSession::Send` 只把帧 `post` 到 socket IO 线程，不阻塞、不重入）。
- 下载路径由 `message_resources.sha256` 推出，`1509/1511` 只读 blob。

## 3. 秒传判定与持有性证明（1513/1514）

1507 处理时（FileWorker 线程，消息仍为 Pending、`server_offset == 0`）同时满足以下三点才下发一次性挑战：

1. 该发送者有一条 Published 的消息，`sha256` 与 `file_size_bytes` 都相同（`MysqlDao::SenderHasPublishedContent`，联表 `chat_messages` 过滤 `sender_user_id` 与 `status=1`）；
2. 对应 blob 文件存在；
3. 文件大小与 DB 真值一致。

只看发送者本人历史，因此不会向其他用户泄露"有人传过相同内容"。判定查询返回三态（`Yes/No/Transient`）：`Transient`（DB 瞬时故障）回 `2002` 让客户端重试，**绝不把"查不到"静默当作"无历史"**。

挑战参数：`nonce` = 16 字节 `RAND_bytes` 安全随机（下发 32 位 hex），`offset` = 随机区段起点，`length = min(size, 64KiB)`。挑战存放在该消息的 `UploadSession` 内，绑定下发时那条 `CSession`，一次性使用，TTL 120 秒；会话逐出或服务重启即失效。

客户端在 File 线程只读源文件计算 `proof = hex(SHA256(nonce_raw16 ‖ file[offset, offset+length)))` 并回 1513（拼的是**原始 nonce 字节**，不是 hex 字符串）。服务端从 blob 读取同一区段，用 `CRYPTO_memcmp`（`llfc::ConstantTimeEquals`）常量时间比对：

- 比对通过 → 与普通上传**共用同一个发布事务**（`CompleteResourceUpload`，幂等）与 `UserMessageNotifier`，回 1514（`status=Published` + `event_seq`）；
- 证明不符（64 hex 但比对不等）→ 回 `2118`，并在本会话内抑制后续挑战下发（服务端闸门）；
- 挑战不存在/超 TTL 120s/绑定连接不符（本会话仍活跃但不属于本次请求）→ 回 `2118`，且**不消费**挑战，客户端重发 1507 重新同步；
- 1507 判定时 blob 缺失或长度不符则不下发挑战。若挑战下发后无法打开 blob，1513 返回 `2118` 并抑制后续挑战；若指定区段读取不足，返回 `FileReadFailed`；区段证明不符则返回 `2118`。客户端按相应错误分类恢复。

**消费顺序与格式校验（防伪造者打出 DoS 与零长度摘要放行）**：

1. 先校验 `message_id` 属于本人（`req_uid != sender_user_id`、uid=0 或无资源扩展 → `ResourceForbidden`(2115)，**不是** 2118）、消息仍为 Pending（Published 走下面的幂等重放，Failed/其他终态 → `ResourceStateInvalid`(2116)）；DB 查询瞬时故障（Transient）→ 2002，**不作废挑战**，客户端可原样重试；NotFound → `MsgIdErr`(2111) 并逐出本消息会话；
2. 挑战校验：不存在/已过期（TTL 120s）/绑定的 `CSession` 不是本次连接（`weak_ptr` 对比）→ 回 `2118`，**不消费**该挑战（非法连接不能把合法客户端的挑战烧掉）；只有确认是下发时那条连接的合法持有者，才消费挑战（一次性）；
3. 消费后再做 proof 格式校验：`proof` 必须是 **64 位 hex**（先判长度再 `ConstantTimeEquals`，避免零长度摘要"相等"放行），不符 → 回 `2118` 并置本会话 `challenge_suppressed`（只有合法持有者才允许产生这种副作用）；
4. 通过后进 `BlobInstallGcMutex` 临界区读 blob 区段比对并发布。

`Published` 的 1513 重放（消息已就绪但客户端丢包重试）：直接回原 **`event_seq`**（读 `user_events`，不新增事件、不发 1701），并清掉本消息残留的 `.part`。挑战活跃期间普通 1505 写入会**清空本会话的挑战状态**，因此客户端改用普通上传后不会被迟到的 1513 复挑战拖回。

客户端侧：收到 `mode:"proof"` 在 File 线程算证明发 1513（沿用 1507/1509 的查询超时语义）；收到 2118 后本传输内禁用 proof（`proof_disabled`）并回退普通上传，与服务端 `challenge_suppressed` 构成双端闭环，**不会出现无限挑战循环**；1514 Published 与普通上传完成走同一条完成路径（销账 + 异步归档）。

客户端引擎的 proof 状态机要点：

- `proof_pending` 单飞标记：1513 未回包前丢弃同消息的乱序 1508（避免把证明阶段当成新的查询轮次）、不对 1514 之外的响应复位控制定时器（`HandleInstantProofRsp` 在标记为假时整帧丢弃，绝不触碰当前 1507 的定时器）；`ResumeTransfer`/`ResyncUpload`（含 `BeginQuery`）/`OnConnectionDown` 清位隔离旧阶段；
- **暂停只抑制新请求，不丢弃在途证明**：`PauseTransfer` 保留 `proof_pending` 与 `query_sent_ms`（`BeginQuery` 在 `user_paused` 下不发帧），因此已在途、服务端确实已发布的严格校验 1514 仍能在暂停期间收敛（显示为 COMPLETED）；`HandleTimeout` 在 `user_paused` 时只清计时器、不判连接死亡、不请求重连（该传输恢复时统一经 Resume → 1507 重同步拿新挑战）；
- 1514 只在 `proof_pending` 为真时被采纳，且严格校验 `status == Published`、`server_offset == total_bytes`、`event_seq > 0`；**任一不符（含 `error==0` 但 `status` 非 Published 的"无效成功包"）都走 `ERR_JSON` 坏回包路径**（累计 `json_error_count` → 退避后 1507 重同步 → 达上限转永久失败），绝不当成正常状态切换去无界立即重同步；
- 解码层同步收紧：`error==0` 的 1514 必须带 `status`、`server_offset` 且 `event_seq` 为十进制字符串且 `>0`，缺失/JSON 数字/0 一律 `ok=false`（engine 按坏回包计数），因此"缺失/wrongtype/mismatch"全部有界；
- `json_error_count` **只在普通上传分支清零**：`SendInstantProof` 内部**不再清零**（合法挑战只是"新一次证明尝试"，清零会让非法的 `status`/`offset`/`event_seq` 1514 在 0↔1 之间震荡、永远到不了 `json_error_limit`；坏挑战本身照旧累计）；`publish_retry_count` 仍在 `SendInstantProof` 内按原语义归零；`HandleProgressRsp` 的 proof 分支调用后**立即 return**，不得再触碰已被同步回调释放的传输对象；1513 发送前握住运行时表里同一实例的 `shared_ptr`、发送后仅当"仍是同一实例且仍 `proof_pending`"时才 `EmitUpdate`（`_send` 可同步派发 Published 1514 → 监听者 `Reset`/同 `message_id` 重启）；畸形 proof 挑战会一直累积直到终态（不会被反复清零导致永不失败）；
- 终态时先拷贝 `direction` 再 `emit sig_transfer_finished`（同步 listener 可能重建同 `message_id` 传输，读已释放对象是 UAF）。

## 4. 清理（每轮启动 + 每小时）

- `uploading/*.part`：mtime 超 7 天直接回收。
- `blobs/<xx>/<sha256>`：mtime 超 7 天**且**查询 `BlobHasPublishedReference(sha256)` 返回 `No` 才回收；`Yes`/`Transient`（查库失败）一律保留待下轮。
- **孤儿判定只按 sha256 身份，不附加磁盘 `stat` 大小**：blob 的内容身份就是它的文件名（完整 SHA-256），用"磁盘实际长度 == DB 长度"做附加条件会把"stat 失败/被并发改写"的**现有引用**误判成孤儿并删除。DB 查询是 typed 三态，**"查库失败"绝不当作"无引用"**。
- 孤儿判定查询与 unlink 持 `BlobInstallGcMutex`；Windows 下文件被占用导致删除失败时保留，留到下一轮重试。
- 清理只扫新 CAS 布局（`uploading/*.part` 与 `blobs/<64 位 hex>`），其他残留一律不动，交部署清空。
- 旧 `bin/resource/<sender_uid>/` 布局一律不动（见部署步骤）。

## 6. 部署步骤（需人工执行，本文档只说明不代跑）

1. 停止全部 GateServer、StatusServer、ChatServer、ResourceServer 实例，确保全量重建期间没有请求或旧会话继续访问数据库。**同一 CAS 根目录只允许一个 ResourceServer 进程**——互斥锁是进程内的，多开会让"安装 vs GC"失去保护。
2. 确认配置：`server/ResourceServer/config/config.ini` 的 `[Storage] ResourceRoot`（缺省 `bin/resource`）。若与 `[Output] Path` 指向同一目录，多个进程/多个实例共享同一 CAS 根目录同样违反上一条。
3. 执行 DDL：**跑 `sql备份/20260830_database_rebuild.sql` 全量重建 7 表**（`users/friendships/private_chats/chat_messages/message_resources/friend_requests/user_events`），确认 `message_resources` 带 `(sha256, file_size_bytes)` 索引。**旧布局的库不允许"只 ALTER 补索引 + 清磁盘文件"**：那样 `chat_messages` 会残留 `Published` 行而 blob 已被清空，1509/1511 会读到"有元数据无内容"的坏引用；第 5 节的 ALTER 片段仅适用于**已经是 CAS 布局**的库。
4. 按全量数据库重建流程废弃旧 Redis 用户会话/路由和客户端本地缓存，避免用户 ID、消息 ID 重用旧数据；清空 CAS 根目录（含旧 `<sender_uid>/<message_id>` 布局、遗留 `.part` 与旧 `blobs/`）——项目约定不迁移旧资源数据，清空后所有新上传按内容寻址落盘。
5. 同批发布服务端与客户端（1513/1514 与 `2118` 为新增协议/错误码，客户端 `global.h`、`im_common.h` 枚举壳只引用 `proto/protocol_ids.h`）。
6. 验证：同一文件第二次发给另一个好友即时完成且服务端无 1505 日志；换一个用户发相同内容仍走普通上传，磁盘上物理只有一份 blob。

> 以上步骤本轮**只写文档、未执行**（无服务启停、无 DDL、无磁盘删除）；`server/ResourceServer/config/config.ini` 新增的 `[Storage]` 段是本轮**源码改动**（已写入工作区），但**未部署**（未拷贝到运行目录、未启动验证）。
