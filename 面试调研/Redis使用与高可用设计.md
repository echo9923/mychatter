**其他事实（面试要能脱口而出）：**
- 所有服务用的是**同一个单节点 Redis**（配置里只有一组 Host/Port/Passwd），没有从库、没有哨兵、没有 Cluster；连接池大小各服务不同：**ChatServer 10 条**（`ChatServer/src/RedisMgr.cpp:10`）、GateServer/StatusServer 各 5 条，后台线程每 60s 对所有连接 PING 一次，失败会 `reconnect()` 补连接。
- 分布式锁：`SET lockName uuid NX EX 10`，释放用 Lua `get == uuid then del`（`day32`、`DistLock.cpp`）；没有 watchdog 续期，业务事项必须 10s 内完成。
- `lockcount` 全局锁当初用来保护 `logincount` 读改写，`day35` 已优化成「心跳定时器统一统计一次连接数后直接 HSet」，把高频锁去掉了——这是「锁粒度与频率」的一个好故事。
- **已核实 bug**：工作区 `server/StatusServer/src/StatusServiceImpl.cpp:102-106` 的 `Login` 是 `bool success = Get(...); if (success) { error = UidInvalid; }`——`RedisMgr::Get` 命中 key 返回 `true`，所以这里**确实写反了**（token 存在反而报 UidInvalid），应改成 `if (!success)`；面试如果被现场看代码，这是个雷。
- Redis 在项目里扮演的是**缓存 + 临时状态 + 协调**，权威数据（用户、好友、消息）都在 MySQL——这句话是华为问28 的关键，也是问43 降级设计的基础。

## 2. 逐题调研

### 2.1 OPPO 二面·问8：Redis 依赖重，可用性怎么保证？

**面试官原话（转写）**
> 问8：然后我看你这里对 Redis 的依赖还挺重的，就有很大量的这个信息都存储在 Redis 里面。嗯，是的，那你这个 Redis 的可用性怎么保证？

**你当时的回答（压缩）**
> 因为目前设计的比较简陋，正常情况下应该要做到一些主从复制这些内容；现在就是单纯一个单节点。

**状态：⚠️ 半对——诚实承认是好品质，但没有展示「我知道单点挂了的后果 + 我会怎么改」。**

**考点分析**
- 面试官在测两件事：①你知不知道 Redis 在你的系统里是**强依赖**（登录、互斥、调度都靠它）；②你有没有完整的「高可用 + 降级」思路。
- 只说「应该做主从复制」太薄：主从解决的是数据副本，不解决自动切换（要哨兵/Cluster）；而且客户端要能发现新主。
- 还要能报出「Redis 挂掉后哪些功能受影响」，这比背方案更打动人。

**可直接背的参考回答**
> 我承认现在的 Redis 是单节点，这是明确的可用性短板，也是我复盘时最想改的地方。先说影响面：Redis 挂掉会有四类功能受损——①登录分配（StatusServer 要读 token 和节点注册表）；②ChatServer 登录校验 token、写在线位置；③多端互斥/踢人（`uip_`/`usession_`）；④用户资料缓存（`ubaseinfo_`，这块有 MySQL 兜底，影响最小）。所以它不是一个「可选缓存」，而是接近强依赖，必须做高可用和降级两条线。
> 高可用上我会分阶段：**近期**做主从复制 + 哨兵（1 主 2 从 + 3 哨兵），哨兵负责自动选主和通知客户端，客户端连接池支持 sentinel 地址发现，切换期间写请求失败要重试；**关键路径强制读主**，比如 token 写入后马上校验这种场景，不能读从库；**远期**如果数据量和 QPS 上来了，再考虑 Redis Cluster 做分片。降级上：token 做成自包含（JWT/HMAC），ChatServer 本地验签，Redis 只保留「会话归属/在线状态」这类可降级数据；同时网关做限流，MySQL 做兜底但必须配合熔断，防止把 MySQL 打挂。
> 另外我会补监控：主从复制延迟、哨兵状态、连接池失败率、Redis P99，做切换演练。高可用不是配了哨兵就完事，关键是**演练过的切换**。

**技术要点拆解**
- 单点风险：进程崩溃/机器断电（宕机）、内存满触发 eviction（数据被淘汰）、慢查询阻塞（单线程）、主从/持久化配置缺失（重启丢数据）。本项目还没有 RDB/AOF 配置的痕迹（`待核实` 部署时是否开启）。
- 高可用演进路径：

| 阶段 | 方案 | 解决的问题 | 局限 |
| --- | --- | --- | --- |
| 0 | 单节点 | 简单 | 单点故障、无副本 |
| 1 | 主从复制 | 数据副本、读扩展 | 主挂需人工切换 |
| 2 | 主从 + 哨兵 | 自动选主/切换 | 切换窗口秒级；写仍单主 |
| 3 | Cluster | 分片 + 副本 + 自动 failover | 多 key 受限、运维复杂、客户端要求高 |

- 客户端配套：连接池要支持哨兵（hiredis 不直接支持，需自己实现或换 redis-plus-plus）；设置 connect/read/write 超时；失败重试 + 熔断，避免线程全都堵在等待 Redis 上。
- 「哪些数据必须读主」清单：token 写后立即校验、分布式锁、`uip_`/`usession_` 的读改写；可读从的：`ubaseinfo_` 这类缓存（能容忍秒级旧值）。

**当前项目实现对照**
- 单节点配置：`ChatServer/config/chatserver1.ini`、`StatusServer/config/config.ini`、`GateServer/config/config.ini` 的 `[Redis]` 段各一组 Host/Port/Passwd。
- `RedisConPool`（`server/ChatServer/include/RedisMgr.h`）只连接一个地址，60s PING 保活 + 失败重连——这是「连接级」容错，不是「节点级」容错。
- 无主从/哨兵/Cluster 代码（`待核实` 是否有部署脚本另做过）。

**差距与改进建议**
1. 本地用 Docker 起 1 主 2 从 + 3 哨兵，把 `RedisMgr` 的连接方式改成 sentinel 发现（或临时用「配置多地址 + 故障切换」），哪怕只是实验，也能让面试回答从「应该做」变成「我做过」。
2. 明确降级开关：Redis 不可用时，登录走 JWT 本地校验、资料走 MySQL（限流版），互斥功能降级为「允许双端，恢复后踢一个」。
3. 补监控项与切换演练记录。

**追问预判**
- 主从复制是同步还是异步？会丢数据吗？——默认异步，主挂时可能丢最后一段未同步的写；可用 `WAIT`/`min-replicas-to-write` 提高保证，但会更慢。
- 哨兵怎么知道主挂了？——主观下线 + 询问其他哨兵达成 quorum 后的客观下线，细节见 2.2/2.15。
- 读写分离后读到的 token 是旧的怎么办？——关键路径强制读主；弱一致数据才读从。
- Redis 挂了，你的服务是「快速失败」还是「无限重试」？——网关限流 + 客户端熔断 + 快速失败，绝不能让业务线程池被超时等待占满。

### 2.2 OPPO 二面·问9：重新设计如何加固 Redis 集群可用性？

**面试官原话（转写）**
> 问9：那如果让你重新设计一下呢，你加固一下你这个 Redis 集群的可用性，你会怎么设计呢？

**你当时的回答（压缩）**
> 首先要做到主从复制，增加一批从节点做到读写分离，加上哨兵机制，保证主 Redis 宕机时可以自动切换到其他从节点上，保证 Redis 持续可用。

**状态：✅ 基本可以（方向完整），但缺少「客户端/切换窗口/读主策略」这些工程细节。**

**考点分析**
- 三个关键词你都说到了：主从复制、读写分离、哨兵。面试官接下来可能往深处挖：复制是全量还是增量？哨兵怎么选主？切换期间你的服务怎么办？读写分离哪些能读从？——这些就是本节的加分点。
- 注意「主从复制 + 读写分离」不是免费的：复制延迟会让「刚写的 token 读不到」，登录就会偶发失败。要能说出「关键读强制走主」。

**可直接背的参考回答**
> 我的设计会分三层：
> **第一层，数据副本：主从复制。** 主节点负责写，从节点实时复制主的数据。复制流程是 PSYNC：首次连接做全量同步——主节点 fork 出 RDB 快照发给从节点，同时把期间的写命令缓存起来，快照传完再补发增量；之后是增量同步，主节点把写命令持续传给从节点，并用 replid + offset 标记进度，短时间断线只要 offset 还在复制缓冲区里就继续增量，否则退化成全量。这里要清楚：默认**异步复制**，主挂了可能丢最后一点数据；对可靠性敏感可以配 `min-replicas-to-write`。
> **第二层，自动切换：哨兵。** 部署 3 个以上奇数哨兵，监控主从和彼此。主节点在 `down-after-milliseconds` 内无响应，先被单个哨兵判主观下线；够 quorum 的哨兵确认后变客观下线，再由多数派选出一个哨兵 leader 执行故障转移：从之前的从节点里选数据最新的提升为主，让其他从节点改指向新主，并通过发布订阅通知客户端新主地址。哨兵解决的是「主挂了自动切」，不止是「有副本」。
> **第三层，业务侧配合。** ①客户端要支持哨兵寻址（我们的 hiredis 封装要改造或换 redis-plus-plus）；②读写分离要有策略——**token、分布式锁、在线位置这些关键读写都走主**，只有用户资料这类缓存才允许读从，避免主从延迟导致的登录失败；③切换有秒级~十几秒的写不可用窗口，业务要重试 + 熔断 + 限流，不能无限等待；④切换后要验证新主数据完整性和旧主回归后的角色（旧主会自动变成从）。
> 如果未来单实例容量不够（内存/QPS 到瓶颈），再上 Redis Cluster：数据按 16384 个槽分片到多个主，每个主配从节点，slot 级自动故障转移；代价是事务/多 key 操作受限，客户端要 cluster-aware。现阶段数据量小，哨兵方案更划算。

**技术要点拆解**
- 全量 vs 增量（必会）：
  - 全量：`PSYNC ? -1` → `+FULLRESYNC <replid> <offset>`；master `BGSAVE` 生成 RDB + replication buffer；从节点清库、加载 RDB、再消费 buffer 增量；期间主节点继续服务。
  - 增量：`PSYNC <replid> <offset>` → 如果 offset 在 `repl_backlog`（默认 1MB 环形缓冲）内 → `+CONTINUE` 补差量；否则全量。backlog 太小、断线太久都会导致全量同步风暴。
  - 复制风暴优化：级联复制（从节点也带从）、适当调大 backlog、网络抖动时先重试再判死。
- 哨兵机制：SDOWN/ODOWN、quorum、leader 选举（epoch 投票，majority）、从节点选择（priority → offset → runid）；`+switch-master` 事件；哨兵本身也要 ≥3 台防脑裂。
- 读写分离一致性：复制延迟监控 `master_repl_offset - slave_repl_offset`；「写后读」场景强制读主；从库默认只读。
- 切换窗口：哨兵默认 `down-after` 30s（可调小到 5~10s），加选举+提升，整体秒级到十几秒；期间写失败要快速失败而不是挂起。

**当前项目实现对照**
- 无主从/哨兵实现；单节点配置见 2.1。`day09` 只有「搭建单机 Redis + 连接池」。
- `RedisConPool` 的重连只处理单地址连接断开，不处理「主节点角色变化」。

**差距与改进建议**
1. 做一次本地哨兵实验并写进项目笔记：docker-compose 起 1 主 2 从 3 哨兵，演示 `kill -9` 主节点后客户端自动切到新主；面试可直接讲实验过程和切换耗时。
2. 在代码里区分「强一致读」与「可缓存读」路径（哪怕先用注释标记），体现读写分离策略。
3. 补一个降级开关：Redis 完全不可用时业务怎么走（见 2.10/2.11）。

**追问预判**
- 主从全量同步时主节点 fork 会不会阻塞？——fork 本身 O(内存页表)，通常毫秒级，但内存大、写多时 RDB 生成的 COW 会带来内存膨胀压力；控制实例内存、低峰做、或调 `repl-diskless-sync`。
- 哨兵切换期间你的登录会怎样？——写失败快速失败/重试，读走本地缓存或 MySQL 兜底；需要演练。
- 为什么不用 Cluster 一步到位？——数据量小、事务/多 key 多、运维和客户端成本高；先哨兵，规模到了再 Cluster。
- 主从复制延迟怎么观测？——比较主从的复制 offset 或用 `INFO replication` 的 lag。

### 2.3 OPPO 二面·问10：整个集群挂了，怎么快速恢复数据？

**面试官原话（转写）**
> 问10：那我假如我们整个集群都挂掉了，你有什么办法能够快速恢复你这些数据？

**你当时的回答（压缩）**
> 快速恢复的话，平时保存的时候使用 AOF 和 RDB 快照的混合持久化，宕机之后迅速读取这些文件恢复数据。

**状态：✅ 可以（方向正确），但「怎么快」「怎么保证数据不缺」「集群拓扑怎么恢复」没展开。**

**考点分析**
- 这题实际考持久化机制 + 恢复流程 + 容灾意识。关键词：RDB/AOF/混合持久化、restart 加载顺序、备份与演练、集群恢复顺序。
- 还要说清「Redis 恢复的数据是你系统的哪一部分」——本项目 Redis 存的都是缓存和临时状态，丢了可以重建，但用户会感到「全部用户重新登录/在线状态丢失」，所以要快；而真正的权威数据在 MySQL，不能把 Redis 当唯一存储。

**可直接背的参考回答**
> 分两个层面。
> **持久化机制层面：** 我用 RDB + AOF 混合持久化。RDB 是周期性快照，文件紧凑、恢复快，但两次快照之间的数据会丢；AOF 是追加写命令，默认 `appendfsync everysec`，最多丢 1 秒数据，重放慢、文件大。混合持久化（Redis 4.0+，`aof-use-rdb-preamble yes`）在 AOF 重写时用 RDB 做前半段快照、后面追加增量命令，重启时先加载 RDB 再重放少量增量，**既快又几乎不丢**，这就是我选它的原因。
> **恢复与容灾层面：** 单机重启就是从磁盘加载；哨兵/集群场景由故障转移自动把从库提升，不需要等文件恢复。如果是「整个集群都挂了」——比如机房断电，恢复顺序是：先按拓扑恢复主节点再恢复从节点（或反过来让哨兵重新协商），确认 slot 覆盖/主从关系，再对外服务；Cluster 的节点拓扑保存在 `cluster-config-file`（nodes.conf）里，要保证文件和持久化文件都完好。同时要防两个坑：①持久化文件可能损坏，需要 `redis-check-aof --fix` / `redis-check-rdb` 修复；②AOF 太大导致恢复慢，所以要定期 `BGREWRITEAOF` 压缩。
> **兜底：** 定期把 RDB/AOF 备份到异地/对象存储，做恢复演练；更重要的是，我们系统的权威数据在 MySQL，Redis 挂掉后即使数据全丢，也能从 MySQL 和客户端重建——所以我把 Redis 定位成「可恢复的缓存和临时状态」，这才是不怕它挂的底气。

**技术要点拆解**
- RDB / AOF / 混合对比：

| 维度 | RDB | AOF | 混合（RDB preamble） |
| --- | --- | --- | --- |
| 数据安全 | 丢快照间隔数据 | everysec 丢≤1s；always 不丢但慢 | 接近 AOF，恢复快 |
| 恢复速度 | 快 | 慢（重放命令） | 快（先 RDB 再少量 AOF） |
| 文件大小 | 小 | 大（需重写压缩） | 中 |
| 性能影响 | fork + COW | 取决于 fsync 策略 | 同 AOF |
| 适用 | 容忍丢一段、要快恢复 | 要求少丢 | 生产推荐 |

- `appendfsync` 取舍：`always`（每命令 fsync，最强持久化、吞吐骤降）、`everysec`（默认，最多丢 1s）、`no`（交给 OS，可能丢更多）。
- 恢复流程：重启 → 加载 AOF（若开启优先 AOF）或 RDB → 数据就绪 → 哨兵/集群拓扑恢复 → 对外服务。
- 集群全挂恢复顺序：确保每台机器持久化文件完整 → 按最后已知拓扑启动 → `CLUSTER INFO` 检查槽覆盖与状态 → 必要时 `--cluster fix` 修复。
- 备份策略：定时全量 + 增量、异地多副本、定期演练（没有演练的备份不算备份）。

**当前项目实现对照**
- 项目代码层没有持久化配置（`待核实` 部署时是否在 redis.conf 开启 RDB/AOF）；`day09` 只讲了安装与连接。
- Redis 中的数据（token、uip、usession、ubaseinfo、验证码、连接数）**都可以从 MySQL/重新登录重建**：`ubaseinfo_` 来自 MySQL（`LogicSystem.cpp:750-772`），登录态本身就是临时的。这点要在面试里主动说，把「Redis 挂了」降级为「用户需要重新登录，数据不丢」。
- MySQL 死锁/恢复相关可参考 `day41-分布式死锁解决方案.md`（虽然是 MySQL，但体现你对数据可靠性的敏感度）。

**差距与改进建议**
1. 在本地实验：开启 `appendonly yes` + 混合持久化，写入数据后 `kill -9`，重启验证丢多少；记录恢复时间。面试可报实测数字。
2. 写一份「Redis 数据重建清单」：哪些 key 从 MySQL 重建、哪些可丢（在线状态）、哪些必须保留（锁不能残留太久）。
3. 把「权威数据不在 Redis」这句话固化成话术，避免面试官担心你把缓存当数据库。

**追问预判**
- AOF 和 RDB 同时存在，重启用哪个？——优先 AOF（数据更全），没有 AOF 才用 RDB；混合持久化时 AOF 文件本身就带 RDB 头。
- AOF everysec 为什么最多丢 1 秒？——fsync 由后台线程每秒做一次，崩溃时最多丢上一秒的写。
- fork 时内存为什么翻倍？——写时复制，父进程和子进程共享页，只有写操作的页才复制；写多时内存膨胀明显，要预留。
- 恢复后用户的在线状态怎么办？——全部视为离线，用户重连后重建；不需要恢复在线状态，这是临时数据。

### 2.4 百度二面·问37：Redis 集群中某个节点宕机，会发生什么？

**面试官原话（转写，来自问题清单）**
> 问37：如果 Redis 集群中某个节点宕机，会发生什么？

**你当时的回答**
> 面经只有问题清单、没有保留现场回答转写——按「未准备」处理，以下给完整参考回答。

**状态：❓ 未准备（建议按下面结构背熟）。**

**考点分析**
- 这题要**分情况**回答，面试官看的是你的条件分支能力：是主还是从？有没有副本？集群是否允许部分槽不可用？
- 标准回答框架：节点角色 → 其他节点如何感知 → 是否触发 failover → 对客户端的影响与数据丢失窗口。

**可直接背的参考回答**
> 要分情况。
> **如果挂的是从节点**：最轻。集群其他节点通过 gossip 检测到它失联，把它标记为 fail（`cluster-node-timeout` 内无响应）。它的主节点如果配置了副本迁移，可能重新分配一个从节点；对客户端基本无感，只是这个分片的读扩展少了一个副本。
> **如果挂的是主节点且有副本**：触发自动故障转移。它的从节点发现主失联，先在集群里发起投票；获得多数主节点同意的从节点被提升为新主，接管原来的 slot，并广播新的 slot 归属。客户端如果访问到了旧主，会收到 `MOVED` 重定向到新主（前提是客户端是 cluster-aware 的）。这个过程的检测窗口由 `cluster-node-timeout`（默认 15s）决定，期间这个分片的写会失败或超时；因为是异步复制，主挂前未同步到从的写会丢。
> **如果挂的是主节点且没有副本**：这是最糟的。它负责的那些 slot 直接失去归属，客户端访问会报 `CLUSTERDOWN` 或者连接被拒；如果 `cluster-require-full-coverage` 是默认的 `yes`，**整个集群会停止对外服务**，不只是这一个分片；必须人工介入：要么把它的槽重新分配给其他主节点（数据已丢），要么恢复这个节点；如果这个 slot 的数据还在 AOF/RDB 里可以尝试恢复。而且没有副本时没有投票对象，集群需要多数主节点在线才能维持状态，掉一个主可能直接影响可用性。
> 所以生产上：每个主至少配一个从；`cluster-require-full-coverage` 是否关闭要按业务取舍（关闭后坏槽只影响部分 key）；同时监控节点状态和 failover 事件。

**技术要点拆解**
- 节点失联判定：`cluster-node-timeout` 内 PING/PONG 无响应 → PFAIL（主观）→ 通过 gossip 被多数主节点确认 → FAIL（客观）。
- 故障转移资格：从节点只有在其主被标记 FAIL、且自身数据足够新（`cluster-replica-validity-factor` 限制断连时长）才能参选；选举需要**多数主节点**投票，epoch 递增防重复。
- 客户端感知：MOVED/ASK 重定向、slot 缓存刷新；非 cluster 客户端直接报错。
- `cluster-require-full-coverage yes`（默认）：任一槽无归属则全集群拒绝命令——考试常考的点。
- 数据丢失窗口：异步复制 + 主挂时未确认写；`WAIT` 可以缓解但牺牲性能。

**当前项目实现对照**
- 本项目**没有用 Cluster**，单节点（master）/计划哨兵（未来）。面试可以按「如果我的数据量涨到要分片，会这样处理」来答，并补一句「当前用哨兵就够了，因为数据分片不是当前瓶颈」。
- 相关：节点注册 lease 的「过期即摘除」和 Cluster 的故障检测是同类思路，可以在面试里类比。

**差距与改进建议**
1. 把「有副本 / 无副本 / 全槽覆盖」三种分支背成一分钟版本。
2. 记住三个关键词：`cluster-node-timeout`、PFAIL/FAIL、`cluster-require-full-coverage`。
3. 如果面试官追问「怎么避免丢数据」，回答 `WAIT` / `min-replicas-to-write` / 至少一个同步副本的取舍。

**追问预判**
- failover 期间客户端收到什么错误？——连接超时/`CLUSTERDOWN`，之后 cluster-aware 客户端会刷新 slot 并重试。
- 从节点数据比别的从旧能参选吗？——不能，会综合 offset 和 `cluster-replica-validity-factor` 判断。
- 主恢复回来后如何？——自动变成新主的从节点，重新同步数据。
- 有没有可能脑裂？——网络分区时少数派主停止写（需要多数主在线才能服务），分区恢复后旧主降级为从；但异步复制下仍可能丢未同步的写。

### 2.5 百度二面·问38：Cluster 的 slot 是什么？数据怎么分布？

**面试官原话（转写，来自问题清单）**
> 问38：Redis Cluster 的 slot 是什么？数据是怎么分布的？

**状态：❓ 未准备。**

**可直接背的参考回答**
> Redis Cluster 没有用一致性哈希，它把整个键空间划分成固定 **16384 个槽（slot）**。每个 key 归属哪个槽是 `CRC16(key) mod 16384` 算出来的，槽再分配给具体的 master 节点，每个 master 负责一部分槽，并可以带从节点做副本。客户端或代理通过集群拓扑知道 slot → 节点的映射，请求直接打到对应节点；打错了会收到 MOVED 重定向。
> 加法、扩容时不是重新哈希所有 key，而是以**槽为单位迁移**：比如从 3 主扩到 4 主，把一部分槽从旧节点迁移到新节点，用 `CLUSTER SETSLOT` 和 `MIGRATE` 完成，迁移过程中会同时用到 MOVED（槽已永久归属新节点）和 ASK（迁移中的临时重定向）两种应答。
> 为什么是 16384？主要考虑心跳和 gossip 的开销：集群节点间交换的位图标记「我负责哪些槽」，16384 位刚好 2KB；如果槽太多，心跳包会过大；同时 Redis 集群的实际规模设计在千节点以内，16384 足够均匀分布了。这是 Redis 作者在 GitHub 上解释过的取舍。
> 使用上的限制：多 key 操作（MGET、事务、Lua）要求 key 落在同一个槽，可以用 hash tag，比如 `{uid}:profile` 和 `{uid}:session` 只按 `uid` 计算槽，保证同一用户的数据在一起。

**技术要点拆解**
- 数据结构：每个节点用 16384 位 bitmap 记录自己负责的槽，节点间通过 cluster bus（端口 = 服务端口 +10000）gossip 交换状态。
- 客户端路由：`MOVED` = 槽永久迁移，客户端更新本地 slot 缓存；`ASK` = 迁移中的临时重定向，客户端本次去目标节点但**不更新缓存**，且要先发 `ASKING`。
- hash tag：`{}` 内的内容参与哈希；用于把相关 key 绑到同一槽（同一用户、同一会话）。
- resharding 过程：`CLUSTER SETSLOT <slot> MIGRATING/IMPORTING` + 逐个 key `MIGRATE`；期间源节点对已迁的 key 回 ASK/ MOVED。
- 与一致性哈希对比：Cluster 的槽是固定且显式管理的（槽归属表），一致性哈希的环是动态的（hash 环上的节点）；前者可以精确控制迁移单位，后者只需要算哈希。

**当前项目实现对照**
- 未使用 Cluster（单节点）；`待核实` 是否有升级规划。
- 如果升级：用户相关 key（`ubaseinfo_<uid>`、`utoken_<uid>`、`uip_<uid>`）天然按 uid 分散，可用 hash tag 保证同一用户 key 同槽；分布式锁（`lock_<uid>`）也按用户分散。
- 注意：`logincount` 哈希、`chatserver:registry` 哈希是**全局热点 key**，在 Cluster 里会落在单个槽/节点，需要单独评估（本地缓存/拆分）。

**差距与改进建议**
1. 背熟 16384 的三个数字：2KB bitmap、≤1000 节点、CRC16；以及 MOVED/ASK 的区别。
2. 想清楚本项目切到 Cluster 后哪些 key 是热点、哪些操作跨槽（事务/多 key），这题常被追问。
3. 记住 hash tag 示例，体现你会用。

**追问预判**
- 16384 个槽，100 个节点怎么分？——平均分或按容量权重分（`redis-cli --cluster rebalance` 支持 weight）。
- 客户端怎么知道槽归属？——首次 `CLUSTER SLOTS`/`SHARDS` 拉取拓扑，收到 MOVED 后刷新。
- ASK 和 MOVED 为什么要区分？——迁移中源节点仍有部分 key，客户端不能永久改缓存，否则没迁的 key 会找不到；因此用 ASK 临时跳转并要求 ASKING。
- 同一个 key 一定在同一个槽吗？——是，除非故意用 hash tag 把不同的 key 绑在一起；同一 key 永远哈希到同一槽。

### 2.6 百度二面·问39：master 挂了怎么处理？没有副本会怎样？

**面试官原话（转写，来自问题清单）**
> 问39：master 挂了之后集群怎么处理？没有副本会怎样？

**状态：❓ 未准备。（与问37 部分重叠，但这里要讲清 failover 的完整流程。）**

**可直接背的参考回答**
> 有副本的情况：主节点被判定失联后，集群走一轮选举。过程是——从节点发现主节点 PFAIL，通过 gossip 收集其他主节点的确认，达到多数派后主节点被标记 FAIL；该主节点的从节点发起竞选，需要在有槽的主节点中拿到多数票，得票的从节点提升为新主，接管原主的槽，然后广播新拓扑；客户端收到 MOVED 后把请求切到新主。整个检测+选举的时间取决于 `cluster-node-timeout`（默认 15s，可调小），这期间这个分片的写请求会失败或超时。
> 没有副本的情况：该主节点的槽没有任何人可以接管，槽处于「无归属」状态。默认 `cluster-require-full-coverage yes` 时，**整个集群都会拒绝服务**（返回 CLUSTERDOWN），影响面从「一个分片」扩大到「全站」；即便把它设为 no，也只是把影响限制在那些槽上。恢复方式只有人工：把槽重新分配给其他主节点（数据已经丢了）或修复节点后重新加入。更要命的是集群需要多数主节点在线，掉一个主节点会削弱集群的投票多数，接连掉主可能进入不可用状态。
> 所以结论：主节点必须配从节点，并在故障后检查从节点是否完成任务；`WAIT` 和 `min-replicas-to-write` 可以用来减少异步复制丢的数据；对特别关键的数据，链路层（比如消息落 MySQL）有权威存储兜底。

**技术要点拆解**
- failover 详细步骤：PFAIL → 其他主节点确认 → FAIL → 从节点竞选（只有它的主被 FAIL 且自己数据足够新才有资格）→ 多数主节点投票 → 提升 + 广播。
- 为什么需要多数派：防止网络分区中左右两侧各自选主（脑裂）。
- `cluster-node-timeout` 的取舍：调大容错但发现慢；调小敏感但易误判。
- 数据丢失窗口：异步复制，主挂时没有同步给从的写会丢；WAIT numreplicas timeout 可以把关键写同步到 N 个副本，代价是延迟。
- 人工恢复路径：`redis-cli --cluster fix`、`reshard`、手动 `CLUSTER FORGET/MEET`、从备份恢复。

**当前项目实现对照**
- 项目未用 Cluster；单节点加上「无副本」正是最坏情况（见 2.1）。但项目权威存储在 MySQL，Redis 丢失的只是临时状态，所以危害等级不同——面试时要主动对比，显示你理解「缓存的高可用」和「数据库的高可用」要求不同。
- 多端互斥/在线状态丢失的代价是「用户可能双端在线」而非「数据损坏」。

**差距与改进建议**
1. 画一张 failover 流程图并背下时间线（检测 → 选举 → 切换）。
2. 记住两个配置名：`cluster-node-timeout`、`cluster-require-full-coverage`；一个数据保护配置：`min-replicas-to-write`。
3. 把「没有副本 + 全槽覆盖 = 全站不可用」当作必须能说出的知识点。

**追问预判**
- 从节点为什么不马上接管？——要先确认主真的挂了（多节点确认），否则网络抖动会频繁切换。
- 选举 stalemate 怎么办？——等待多数派恢复；这也是要奇数部署、保证多数派的原因。
- 主从切换后旧的写请求怎么办？——客户端收到 MOVED，把请求重定向到新主；写失败的请求由上层重试/幂等处理。
- 与本项目单节点故障对比？——本项目是缓存角色，故障影响登录/在线状态，MySQL 兜底；Cluster 主节点无副本故障影响的是数据可用性。

### 2.7 百度二面·问40：存登录态的 Redis 节点挂了，大量登录请求涌进来怎么办？

**面试官原话（转写，来自问题清单）**
> 问40：如果存储登录态的 Redis 节点挂了，大量登录请求涌进来会发生什么？

**状态：❓ 未准备。这题是本项目最痛的场景，要背得非常熟。**

**考点分析**
- 这是一道「故障链」题：不仅要答「会怎样」，还要答「怎么防」。面试官想看雪崩放大效应：Redis 超时 → 业务线程阻塞 → 队列堆积 → 服务不可用 → 客户端重试 → 更糟。
- 结合项目：登录链路是 GateServer 查 MySQL 验密 → StatusServer 写 token 并分配节点 → 客户端连 ChatServer → ChatServer 校验 token。Redis 在这个链路里出现 3 次，任一失败都可能卡住登录。

**可直接背的参考回答**
> 先说会发生什么，这是一条典型的雪崩链：
> 登录高峰期，大量请求走到校验 token / 分配节点的逻辑，Redis 节点挂了，客户端连接池里的请求开始超时。我们网关有 IO 线程池和业务线程池，登录查库和 Redis 调用都在业务线程池里执行——Redis 变慢后，业务线程的任务开始积压，队列满之后新登录请求被拒绝或超时；客户端看到失败会**重试**，请求量进一步放大。如果这时系统设计成「失败就查 MySQL 兜底」，那 MySQL 的连接池和 CPU 也会被打满，从一个组件的故障扩散成全链路不可用。总之：**单点 Redis 故障 + 无降级的重试 = 全站登录不可用**。
> 防的措施分四层：
> **第一，恢复可用性**：登录态 Redis 做主从+哨兵（或 Cluster），节点挂了自动切换；客户端连接池支持新主地址、设置短超时 + 快速失败 + 熔断（连续失败就暂停请求一段时间再半开），不能让线程堆在等待上。
> **第二，消除强依赖**：把登录 token 做成自包含的 JWT/HMAC，服务端本地验签，不查 Redis；Redis 只保留「用户当前在哪个节点、哪个 session」这种会话控制信息，且允许降级——降级期间不踢人、不保证单端，恢复后再纠正。
> **第三，兜底有保护**：必须查库时（比如验证码/密码校验降级），走独立的、受限的兜底通道——单独的小连接池、限流（比如只放 10% 流量）、单飞（同一个 key 的并发回源只放一个请求）、熔断。绝不能让兜底流量直接冲到 MySQL。
> **第四，入口限流**：网关按用户/IP 维度做令牌桶或排队，超出容量快速失败并返回「系统繁忙，请稍后重试」，让用户重试进入可控节奏，而不是全量冲击后端。
> 另外，客户端重试要加退避和抖动，避免同一秒集中重试；监控上要对 Redis P99、连接池等待数、业务线程队列长度做告警——**在这个场景里，最先出问题的信号通常是线程池队列而不是 Redis 本身**。

**技术要点拆解**
- 为什么「一个 Redis」能打掉全站：登录是所有用户的必经入口，且登录链路对 Redis 是串行依赖（查 token → 写会话 → 分配节点），任一环节超时都会拉长整个请求；线程池是有限资源，等待型故障最容易拖垮它。
- 雪崩放大链：Redis 慢 → 线程占用 → 队列满 → 全服务不可用 → 客户端超时重试 → QPS 放大 → 更不可用。
- 熔断/降级/限流的区别：限流是控制入口速率（丢请求或排队），熔断是发现下游持续失败后快速失败不再调用，降级是换一条更弱的实现路径（本地缓存/MySQL）。
- 单飞（request coalescing）：同一个 key 并发回源只放行一个，避免大量线程同时查询同一个热 key。
- 快速失败比慢失败好：超时必须设得很短（比如 50~100ms 级），否则线程池排队时间会远超超时时间。

**当前项目实现对照**
- 登录链路：`GateServer/src/LogicSystem.cpp` 的 `/user_login`（查 MySQL → `GetChatServer`）→ `StatusServer` 写 `utoken_` + 分配节点 → `ChatServer` 登录校验 `utoken_` + 加锁写 `uip_`/`usession_`。
- GateServer 有 IO/业务线程池（OPPO 问21 你答过），可以在面试里复用这个细节，说明你知道「线程池是故障传导的关键环节」。
- 现状没有熔断/限流/本地缓存/兜底查询；Redis 超时会直接失败，但 ChatServer 连接池是 10 条（`RedisMgr.cpp:10`），阻塞面相对有限——这点可以两面说：资源隔离好，但吞吐也受限。

**差距与改进建议**
1. 给 Redis 客户端封装加**超时 + 熔断 + 降级开关**（可以先做超时与失败计数）。
2. 用 JWT/HMAC 替换「登录必查 Redis」，这同时是问43 的答案。
3. 在 GateServer 登录路径加限流（哪怕是一个简单的令牌桶），并把「重试退避」写进客户端。
4. 准备一版「Redis 故障演练预案」：把 Redis 手动停掉，观察系统行为（谁先崩、错误码是什么、恢复后如何回到正常），面试讲演练结果最加分。

**追问预判**
- Redis 挂和 Redis 慢，哪个更危险？——慢更危险，因为等待型故障先耗尽线程池；所以超时要短、要熔断。
- 兜底查 MySQL 怎么保证不把 MySQL 打挂？——限流 + 单飞 + 独立连接池 + 只读从库/缓存结果；还要给兜底路径设开关和上限。
- 切换过程中已经发出的登录请求怎么办？——快速失败让客户端退避重试，幂等（token 生成可以覆盖旧值，不影响正确性）。
- 为什么不用 Redis 持久化的方式早恢复？——恢复时间不可控（取决于数据量），登录是入口，需要的是秒级 failover 而不是分钟级重启；持久化是最后兜底。

### 2.8 百度二面·问41：缓存击穿、穿透、雪崩分别是什么？怎么解决？

**面试官原话（转写，来自问题清单）**
> 问41：什么是缓存击穿、缓存穿透、缓存雪崩？分别怎么解决？

**状态：❓ 未准备（基础题，必须秒答）。**

**可直接背的参考回答**
> **缓存穿透**：查的是一个**数据库里也不存在的数据**，缓存永远不命中，每次请求都打到数据库。比如有人拿随机 uid/邮箱疯狂查询。解决办法：①缓存空值（查不到也写一个短 TTL 的空标记，防重复穿透）；②布隆过滤器，先用它拦掉一定不存在的数据；③入口参数校验和限流，异常查询直接拒绝。注意空值缓存要设短过期（比如 30~60 秒），防止数据后来被创建时一直读空。
> **缓存击穿**：某个**热点 key 恰好过期**的瞬间，大量并发请求同时回源查同一个 key，把数据库打出一个尖峰。解决办法：①互斥锁/单飞，只放一个请求去加载，其他请求等待或短暂返回旧值；②逻辑过期，key 不设物理 TTL，值里存逻辑过期时间，过期后由异步线程更新，读请求先返回旧数据；③热点 key 永不过期 + 后台定时刷新。
> **缓存雪崩**：两种形态——**大量 key 在同一时间过期**，或者 **Redis 集群整体宕机**，导致所有请求同时涌向数据库。解决办法：①过期时间加随机抖动，避免批量同时失效；②多级缓存（本地缓存兜底）和 Redis 高可用；③限流、熔断、降级，数据库前面要有保护；④缓存预热，重启后先灌热点数据再放流量。
> 用我项目里的例子说：`ubaseinfo_<uid>` 是查得到才写的缓存；如果给 `utoken_` 加 TTL，那登录高峰前要预热，并且 TTL 要带抖动；验证码 key 是「短 TTL + 一次性」，过期是正常语义，不需要保护。

**技术要点拆解**
- 三种问题是三个不同维度：「不存在的数据」→ 穿透；「单个热 key 失效」→ 击穿；「大面积失效/宕机」→ 雪崩。
- 空值缓存的细节：写空值 `NULL` 标记而不是不写；短 TTL；和布隆过滤器配合使用（布隆有误判，说「可能存在」的还是要查）。
- 互斥锁重建 vs 逻辑过期：

| 方案 | 一致性 | 可用性 | 复杂度 |
| --- | --- | --- | --- |
| 互斥锁重建 | 高（拿到的都是新数据） | 等锁期间请求阻塞/降级 | 中（锁 + 超时） |
| 逻辑过期 + 异步更新 | 最终一致（可能返回旧值） | 高（不阻塞） | 中 |
| 永不过期 + 后台刷新 | 最终一致 | 高 | 需要刷新任务 |

- TTL 抖动：`ttl = base + rand(0, base*0.2)`，避免整点失效。
- 多级缓存：进程内 LRU（毫秒级、无网络）→ Redis → DB；本地缓存要解决一致性（订阅变更/短 TTL）。
- 布隆过滤器：空间小、有误判；不适合频繁删除（可用 counting bloom / RedisBloom）。

**当前项目实现对照**
- `ubaseinfo_`：`Get` 失败后查 MySQL 再 `Set`（`LogicSystem.cpp:730-775`）——典型 cache-aside，**没有空值缓存、没有 TTL、没有互斥重建**。
- 验证码：`code_<email>` TTL 600s（VarifyServer），天然防穿透（验证码必须存在）。
- token/在线状态：无 TTL（master），不存在穿透问题。
- 分布式锁重建：可以用项目现成的 `DistLock` 做单飞。

**差距与改进建议**
1. 给 `ubaseinfo_` 加空值缓存 + 随机 TTL；查询不存在的用户是常见攻击面。
2. 把「互斥重建」和项目现有 `DistLock` 结合起来讲，故事完整（锁 + 短超时 + 拒绝降级）。
3. 背好一句话区分三者，避免面试紧张时混：**穿透是数据不存在，击穿是一个热点过期，雪崩是同时过期/整体宕机**。

**追问预判**
- 布隆过滤器的误判率怎么控制？——位数组大小和哈希个数按预估数据量与误判率计算，误判只会多放一些查询。
- 空值缓存会不会占内存被攻击？——短 TTL + 容量上限 + 对不存在 key 的请求先做参数校验/限流。
- 逻辑过期读到旧数据会不会有业务问题？——弱一致场景可接受；强一致场景用互斥重建。
- 本地缓存怎么失效？——短 TTL + 发布订阅/版本号，接受窗口内的旧值。

### 2.9 百度二面·问42：热点 key 怎么处理？

**面试官原话（转写，来自问题清单）**
> 问42：热点 key 怎么处理？

**状态：❓ 未准备。**

**可直接背的参考回答**
> 分「怎么发现」和「怎么解决」两步。
> **发现**：①Redis 自带工具——`redis-cli --hotkeys`（需要 LFU 淘汰策略）、`OBJECT FREQ` 看访问频率、`--bigkeys` 找大 key；②`MONITOR` 可以采样但性能开销大，只能短时用；③代理层统计（codis/twemproxy 这类会在转发时计数）；④业务埋点，按 uid/消息维度统计；⑤慢查询日志。
> **解决**：
> ①**本地缓存**：最热的 key 放到进程内缓存，请求不打 Redis，比如排行榜、热门直播间。代价是多实例一致性，用短 TTL 或变更通知解决。
> ②**key 打散**：把一个热 key 拆成 N 份（`hot:{0..N}`），写的时候随机写一份或全写，读的时候随机读，把单节点压力摊到 N 个。适合计数器类场景，读到的值可能有偏差，可以定期合并。
> ③**多级缓存**：本地缓存 → Redis → DB，逐级兜底。
> ④**读写分离/加副本**：读热点走从节点或只读副本；写热点没法靠副本解决，要用打散或异步化。
> ⑤**限流/降级**：对单 key 维度的 QPS 做保护，超过阈值就降级。
> ⑥**大 key 拆小**：一个 hash 存了 10 万个字段就是大 key，改成按前缀分桶（`user:info:{shard}`），避免单 key 阻塞。
> 我项目里的热点点：`logincount` 和 `chatserver:registry` 是全局哈希，所有调度、所有节点都读写它，量大了就是热点；另外最初连接数更新用全局锁 `lockcount`，本身就是逻辑热点，后来我改成心跳定时器统一统计一次再写，去掉了高频锁——这就是「把热点写变成周期批量写」的思路。

**技术要点拆解**
- 热点 key 的危害：Redis 单线程处理命令，一个 key 的 QPS 过高会占满单节点 CPU，影响同一节点上的其他 key（队头阻塞）。
- 探测手段对比：采样类（hotkeys/OBJECT FREQ，成本低但需要 LFU）、全量类（MONITOR，成本高）、代理类（准确但要代理层）。
- 打散的细节：读随机、写全量会放大写流量；写随机 + 定期聚合会有偏差；选择取决于业务（计数、库存这类要有合并逻辑）。
- 热点 key 和大 key 是两个问题但常一起出现：大 key 的问题在内存/网络/阻塞（删除、序列化），热点在 CPU。
- 从库分担：主从架构下读热点可以扩从，但复制延迟和写热点无解。

**当前项目实现对照**
- `logincount`：master 每 60s 全量 HSet；Season_2 改成每 2s `SET lease` 单 key——本来就不大，是「每个节点一个 key」，压力分散，不是单 key 热点。
- `chatserver:registry`：所有调度实例 `HGETALL`，节点多、调度频率高时是热点；优化方向是调度本地缓存 + 事件通知。
- `lockcount`：历史全局锁，`day35` 已去掉（心跳统一写 count）——现成的「热点/锁优化」案例。
- `ubaseinfo_`：按 uid 分散，天然没有单 key 热点；如果某个大 V 被频繁查询，那就是热点，可用本地缓存。

**差距与改进建议**
1. 把 `lockcount` 优化的故事背熟：问题（每个用户上下线都要抢全局锁更新计数）→ 方案（心跳周期内统计，一次写入）→ 收益（去锁、降频）——这比背通用八股更有说服力。
2. 面试时先问清「读热点还是写热点」，因为答案不同（读走缓存/副本，写要打散/异步）。
3. 给 `chatserver:registry` 的读加本地缓存（10s 级），体现你会优化自己系统的热点。

**追问预判**
- 热点 key 打散后怎么保证计数准确？——定期合并/汇总，或接受最终一致；强一致计数用 `INCR` 分桶后求和。
- 本地缓存过期会不会造成瞬时回源尖峰？——加随机抖动 + 互斥重建 + 错峰刷新。
- 怎么判断一个 key 是热 key？——频率阈值 + 时间窗口，用 LFU/采样统计，业务埋点更精确。
- 热点 key 和缓存击穿的区别？——击穿强调「过期瞬间」，热点强调「持续高频」；热度会让击穿后果更严重。

### 2.10 百度二面·问43：「Redis 挂了登录服务就不可用」这个设计有什么问题？怎么改？

**面试官原话（转写，来自问题清单）**
> 问43：Redis 挂了登录服务就不可用，这个设计有什么问题？应该怎么改？

**状态：❓ 未准备（这是问40 的「设计结论版」，也直接点名了本项目最大隐患）。**

**考点分析**
- 面试官期待的答案是：**可用性耦合**——把一个 99.9% 的组件放进登录的关键路径，整体可用性就降到它的水平；而且登录是入口，故障影响全社会。
- 改法要落在「依赖降级」上：让 Redis 从「必须」变成「最好有」，或者至少让失败路径可控。

**可直接背的参考回答**
> 问题本质是**把可选的缓存组件放进了不可降级的强依赖路径**，导致两个后果：
> 第一，可用性相乘。假设登录服务本身 99.9%，Redis 99.9%，串联后可用性上限降到约 99.8%；更要命的是登录是所有用户的必经入口，Redis 抖一下就会放大成全站事故。第二，故障扩散：Redis 挂了以后，如果代码是「失败重试」或「失败查库」，会把请求堆积到线程池和 MySQL，从一个组件故障演变成全链路雪崩。
> 改法我会做四件事：
> **①把 token 变成自包含凭据。** 登录成功后签发 JWT 或 HMAC 签名 token，包含 uid、签发/过期时间、签名；ChatServer 登录校验时本地验签即可，不需要查 Redis。这样「验证身份」这条最关键的路径完全不依赖 Redis。
> **②把 Redis 降级为「会话控制」的弱依赖。** Redis 里只保留当前在线位置、session id 这类用于踢人/状态的临时数据；Redis 不可用时允许降级——暂不保证单端互斥（允许两个端同时在线），恢复后再按新写入的状态把旧的踢掉。这是用「短暂弱一致」换「登录可用」。
> **③多级兜底 + 保护。** 本地缓存热 token/用户资料；必须查库时走限流的兜底通道（只放一部分流量、单飞、独立连接池）；网关入口限流 + 客户端退避重试。
> **④Redis 自身高可用。** 主从+哨兵/Cluster 做故障自动切换；客户端短超时 + 熔断，切换期快速失败。
> 最后要明确取舍：**登录可用性优先级高于「严格单端在线」**，所以选择 AP 而不是 CP；恢复后的一致性用「最后写入的会话状态 + 踢旧端」来收敛。

**技术要点拆解**
- 可用性数学：串联依赖的可用性 = 各环节相乘（0.999 × 0.999 ≈ 0.998）；关键路径上的组件越少越好。
- 无状态 token（JWT）：签名校验不需要存储，天然可水平扩展；缺点是无法主动吊销（要做黑名单又依赖存储），所以「踢人/强制下线」用短 TTL + Redis 会话状态 + 版本号（token 里带 tokenVersion，服务端改版本即可吊销）。
- 降级设计三板斧：
  1. **绕开**（JWT 本地验签）；
  2. **兜底**（本地缓存/MySQL，限流）；
  3. **快速失败**（限流熔断，保系统不雪崩）。
- 一致性取舍：降级窗口允许多端在线，恢复后按 `usession_` 收敛；相比「全部登不上」，这个代价可接受。
- 监控与演练：故障注入（停 Redis）验证降级路径真的可用，而不是设计文档上的可用。

**当前项目实现对照**
- 现状：token 写/读、`uip_`/`usession_`、资料缓存全部走 Redis；ChatServer 登录 `LogicSystem.cpp:132-141` 先 `Get(utoken_)`，失败直接返回 UidInvalid——Redis 一挂，新登录和重连全部失败（工作区 master 无重连，Season_2 的 `/reassign_chat` 也要经过 StatusServer 校验 token）。
- Session token 在 Season_2 有 86400s TTL，仍是「查 Redis」模式；没有 JWT/本地验签。
- GateServer 登录验密直接查 MySQL，本身是另一个潜在的入口瓶颈（可加缓存/限流）。
- 参考 `day17`：早期版本 token 存在 StatusServer 内存里，后来改成 Redis——**从单机内存到集中存储解决了多实例一致性，但同时引入了强依赖**，这个演进可以讲成「同一问题的两种取舍」。

**差距与改进建议**
1. 把 token 换成 HMAC/JWT（哪怕先做 HMAC-SHA256 的简单版），ChatServer 本地验签，Redis 只存「可选吊销」信息——这是本文件最值得动手的改进。
2. 实现降级开关（配置或信号触发）：Redis 不可用时登录走本地验签、互斥降级、资料走带限流的 MySQL。
3. 做一次故障演练并记录：停 Redis → 登录、发消息、重连分别什么表现 → 恢复后的行为。

**追问预判**
- JWT 不能主动踢人怎么办？——短 TTL + token 版本号/黑名单（黑名单可以放本地缓存 + Redis 双写，Redis 挂了至少保住登录，踢人延后）。
- 本地验签的密钥怎么管理？——配置文件/环境变量/密钥服务分发，定期轮换，不能硬编码在客户端。
- 降级允许双端在线，消息会乱吗？——消息权威在 MySQL、按用户游标补齐，双端各拉各的，冲突窗口恢复后由踢人收敛。
- 为什么不用 MySQL 直接替代 Redis 存登录态？——读 QPS 和延迟（每次登录/校验打 DB）不划算，MySQL 适合做兜底而不是主路径。

### 2.11 华为主管面·问28：为什么用 Redis？

**面试官原话（转写）**
> 问28：那当时为什么会选择用 Redis 啊？为什么使用 Redis 这个数据库？

**你当时的回答（压缩）**
> ①有些东西想快速读写；②不想让它打到 MySQL，比如用户资料/头像预先加载到 Redis，登录时读取更快；③Redis 有自动过期时间，用来做聊天服务水平扩展和掉线自动下线；④用户登录在哪个服务这种临时状态写 Redis，下线后过期或者主动清除都方便，不用写 MySQL。

**状态：✅ 基本可以（四个点都对），补上「边界」会更完整。**

**可直接背的参考回答**
> 主要是四个原因：
> **第一，读写性能。** Redis 数据在内存、单线程无锁处理命令，读写在亚毫秒级，而我们的登录、发消息是高频路径，需要低延迟。我还用了 Redis 的多种结构：String 存 token 和资料 JSON、Hash 存节点注册表和连接数、TTL 做过期语义——不是把它当单一 KV 用。
> **第二，给 MySQL 减压。** 用户资料、头像这些数据，登录时每个用户都要读，直接打 MySQL 会放大查询量。我把 `ubaseinfo_<uid>` 做成 cache-aside：先查 Redis，没有再回源 MySQL 并写回；这样热数据的读压力从数据库挪到内存。
> **第三，TTL 原生支持临时状态的生命周期管理。** 验证码设过期自动消失；聊天服务的节点注册用「2 秒续期、6 秒过期」的租约来判断存活——过期即下线，不用自己写清理任务；用户掉线清理也靠「心跳超时 + 删除 Redis 记录」，不用为临时状态建表、写删除逻辑。
> **第四，临时状态不值得写 MySQL。** 比如「用户在哪个 ChatServer 上、当前 session 是什么」这种只在用户在线期间有意义的数据，写 MySQL 既增加写放大，又要维护清理任务；放 Redis 天然是临时语义，重启重建成本也低。
> 我也清楚边界：Redis 是内存数据库，大 value、大 key 会带来成本和阻塞风险；持久化只是尽力而为，所以我们的**权威数据（用户、好友、消息）在 MySQL**，Redis 定位是缓存 + 临时状态 + 协调（分布式锁），不是唯一存储。

**技术要点拆解**
- Redis 快的原理：纯内存 + 单线程命令处理（无锁）+ IO 多路复用 + 高效数据结构（跳表/压缩列表等）；但单线程也意味着慢命令（大 key、KEYS）会阻塞所有人。
- 数据结构选择：
  - String：token、序列化 JSON、计数器（`INCR`）；
  - Hash：`logincount`、`chatserver:registry`（field 级读写，不用整取）；
  - ZSet：排行榜/延迟队列（本项目未用但可提）；
  - List/Stream：简易队列/消息流。
- TTL 的两种用途：**语义型过期**（验证码、token）和**判活型过期**（lease 租约，过期=下线索性）。后者是面试亮点。
- 与 MySQL 的角色分工：MySQL 保证 ACID/持久化/复杂查询；Redis 保证低延迟/高吞吐/临时状态；两者不是替代关系。
- 内存成本：Redis 数据全在内存，容量是最贵的资源；要有淘汰策略（`maxmemory-policy`）、大 key 治理、过期策略（惰性 + 定期删除）。

**当前项目实现对照**
- `ubaseinfo_` 预加载：`LogicSystem.cpp:730-775`，Redis 未命中查 MySQL 再写回（登录时一次性取资料/好友/申请）。
- TTL 判活/掉线：Season_2 lease 2s/6s（`ChatServer.cpp`）；master 是 60s 心跳 + 20s 连接超时（`CSession.cpp:271-278`）+ 主动清理（`DealExceptionSession`）。
- 登录临时状态：`uip_`/`usession_`/`utoken_`，不写 MySQL；掉线清理走心跳（`day35`）。
- 验证码过期：VarifyServer `SetRedisExpire`（600s）。
- 磁盘/内存事实：单节点、无 maxmemory 配置（`待核实`），存在内存打满风险——可以主动说出这个风险，显示边界意识。

**差距与改进建议**
1. 在回答末尾主动加「边界与风险」：内存成本、持久化弱、单线程慢命令、不能当权威存储、单点问题——面试官喜欢自省式回答。
2. 补一个 Redis 使用规范：key 命名（已有前缀）、TTL 策略、大 key 阈值、淘汰策略。
3. 如果被追问「为什么不用 MySQL 存临时状态」，按「写放大 + 清理成本 + TTL 语义」三点回答（你的原话已经接近，梳理清楚即可）。

**追问预判**
- Redis 单线程为什么还能快？——内存操作 + 无锁 + epoll + 高效数据结构；瓶颈通常是网络和慢命令。
- Redis 存头像吗？——存的是头像 URL/路径（元数据），图片本体在资源服务/文件系统，不能把大文件塞 Redis。
- 内存满了怎么办？——设置 maxmemory + LRU/LFU 淘汰，只淘汰缓存类数据；`uip_`/锁这类关键 key 要考虑不被淘汰或用独立实例。
- 为什么不用本地缓存替代 Redis？——多实例一致性、跨服务共享、TTL/淘汰运维能力；本地缓存只能作为多级缓存的第一层。

### 2.12 百度一面·问29~31：多进程/多机的全局变量放在哪？

**面试官原话（转写）**
> 问29：假如线上服务部署了很多个进程、多台机器，需要维护一个全局变量，这个变量是在数据库吗？还是在什么地方？（答29：没听清）
> 问30：第一就是，是在数据库中吗？还是在什么？
> 问31：那就是说他其实是需要起一个 Redis 服务对吧？然后假如我部署了五个进程，这五个进程去访问同一个人（同一个变量）。

**你当时的回答（压缩）**
> 放到 Redis 里，然后通过分布式锁去拿。

**状态：✅ 可以（方向对），但要补「为什么是 Redis 而不是 DB/本地」和「锁保护什么」。**

**考点分析**
- 背景是你 RPC 项目里的「主/从 Reactor 选举」：单进程内可以用原子变量，多进程/多机就需要一个所有实例都能访问、且支持原子互斥操作的共享存储。
- 面试官在验证你知不知道：跨进程共享内存不可行（地址空间独立）→ 需要外部协调服务 → Redis/etcd/DB/ZK 各自适合什么。

**可直接背的参考回答**
> 多进程、多机之后，本机的内存和原子变量只能保证进程内可见，不可能做全局协调，必须放到一个所有实例都能访问的外部存储里。选型上：
> ①**Redis**：部署成本低、读写快、天然支持原子命令和分布式锁，非常适合「全局标志、计数器、临时状态」这类数据；用 `SET NX` 或 Lua 做原子读改写，或者 `SET NX` 直接选主，不需要读。缺点是有网络往返、需要处理超时和故障。
> ②**etcd/ZooKeeper**：为分布式协调而生，提供租约、watch、revision/CAS，最擅长「选主、配置、服务发现」；强一致，但运维成本高。
> ③**数据库**：可以用唯一约束或条件更新 `UPDATE ... WHERE version = x` 做 CAS，持久可靠，但高频读写不合适，适合作为兜底。
> 我这个场景（选出谁是主 Reactor/全局唯一角色）用 Redis 加分布式锁是最省事的；但更严谨的做法是直接利用 `SET key value NX PX` 的原子性——**谁设置成功谁就是主**，不需要先读再判断，天然没有竞态；锁则用于保护更复杂的「读-改-写」临界区。

**技术要点拆解**
- 跨进程共享变量必须满足：所有实例可达 + 操作原子 + 故障可发现（超时/租约）。
- Redis 原子性来源：单线程执行 + 单命令原子 + Lua 脚本整体执行。
- 分布式锁的适用边界：保护小临界区；更大的协调（选主、配置分发）优先用 etcd/ZK 的租约 + watch。
- 数据形态：小表/单 key 标志比「塞进业务大表」更利于加锁和缓存（对应 2.14）。

**当前项目实现对照**
- `DistLock`（`day32`）：`SET lock:xxx uuid NX EX 10` + Lua 释放，正是这个思路的项目落地；使用场景：用户登录互斥（`LogicSystem.cpp:198`）、心跳/掉线清理（`CSession.cpp:292`）、连接数更新（`RedisMgr.cpp:397`）。
- Season_2 调度不再需要锁：节点注册 + lease 用 TTL 语义替代锁；连接数由每个节点写自己的 key，天然无竞争——**「用数据模型消除锁」比加锁更好**，这个观点可以在面试里讲。

**差距与改进建议**
1. 补一句「单命令原子（SET NX）优先于锁」，这是比「加锁」更高一层的回答。
2. 准备 etcd/ZK 与 Redis 的选型对比，回答「为什么不用 ZooKeeper」。
3. 把项目里「哪些地方用了锁、哪些地方用数据模型消除了锁」列成清单。

**追问预判**
- 全局变量放 Redis，Redis 挂了怎么办？——见 2.1/2.10：高可用 + 降级；如果只是选主，可以退化为「静态配置指定主」。
- 为什么不共享内存/消息队列？——共享内存限于单机；消息队列解决异步，不提供一致的当前值。
- 锁和 CAS 怎么选？——临界区复杂、操作多步用锁；单点判断用 CAS/原子命令。

### 2.13 百度一面·问33~35：跨地域 20ms 竞态与「读时加锁」

**面试官原话（转写，压缩）**
> 问33：5 个进程、一个 Redis、跨地域单次访问 20ms。进程一读到了旧值，进程二在进程一写之前也读到了相同的值，两个都认为自己该写，会出现什么情况？
> 问34：那你的意思是你在读的时候其实就加锁？
> 问35：你读的时候加锁，就是阻止它去做修改是吧？

**你当时的回答（压缩）**
> 出现两人同时写、都认为自己是「主」的情况。解决方式是加分布式锁，连上 Redis 后立马加锁。
> 问34/35 追问「读时就加锁」——你回答「对，读的时候加锁」。

**状态：⚠️ 被打穿——方案能保正确性，但面试官在问38 明确点评「频繁读加锁有延迟损耗」。**

**考点分析**
- 这是典型的 **read-modify-write 竞态**：两个进程都先 GET 到 `holder=null`，各自认为「没人当主」，然后都去 SET，后写的覆盖先写的（或双写造成状态不一致）。
- 「读时加锁」把整个读-改-写串行化，正确性没问题，但代价：①读操作也要抢锁，读多写少场景下吞吐急剧下降；②跨地域 20ms，加锁 + 读 + 写至少 2~3 个 RTT，延迟成倍；③锁竞争、锁超时、锁未释放（依赖 TTL 兜底）都会变成新的故障点。
- 正确解法是**把「判断」合并进「写」的原子操作里**，让读路径不加锁。

**可直接背的参考回答**
> 这个场景的正确性要求是「同一时刻最多一个进程认为自己该写」，本质是 read-modify-write。我当时的回答「读时加锁」能解决正确性问题，但它把读路径也串行化了——就像面试官点评的，线上高频读取时，频繁加锁会带来明显的延迟损耗，尤其是跨地域一次 20ms，锁 + 读 + 写放大到 40~60ms，还会在锁上排队。
> 更好的做法有三种，按场景选：
> **①用原子写原语消除「先读后写」。** 如果逻辑是「选出唯一的主」，直接 `SET lock:master <id> NX PX 30000`——谁设置成功谁就是主，失败的人直接放弃，全程不需要读、不需要加锁，天然没有竞态。这是 leader election 的标准做法。
> **②乐观锁/CAS。** 如果必须先读再判断，那读可以不加锁，写的时候用版本号做 CAS：Redis 可以用 `WATCH key` + `MULTI/EXEC`，或者一段 Lua 脚本做「比较再设置」；数据库可以用 `UPDATE ... SET v = v+1 WHERE v = 旧值`。CAS 失败就重读重试。写冲突概率低时，这比锁开销小得多。
> **③把状态判断放到写操作内部。** 比如用 `INCR`/`SETNX` 这类单命令做判断，或者把「选主」下沉到 etcd/ZooKeeper 的租约 + revision 事务里——它们本来就是为分布式协调设计的，天然支持 watch，不需要轮询和加锁。
> 加锁不是不能用，而是要用在正确的地方：**只保护写临界区，粒度尽量小，读路径尽量无锁**；锁要有超时、要有唯一 value、释放用 Lua，并配合 fencing token 防止「锁过期后旧持有者还在写」。

**技术要点拆解**
- 竞态时间线：

```
T0  P1 GET holder -> null
T1  P2 GET holder -> null          ← 20ms 窗口
T2  P1 SET holder=P1
T3  P2 SET holder=P2               ← 覆盖 P1，双主
```

- 三种并发控制对比：

| 方案 | 读开销 | 写开销 | 一致性 | 适用 |
| --- | --- | --- | --- | --- |
| 读时加锁（悲观） | 高（抢锁+RTT） | 高 | 强 | 临界区复杂、写冲突高、吞吐要求低 |
| 写时 CAS（乐观） | 低（无锁） | 中（失败重试） | 强（按版本） | 读多写少（大多数场景） |
| 原子写原语 | 无 | 单命令 | 强 | 选主、抢占、计数 |
| 选主服务（etcd/ZK） | watch 低 | 租约事务 | 强 + fencing | 分布式协调 |

- Redis 的 `WATCH/MULTI/EXEC`：WATCH 后如果 key 被改动，EXEC 失败返回 nil，需要重试；Lua 更简单（一段脚本内比较并写，单线程执行，天然原子）。
- fencing token：锁服务每次成功加锁发一个单调递增的 token，被保护资源校验 token 只增不减，防止「旧持有者暂停后醒来继续写」。Redis 简单锁一般没有 fencing，强一致场景建议用 ZK/etcd 或数据库唯一约束兜底。

**当前项目实现对照**
- `DistLock`（`SET NX EX` + Lua 释放）已经具备正确锁的雏形，但项目里用法是「连上锁后再读改写」（登录互斥场景），这也正是面试官点评的读路径加锁模式——可以主动说「第二季我会把纯判断类的逻辑改成原子写/CAS，只保留互斥类临界区（比如踢人）用锁」。
- `day35` 把 `lockcount` 高频全局锁优化成心跳周期写，正是「减少锁的使用面」的实际案例，可以作为回答的收尾例证。

**差距与改进建议**
1. 把上述三种方案背熟，并能对「谁是主 reactor」这个具体问题给出「`SET NX` 一步搞定」的答案。
2. 检查项目里所有 `acquireLock` 的使用：哪些是真互斥（踢人/登录状态变更），哪些可以改成原子命令或 SQL 条件更新，列出来。
3. 给锁加指标（等待时长、失败率），面试讲「我们上线后观测到锁等待 P99 是多少」会非常加分。

**追问预判**
- CAS 失败重试太多次怎么办？——限制重试次数 + 退避；冲突极高说明该用悲观锁或重新设计（比如分片降低冲突）。
- Redis 单线程，为什么还会有竞态？——单命令原子，但 GET+SET 是两条命令；redis 单线程保证的是命令级串行，不保证客户端「读-改-写」序列原子。
- 锁过期但业务没执行完怎么办？——watchdog 续期 / 扩大 TTL / fencing token / 让业务幂等；见 2.15。
- 为什么面试官说「线上不常见」？——高并发系统读路径必须无锁扩展，锁只出现在写关键区；审批流程类低频场景才到处加锁。

### 2.14 百度一面·问36~38：全局字段放小表还是大表？如何看待面试官点评？

**面试官原话（转写，压缩）**
> 问36：这个字段可能在某张表里。你有两种选择：单独建一张只有一两个字段的表来存这个全局变量；或者在大表的很多字段里放一个「它是不是主」的字段。你倾向于哪种？
> 问37：原因呢？——你答：因为我只要记住谁是主就行了，没必要给其他子 Reactor 也加字段；另外放一起有点浪费。
> 问38（面试官点评）：如果你在读的时候就给这条数据加锁，线上其实会大量地读某条数据……频繁加锁会对某些连接的时延有损耗。你这个方法可行，但线上不太常见，需要根据实际情况调整。

**状态：36~37 ✅（选小表正确）；38 ⚠️（被点出读路径加锁的代价，需要复盘）。**

**可直接背的参考回答（表结构部分）**
> 我倾向于**单独的小表（或者 Redis 里的单 key）**，原因有四层：
> ①**语义和锁粒度**：这个字段是「全局唯一状态」，跟业务大表里的用户属性没有关系。放在单独一行，锁的范围就是这一行，更新它不会影响大表单行上的其他业务字段，也不会和大表的更新互相争行锁；反之，大表里更新一个字段会锁住整行（InnoDB 行锁），把热点的写和用户数据的写混在一起。
> ②**访问模式**：这类状态是读多写少的「协调数据」，独立出来后可以缓存、可以做 CAS/唯一约束，甚至换成 Redis/etcd，未来替换存储不影响业务表。
> ③**表体积和查询成本**：大表可能几千万行、索引多，任何一次针对它的查询/更新都要走索引和 buffer pool；小表只有一行，基本常驻内存。
> ④**扩展性**：以后要加 leader 选举的附加信息（任期、健康时间、fencing token），小表加字段干净，大表加字段代价大。
> 唯一要接受的代价是多一次关联/查询，以及多一张表的管理成本——和它带来的隔离与并发优势相比是值得的。
> 至于「读时加锁」的问题，面试官说得对：线上读远多于写，如果把读也放进锁里，读并发就被串行化了，20ms 的跨地域访问会直接体现在时延上。正确做法是**读不加锁、写做 CAS/原子操作**（见上一题），或者干脆把「谁是主」放进 Redis，用 `SET NX` 一步选主。

**技术要点拆解**
- InnoDB 行锁是锁索引记录实现的；大表里更新一行会影响该行的其他更新（行锁互斥），热点行还会引发锁等待；小表把「协调状态」隔离成独立行/独立存储。
- 小表的缺点：join 成本、一致性约束（外键/事务）、多一次网络往返；如果这个字段本来是「实体的一部分」且写不频繁、读不密集，放大表也合理——**关键是访问模式，而不是表的大小**。
- 高频读的优化顺序：缓存 → 无锁读 → CAS 写 → 悲观锁写（最后选择）。
- 面试官点评本质：**悲观锁不能放在读路径上**；这也是分布式锁使用的一条铁律。

**当前项目实现对照**
- 「谁是主」在本项目里对应「哪个 ChatServer 是用户的主节点」：`uip_<uid>` 用 Redis 单 key 承载，没有放进用户大表，天然符合「小表/独立存储」原则；更新走「锁 + 校验 + 写」，读走 GET。
- 连接数状态 `logincount` 也是独立 hash，不放用户表。
- 对比：`utoken_` 曾经在 StatusServer 内存里（day17），改成 Redis 后跨实例一致——说明这类状态独立存储、集中访问是正确方向。
- 唯一要改的是：登录互斥的**读判断也在锁里**（`LogicSystem.cpp:198-246`），可以在面试里主动说「第二季会把读判断改成 CAS/版本号，锁只保护写」。

**差距与改进建议**
1. 背熟「小地表的四个理由 + 一个代价」，并会说「关键看访问模式」。
2. 把面试官点评转化为主动回答：「如果重来一次，我会用 `SET NX`/版本号 CAS 取代读时加锁，读路径保持无锁。」
3. 项目里若有类似的「全局状态」，统一按「独立 key/表 + 无锁读 + 原子写」改造。

**追问预判**
- 小表和大表的一致性怎么保证？——同一事务里更新，或用 Redis 单 key 承载；避免两处写。
- 小表放在 Redis 还是 MySQL？——高频协调放 Redis（快、TTL、原子命令），需要持久和审计放 MySQL。
- 如果公司规范不允许多建表？——用独立行 + 唯一约束/专用列，或独立 Redis key；核心是隔离热点。
- 版本号 CAS 会不会有 ABA 问题？——单调递增的版本号/时间戳，不用值本身比较。

### 2.15 专题速查：Redis 高可用、持久化、缓存与锁（面试前 10 分钟过一遍）

> 本节把前面各题的技术点压缩成速查卡，防止紧张时答漏。项目对照见各题末尾。

#### 2.15.1 主从复制（全量/增量）

1. 从节点 `REPLICAOF host port` 发起同步，`PSYNC` 协商。
2. 首次/backlog 不足 → 全量：master `BGSAVE` 生成 RDB + 复制缓冲区；从节点清库加载；补发 buffer 增量。
3. 断线重连 → `PSYNC replid offset`：offset 在 `repl_backlog`（默认 1MB 环形）内则 `+CONTINUE` 增量，否则退化全量。
4. 默认**异步复制**：主挂可能丢最后一段写；`WAIT`、`min-replicas-to-write` 可增强，但增延迟。
5. 读写分离：复制延迟 `master_repl_offset - slave_repl_offset`；关键读（token/锁）走主，缓存类读可从。

#### 2.15.2 哨兵选主

1. Sentinel ≥3 台（奇数），监控主从 + 彼此。
2. 主观下线 SDOWN（`down-after-milliseconds` 无响应）→ 询问其他哨兵，达 quorum → 客观下线 ODOWN。
3. leader 哨兵选举（Raft 风格、epoch、多数派）执行 failover。
4. 选从优先级：`replica-priority` → 复制 offset（数据最新）→ runid 字典序；提升为新主，其他从 `REPLICAOF` 新主。
5. 客户端通过哨兵询问主地址（`SENTINEL get-master-addr-by-name`）或订阅 `+switch-master`；客户端库要支持（hiredis 需自研/换库）。
6. 局限：切换窗口秒级~十几秒；异步复制丢数据窗口；不分片。

#### 2.15.3 Cluster（16384 slot / MOVED / ASK）

1. `slot = CRC16(key) mod 16384`；槽分配至 master，master 可带从。
2. 16384 的由来：心跳/gossip 位图 2KB；设计规模 ≤1000 节点；足够均匀。
3. `MOVED`：槽永久迁移，客户端更新本地映射；`ASK`：迁移中的临时重定向，先发 `ASKING`，不更新缓存。
4. 多 key 操作需同槽，用 hash tag `{uid}`。
5. 需要多数主节点在线才能服务；`cluster-require-full-coverage=yes`（默认）时任一槽无归属则全集群拒绝服务。
6. `cluster-node-timeout` 决定故障检测（默认 15s）；故障转移需要从节点 + 多数派投票。

#### 2.15.4 持久化（RDB / AOF / everysec）

1. RDB：快照、恢复快、文件小；丢快照间隔数据；fork+COW 有内存和延迟成本。
2. AOF：`appendfsync always/everysec/no`；everysec 最多丢 1s，默认；文件大、恢复慢，需 `BGREWRITEAOF` 压缩。
3. 混合持久化（4.0+）：AOF 重写时 RDB 头 + 增量 AOF；恢复快、丢得少，生产推荐。
4. 恢复：重启加载 AOF（优先）或 RDB；集群先恢复拓扑（nodes.conf）再校验槽；文件损坏用 `redis-check-aof --fix` / `redis-check-rdb`。
5. 备份 + 异地 + 演练；`待核实` 本项目是否开启持久化。

#### 2.15.5 缓存三件套

1. 穿透（数据不存在）：空值缓存（短 TTL）+ 布隆过滤器 + 参数校验 + 限流。
2. 击穿（单个热 key 过期）：互斥锁/单飞重建 + 逻辑过期 + 永不过期后台刷新。
3. 雪崩（大批过期/整体宕机）：TTL 随机抖动 + 多级缓存 + 限流熔断降级 + 高可用 + 预热。

#### 2.15.6 热点 key

1. 探测：`--hotkeys`（LFU）、`OBJECT FREQ`、`MONITOR`（慎用）、代理层统计、业务埋点、slowlog。
2. 解决：本地缓存、key 打散、多级缓存、读写分离/副本、限流降级、大 key 拆桶。
3. 读热点靠副本/缓存，写热点靠打散/异步；本项目 `lockcount` 热点的去锁优化是现成案例。

#### 2.15.7 登录态强依赖的降级

1. 问题：可用性相乘 + 故障扩散；入口组件不能强依赖缓存。
2. 解法：自包含 token（JWT/HMAC）→ 本地缓存 → MySQL 兜底（限流/单飞/熔断）→ 网关限流 → Redis 高可用。
3. 取舍：登录可用性 > 严格单端互斥；降级窗口弱一致，恢复后用 `usession_` 收敛。
4. 演练：停 Redis 验证降级路径，而不是只写文档。

#### 2.15.8 分布式锁正确姿势

1. 加锁：`SET key uuid NX PX ttl`（单命令原子）；不要 `SETNX + EXPIRE` 两步。
2. 释放：Lua 校验 value 再删，防止误删别人的锁。
3. 续期：业务可能超 TTL 时用 watchdog（Redisson 思路：后台定时续期）；项目里 `LOCK_TIME_OUT=10s` 且无 watchdog，业务要短。
4. 失败重试：自旋 + 退避 + 获取超时（项目 `ACQUIRE_TIME_OUT=5s`）；拿不到锁要有降级（拒绝/排队）。
5. fencing token：防「锁过期后旧持有者仍在写」；强一致场景用 etcd/ZK 或 DB 唯一约束兜底。
6. Redlock 争议：多节点多数派加锁依赖时钟/网络假设，Kleppmann 质疑其安全性，antirez 反驳；结论——要求强互斥时别只靠 Redis 单实例锁，加 fencing 或换协调系统。
7. 锁粒度：按用户/资源分 key，避免全局锁；能用原子命令/数据模型消除锁就不加锁（项目 `lockcount` 的优化）。

#### 2.15.9 竞态的正确解法（百度一面复盘）

1. 读时加锁 = 悲观并发控制：正确但把读也串行化，跨地域 RTT 放大，吞吐差——面试官点评的核心。
2. 写时 CAS/乐观锁：读不加锁，写时比较版本（Lua / WATCH+MULTI / SQL 条件更新），冲突重试；读多写少首选。
3. 原子写原语：`SET NX` 选主、`INCR` 计数，一步消除「先读后写」。
4. 协调系统：etcd/ZK 租约 + revision + watch，天然选主且有 fencing 语义。
5. 金句：「锁保护写，不保护读；判断放进写操作里，读路径才能扩展。」
