## 2. 关键发现（面试前必读）

### 2.1 代码分支与面试口径不一致（最高优先级）
- 你在面试中描述的**负载均衡调度、资源服务、断点续传、SQLite 待办/outbox、2s/6s 节点租约**等实现，主要存在于 `origin/Season_2` 分支；**当前工作区是 `master`**，其中不少逻辑缺失或被注释（例如 StatusServer 的最小连接数选择被注释）。
- 影响：如果面试官要求看代码/共享屏幕，master 工作区会"货不对板"。
- 建议：面试前 `git switch Season_2`（或新开工作树）熟悉代码；若面试时说"当前分支"，先统一口径（设计过≠线上跑过），并准备解释分支差异。

### 2.2 术语与口径纠正
- **"一次性语义 / exactly-once"**：不要再说严格恰好一次。正确口径：**At-least-once 投递 + 幂等去重 = 业务上的"恰好一次"效果**。讯飞一面 Q8 当时的答法（哈希记录 UID）属于幂等思路，但表述不准确。
- **消息顺序**："不丢不重不乱序"中的"不乱序"实际保证的是**每会话内按序号有序**，不是全局有序；多端/群聊跨端显示顺序需要能解释清楚。
- **多端互斥**：项目实现的是**账号级全端互斥**（后登录踢掉先登录），不是微信式"同端互斥、异端共存"。描述时要说"单端在线、账号级踢人"，并准备好"如何扩展为多端在线"的回答。

### 2.3 性能数据需要统一口径（数据真实性是失分重灾区）
- 面试中出现的口径：8000 在线（讯飞一/主管）、2 万连接选 8000 用户发 256B、P99<1000ms（网易）、**8.3 万 QPS、90 多微秒（虾皮）**。已核对：仓库两个分支（master / `origin/Season_2`）都没有这两项的原始记录；如果你本地另有记录请补充（待核实）。
- Season_2 已有可复现材料：单 ChatServer 3000 在线 / 60 msg/s / 10min、**P99≈783ms** 通过；5000 档因 **MySQL 死锁**失败。与"8.3 万 QPS / 90µs"差距极大，必须提前想好解释（不同口径/不同链路）或直接改用有证据的数据。
- 建议统一格式：**环境（机器/连接数/报文大小/客户端工具）+ 指标定义（端到端 or 服务端处理；QPS 统计窗口；P50/P99；错误率）+ 逐步加压找拐点 + 瓶颈与优化对比**。

### 2.5 面试声称 vs 实际实现（说之前想清楚"实现了没有"）
- ✅ 有实现（`origin/Season_2`，均有代码）：资源服务、分片续传（offset+分片 SHA-256+整文件 SHA-256+幂等规则）、节点租约（2s 续写/6s 过期，`ChatServer.cpp`+`ChatServerRegistry.h`）、最小负载（连接数）调度+并列轮询（`StatusServiceImpl.cpp:110-150`）、消息落库+唯一键幂等（`uk_chat_messages_client` + 事务内查重）、多端踢人、心跳、连接四状态状态机（`common/include/SessionLifecycle.h`：Open/Draining/Closing/Closed + close 投递 IO 线程）、按 uid 分片业务线程池（`LogicWorkers`）、客户端断线重连（2s/4s/8s）。
- ⚠️ 分支差异（master 旧版）：负载均衡被注释（`StatusServiceImpl.cpp:61-89`）、`Close()` 为 mutex+直连 close、业务仅单工作线程、客户端粘包 bug、无自动重连、拿锁失败仍继续。面试讲 Season_2 前先切分支，否则"货不对板"。
- ❌ 两分支都未实现：消息撤回、未读数、已读回执、假死节点主动摘除、限流/降级/熔断、秒传、5s/500ms 定时轮询补拉（两处面经口径互相矛盾）。离线补拉：Season_2 用 `user_events` 事件序号增量同步，不是"离线消息表"，也不是 500ms 轮询。

### 2.6 你的优势区（保持并打磨）
- 断点续传整体讲对了（需修正两处口径：进度真值在资源服务磁盘 `.part`，下载是客户端按 offset 拉取而非服务端推送）。
- 消息幂等：Season_2 用 `(sender_user_id, client_message_id)` 唯一键 + 事务内先查后插；面试里说的"一次性语义/哈希记录 UID"只是思路，别再说成 `ON DUPLICATE KEY UPDATE`。
- 连接生命周期与四状态状态机（Season_2 `SessionLifecycle` 已实现：Open/Draining/Closing/Closed + close 投递 IO 线程；master 仍是 mutex+直连 close）。
- 节点租约 2s/6s + 最小负载调度 + 并列轮询（Season_2 有实现支撑）。
