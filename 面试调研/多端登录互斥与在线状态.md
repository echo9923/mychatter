### 问19：IM 能多端登录吗？

**面试官原话（转写）**
> "那我们这个即时通信系统它能做到多端登录吗？比如说你手像我们现在微信什么啊？"

**你当时的回答（压缩）**
> "这个没有 PC 和手机啊，现在就是设计的就是这个单端的登录，然后我们还为单端登录就是设计了一套机制，我们就是多端互斥，保证只有一方能登。"

**状态：⚠️ 半对。** 说清了"任意第二个端登录会踢掉旧的"，但"多端互斥"是个自造词，和微信的实际模型（手机/PC 同时在线，同类型端互踢）不一致。面试官顺着问了问20，没有深挖；但如果面试官接着问"那微信手机 PC 同时在线你怎么不支持"，当时的回答会显得对产品模型理解不深。

**考点分析**
1. 是否分得清"端（platform）"和"账号（uid）"：多端登录的问题本质是"按什么粒度维护在线会话"。
2. 是否知道多端同时在线的系统成本：在线状态一份变多份、消息扇出、每端游标、跨端已读同步。
3. 能不能把第一版的"全端互斥"讲成主动取舍，而不是能力缺失。

**参考回答（可直接背）**
> 我们目前实现的是**账号级全端互斥**：同一时刻一个账号只允许一个在线会话，第二个端登录会把上一个端的连接踢掉。
>
> 为什么第一版这么做？因为在线状态只有一份：Redis 里 uid 对应一个 server 名和一个 session id，消息推送、心跳清理、离线兜底、退出清理全部围绕这一份状态，容易保证一致性。
>
> 微信那种是**同端互斥、异端共存**：手机和 PC 可以同时在线，但两个手机登录会互踢。要支持它，在线状态要按"uid + 端类型"存成一组，比如 Redis 里用 Hash 或一组 key，每个端各自记录 server/session_id；发消息时查这个 uid 的所有在线端逐端投递；已读和拉取进度也按端各维护一份游标。我们第一版没有群聊和多端同步，所以选了成本最低、语义最清晰的全端互斥；后续要扩展，是在这层数据结构上加维度，不是推翻重做。

**技术要点拆解**

| 方案 | 在线状态粒度 | 踢人规则 | 消息投递 | 成本 |
|---|---|---|---|---|
| 全端互斥（当前） | uid → 1 个会话 | 新端踢旧端 | 发给唯一在线端 | 最低，1 把 uid 锁 |
| 同端互斥、异端共存（微信） | uid+platform → 每端 1 个会话 | 只踢同 platform | 扇出给所有端 | 中，锁按 uid+platform；消息多端同步 |
| 完全多端在线 | uid → N 个会话 | 只按策略踢 | 扇出 + 每端游标 + 离线补拉 | 高，需收件箱/游标表 |

- 互斥粒度不是技术限制，而是产品语义选择；技术实现永远可以按"uid+端"做 key。
- 多端在线后，"消息可靠"的含义从"至少一个端收到"变成"每个端都能追上进度"，必须靠权威存储 + 每端游标，而不能只靠在线推送（见 [消息存储与分页拉取](消息存储与分页拉取.md)）。

**当前项目实现对照**
- `server/ChatServer/src/LogicSystem.cpp::LoginHandler`（112–249 行）：在线态是 `uip_{uid}`（值=server 名，`USERIPPREFIX`）和 `usession_{uid}`（值=session_id，`USER_SESSION_PREFIX`），均为单值；`server/ChatServer/include/const.h`（75–83 行）定义前缀。任何新登录都会覆盖并踢人 → 属于账号级全端互斥。
- `client/llfcchat/src/mainwindow.cpp::SlotOffline`（116–121 行）：被踢端弹"同账号异地登录，该终端下线！"后断开连接回到登录页。
- day33/day34 文档标题与逻辑即"同账号异地登录踢掉旧连接"，与代码一致。

**差距与改进建议**
- 面试口径统一为"**账号级单端在线（全端互斥）**"，把"多端互斥"从词库里删掉。
- 想升级亮点：把 `uip_/usession_` 改成 `online:{uid}` Hash（field=platform，value=server|session_id|ts），锁 key 变 `lock_{uid}_{platform}`；登录只踢同端，推送遍历所有端。工作量 1–2 天，收益是能正面回答"微信式多端"。

**追问预判**
1. "为什么不做多端同时在线？" → 第一版范围取舍 + 多端扇出与游标成本；不是做不到。
2. "多端在线时消息怎么保证每端都能看到？" → 权威存储 + 每端游标 + 上线/切端补拉，推送只是实时加速。
3. "两个手机同时登录踢哪个？" → 同端互斥、后登录者胜，踢旧留新。
4. "iPad、网页端算哪个端？" → platform 枚举要提前定义清楚，否则会出现两个 mobile 互相踢。

### 问20：登录互斥是怎么实现的？

**面试官原话（转写）**
> "现在是这个登录是怎么实现的啊？"

**你当时的回答（压缩）**
> Redis 里维护在线状态，记录用户在哪个 chat server、对应 TCP connection ID；新端登录后先加分布式锁，读 Redis：如果旧连接在本机就直接 close，在别的机器就发 gRPC 让对方 close；然后更新 Redis、释放锁；所以"最后登录的那个"真正拿到连接。

**状态：✅ 可以（有细节缺口）。** 流程完整，方向正确；但缺三个可被追问的点：① 锁的正确用法（SET NX EX + 唯一 value + Lua 释放）；② 各清理路径（读失败/退出/心跳超时）也要按同一把锁 + session_id 比对，避免误删新登录状态；③ 跨服踢人失败怎么办。

**考点分析**
1. 分布式互斥的经典三件套：集中式状态（Redis）、分布式锁、跨节点通知（gRPC）。
2. 是否理解"必须把所有会改在线态的操作都串行化"，而不只是登录入口。
3. 是否知道"比对 session id 再删"这种防误删模式（等价于 CAS）。

**参考回答（可直接背）**
> 每个用户在 Redis 里有一份在线状态，记录两样东西：他在哪台 chat server 上（`uip_{uid}`）以及对应的连接 ID（`usession_{uid}`，用的是 session 的 UUID，不是裸 fd，因为 fd 会被复用）。
>
> 登录流程是这样的：ChatServer 校验 token 通过后，先以 uid 为粒度拿一把分布式锁——Redis `SET lock_{uid} <UUID> NX PX 10000`，拿不到就在 5 秒内自旋重试；拿到锁之后读在线状态——
> - 如果旧连接在本机，直接在本地找到旧 session，给它发下线通知并清理；
> - 如果旧连接在别的 chat server，就 gRPC 调对端的 `NotifyKickUser`，让对方把旧 session 关掉；
>
> 然后把自己这台 server 名和新的 session id 写回 Redis——**新会话胜出**，最后用 Lua 脚本比对 UUID 释放锁。
>
> 关键是所有会改这份状态的地方都走同一把 uid 锁：登录、主动退出、读写异常清理、心跳超时清理。清理时必须先读 Redis 里的 session_id，和自己的不一致就说明账号已经在别处重新登录，直接退出、绝不能把新状态删掉。这样无论登录、退出还是跨服清理，对同一个 uid 都是串行的。

**技术要点拆解**
- 锁的 key 基于 `LOCK_PREFIX`（`const.h`，值 `lock_`；`DistLock` 内部还会再拼 `lock:`，实际 key 形如 `lock:lock_<uid>`），临界区 = "读在线态 → 踢旧 → 写在线态"。
- 踢旧用同一个入口：本机 `NotifyOffline + ClearSession`，跨机 `NotifyKickUser(uid)`（day34 新增 proto 服务）。
- 清理路径的"防误删"：`usession_{uid} == 自己的 session_id` 才删；否则说明账号已异地登录（`DealExceptionSession`、`AsyncReadBody` 错误分支）。
- 锁的持有时长：正常几十毫秒（几次 Redis + 最多一次 gRPC），10 秒 TTL 足够；但 gRPC 必须带 deadline，否则会突破 TTL（见问23）。

**当前项目实现对照**
- `server/ChatServer/src/LogicSystem.cpp::LoginHandler`（master 行号 112–249）：token 校验（128–141 行，直接读 Redis `utoken_{uid}`）→ 拿锁（198–203 行）→ 读 `uip_` 判断本机/异机（206–234 行）→ 本机 `NotifyOffline + ClearSession`，异机 `NotifyKickUser`（230–232 行）→ 写 `uip_/usession_`、`UserMgr::SetUserSession`（236–244 行）。Season_2 结构相同但行号不同（锁 393–402、踢人 404–422、绑定 424–435），且拿锁失败已 fail closed。
- `CServer::ClearSession`（41–53 行）：按 session_id 移除并通过 `UserMgr::RmvUserSession` 解绑 uid，后者比对 session_id 不同则不动（`UserMgr.cpp` 27–44 行）。
- `CSession::DealExceptionSession`（287–316 行）：拿锁 → 比对 Redis session_id → 一致才删 `usession_/uip_`。
- 文档：day33（单服踢人）、day34（跨服踢人）与代码一致。

**差距与改进建议**
- `LogicSystem.cpp:232`（master）/ `LogicSystem.cpp:420`（Season_2）调用 `NotifyKickUser` **没有接收返回值**；对端失败/超时无人知晓。建议：要么检查 `rsp.error()` 并重试/记录，要么不依赖它——把"新状态写 Redis + 旧连接自检"作为最终一致兜底（见 2.4）。
- 锁的获取失败（`identifier.empty()`）时 **master 代码没有让登录失败，而是继续往下走**（master 199 行拿锁失败仍会执行踢人和写状态），这是隐患：拿不到锁意味着另一个登录流程正在改状态。`origin/Season_2` 已修复为 fail closed（`LogicSystem.cpp:398-402` 直接返回 RPCFailed）。建议 master 也改成拿不到锁直接返回错误码让客户端重试。
- 建议补"旧连接自检"：旧连接在心跳应答/发送前比对 `usession_{uid}` 是否还是自己，不是就优雅下线；这样即使 gRPC 踢人丢了，最终也会收敛（见 2.4）。

**追问预判**
1. "锁加在哪一段？为什么登录要加锁？" → 只锁"读在线态→踢旧→写在线态"这段临界区；因为两个并发登录会互相覆盖、双写。
2. "跨服踢人的 gRPC 失败了怎么办？" → 检查返回值 + 重试 + 兜底自检（见 2.4）。
3. "旧连接自己读/写异常断开，会不会把新登录的状态删了？" → 不会，删之前比对 `usession_` 里的 session_id。
4. "本机踢人和跨服踢人为什么要分开？" → 本机能直接找到内存里的 session 发通知；跨服只能通过 gRPC 让对方在本机执行同样的动作。

### 问23：分布式锁因网络/Redis 抖动没释放，用户一直登不上怎么办？

**面试官原话（转写）**
> "然后我刚刚看到你提到那个用分布式锁来处理多端互斥的那个问题，那比如说加锁的时候出现这个网络或者 Redis 抖动，导致这个锁加上了之后没释放，会不会导致这个用户一直登不上？嗯，你这边是怎么保证他的这个兜底？"

**你当时的回答（压缩）**
> "呃，我们这个加锁的话，我们也是这个锁也是有过期时间的啊。我们最多持有这个锁，我们持有个 10 秒我们就自动的释放。"

**状态：⚠️ 半对。** 过期释放是正确且必要的兜底，但只答了一半。满分答案还要覆盖：锁过期但业务没执行完怎么办（续期 / 缩短临界区 / fencing）、释放时不能误删别人的锁、以及锁获取失败后的用户重试体验。

**考点分析**
1. 死锁兜底：TTL 自动过期是第一层。
2. 锁租约与业务时长的关系：TTL 必须大于临界区最长耗时，否则出现"锁提前释放、两个持有者"。
3. 误删他人锁：释放必须 CAS（value 比对）。
4. 故障可观测性：锁竞争/超时要有指标和重试体验，而不是让用户无限等待。

**参考回答（可直接背）**
> 兜底分三层。
>
> 第一层是锁自带过期时间：`SET key uuid NX PX 10000`，即使进程崩溃或网络抖动导致没能主动释放，最多 10 秒后锁会自动过期，用户不会永久登不上；客户端侧拿锁超时（我们设的是 5 秒）也会返回失败让用户重试，而不是无限卡住。
>
> 第二层是防止"锁过期但业务没做完"。正常临界区只有几次 Redis 操作，几十毫秒，10 秒是数量级的余量；但有两个风险点要堵住：跨服踢人的 gRPC 必须设 deadline，比如 1–2 秒，不能让一次网络抖动把临界区拖到 10 秒以上；如果业务真的可能超时，就用"看门狗"给锁续期——后台线程每隔 TTL/3 检查任务还在跑就 `PEXPIRE` 续期，任务结束再主动释放，这是 Redisson 的做法。更彻底的是 fencing token：每次拿锁拿到一个单调递增的令牌，写 Redis 时带上令牌，只允许更大的令牌覆盖，这样即使旧持有者醒来也写不进去。
>
> 第三层是释放只能删自己的锁：用 Lua 脚本比对 value 里的 UUID 一致才 DEL，避免"A 的锁过期后 B 拿到锁，A 处理完把 B 的锁删了"。
>
> 另外拿锁失败要快速失败返回给用户重试，并打点监控锁的等待时间和超时率，因为这通常说明有慢操作或者热点 uid 竞争。

**技术要点拆解**
- `SET NX PX`：加锁原子；value 用 UUID 标识持有者（day32 已实现，代码里用的是 `SET NX EX 秒`）。
- Lua 释放：GET 比对 + DEL 原子执行（day32/day33 已实现）。
- 续期（watchdog）：仅在"临界区可能长于 TTL"时需要；简单业务优先缩临界区。
- Fencing token：用单调递增版本号做写保护，解决"过期锁的旧持有者还在写"。
- 权衡：TTL 太长 → 崩溃后用户等太久；太短 → 提前过期风险。经验值 TTL ≈ 10 × P99 临界区，且 ≤ 用户可接受的登录失败等待。

**当前项目实现对照**
- `server/ChatServer/src/DistLock.cpp`：`acquireLock` 用 `SET %s %s NX EX %d`（27–49 行）；`releaseLock` 用 Lua 比对 value 再 DEL（52–73 行）。
- `const.h`：`LOCK_TIME_OUT 10`、`ACQUIRE_TIME_OUT 5`（86–88 行），与面试说的"最多持有 10 秒"一致。
- 没有续期机制、没有 fencing token；master 的 `LoginHandler` 拿锁失败（`identifier.empty()`）后仍继续执行（LogicSystem.cpp 198–204 行附近）——这是 master 的真实缺口；`origin/Season_2` 已修复为 fail closed。
- day41 讲的是 **MySQL 间隙锁/插入意向锁**造成的死锁（私聊表、好友表），与分布式锁不是一回事，面试时注意区分：一个在 Redis 层，一个在 InnoDB 层。day35 讲的是"分布式锁↔线程锁"嵌套顺序死锁（已在代码中按"先分布式锁→后线程锁"统一顺序规避）。

**差距与改进建议**
- 拿锁失败应直接返回错误（如 `ErrorCodes::RPCFailed`/新增"操作繁忙"），让客户端稍后重试；现在继续执行等于锁没起作用。
- 给 `ChatGrpcClient::NotifyKickUser` 补返回值检查 + 失败重试（Season_2 已有 3s deadline；投递类 RPC 已有 deadline+3 次重试，踢人 RPC 还没有重试），保证临界区上界可控。
- 有精力再实现 watchdog 续期或 fencing token 做亮点。

**追问预判**
1. "为什么过期时间设 10 秒，不是 1 秒？" → 临界区正常几十毫秒，10 秒是安全余量；太短会在 Redis 抖动时误放锁。
2. "锁过期了但 A 还在写怎么办？" → 续期 / fencing token / 缩短临界区；至少写状态带版本号或时间戳做最后防线。
3. "锁被 Redis 主从切换搞丢怎么办？" → 见 [Redis使用与高可用设计](Redis使用与高可用设计.md)；可用 RedLock 或"锁 + 数据版本校验"降级。
4. "为什么不用数据库唯一键代替分布式锁？" → 在线态是 Redis 数据，不是行记录；也可以讨论 `INSERT ... ON DUPLICATE KEY` / `SELECT FOR UPDATE` 的替代方案，但跨服踢人还是要分布式协调。

### 问25（同场延伸，口径参考）：高并发登录怎么扛？

虽然不在本文件范围内，但和登录/在线状态强相关，这里只记一句可复用口径，详见 [性能压测与容量扩展](性能压测与容量扩展.md)：
> 网关自身有 IO 线程池 + 业务线程池，登录查库在业务线程池里排队，先把 MySQL 保护住；再往上就是热点用户信息（账号/密码/token）前置到 Redis，查不到再回落 MySQL。多端互斥的锁要和这些一起考虑：锁只保护状态变更，不覆盖密码校验、用户信息加载这些可以并行/缓存的部分。

## 2.5 综合专题一：单端/多端互斥的取舍（必须能讲明白）

| 方案 | Redis 在线态 | 锁粒度 | 踢人 | 消息投递 | 典型产品 |
|---|---|---|---|---|---|
| 全端互斥（当前实现） | `uip_{uid}` + `usession_{uid}` 单值 | `lock_{uid}` | 任意新端踢旧端 | 单端 | 早期 IM、需要"账号单在线"的场景 |
| 同端互斥、异端共存（微信式） | `online:{uid}` Hash：platform → server/session | `lock_{uid}_{platform}` | 同端互踢，异端共存 | 扇出到所有端 + 每端游标 | 微信/QQ |
| 完全多端在线 | 每设备一条会话记录 | 按设备/会话 | 可配置策略 | 收件箱模型 + 每端游标 | Slack/企业 IM |

**话术**："互斥粒度是产品语义，不是技术限制；实现差别只在在线态存一份还是存一组、锁按 uid 还是 uid+端、推送是单播还是扇出。"

## 2.6 综合专题二：登录态数据结构设计

当前实现（代码核实）：

| Key | 值 | 写入时机 | 清理时机 | 备注 |
|---|---|---|---|---|
| `utoken_{uid}` | StatusServer 生成的 UUID token | GateServer 调 `GetChatServer` 时写入 | master 无过期/删除逻辑；Season_2 为 `SetEx 86400`（到期自动消失，重登覆盖） | ChatServer 登录时直接读它校验 |
| `uip_{uid}` | chat server 名（如 chatserver1） | 登录成功后 | 退出/异常清理（比对 session） | 无 TTL（`RedisMgr::Set` 是普通 SET） |
| `usession_{uid}` | session_id（UUID） | 登录成功后 | 同上 | 用来防误删 |
| `logincount`（Hash） | server 名 → 在线连接数 | 心跳定时器每 60s 重写 | ChatServer 退出时 HDel | master 负载均衡用；`StatusServer::getChatServer` 目前把读 count 的逻辑注释掉了（仅返回第一个 server，便于测试）。Season_2 改为每节点 `chatserver:lease:<name>`（2s 续期/6s 过期）由调度读取 |

**设计要点（可背）**
1. 连接标识必须用**会话 UUID**，不能用 fd：fd 关闭后会被复用，跨节点比对的语义会错。
2. 状态要能区分"谁写的"（server + session）和"什么时候写的"（时间戳），方便兜底扫描。
3. 生产环境应带 TTL 或版本：例如 `uip_` 设为 90s TTL 并由心跳续期，或写一个 `last_active_ts` 字段，防止 chat server 崩溃留下僵尸在线态。
4. token 要设过期：master 的 `utoken_` 不过期（已核实），Season_2 已改为 86400s；建议新登录时轮换 token。

## 2.7 综合专题三：分布式锁的正确实现

**标准模板（背下来）**
```text
加锁:   SET resource_name my_random_value NX PX 30000
解锁:   Lua: if get(key)==value then del(key) else return 0
续期:   后台 watchdog, 每 TTL/3 检查任务存活 → PEXPIRE key TTL
写保护: 若临界区写外部存储, 写入携带 fencing token(单调递增), 只允许更大 token 覆盖
```

**"10 秒够不够"的判断方法**
- 临界区 = 2~4 次 Redis 往返（<1ms 本地、跨机房 <10ms）+ 至多 1 次跨服 gRPC。
- 结论：只要 gRPC 带 1~2s deadline，10s 有数量级余量；不带 deadline 时，TCP 重传可能让单次调用卡到几十秒，10s 反而会提前过期 → 双写。
- 升级条件：临界区 P99 × 10 > 用户可接受等待，或临界区含不可控外部调用 → 上 watchdog + fencing。

**当前实现差距（两分支已核对）**
- ✅ `SET NX EX` + UUID + Lua 释放（两分支一致）。
- master ❌ 无 gRPC deadline（`ChatGrpcClient.cpp` 未调用 `set_deadline`）；Season_2 ✅ 已加（`NotifyKickUser` 3s，`ChatGrpcClient.cpp:132`）。但**两分支都忽略调用返回值、都不重试**。
- master ❌ 拿锁失败仍继续业务（`LogicSystem.cpp:199`）；Season_2 ✅ 已 fail closed（`LogicSystem.cpp:398-402`）。
- ❌ 两分支都无续期/fencing。

## 2.8 综合专题四："后登录者胜"与"先到先得"的语义

- **先到先得**：第一个拿到锁并完成写状态的人赢；后来者的登录被拒绝或踢掉先来者？
- **后登录者胜（last-login-wins）**：新登录总是踢掉旧连接。当前实现即此语义，但严格说是"**先拿到锁的人先完成，后来者再进入并踢掉他**"——由于锁把流程串行化，最终状态等于"最后一个完成登录流程的人胜出"。
- 竞态窗口：A 拿锁 → A 的临界区超时（锁过期）→ B 拿锁 → A、B 都认为自己赢。解法：冻结 gRPC 时长、续期、fencing token、或写状态时用 CAS（比较旧值）。
- 面试话术："我们的语义是后登录者胜，靠 uid 锁把并发登录串行化；风险窗口只在锁提前过期时出现，所以要保证临界区时长远小于 TTL。"

## 2.9 综合专题五：gRPC 跨节点踢人失败的重试与最终一致

**问题**：`ChatGrpcClient::NotifyKickUser` 失败时 `LoginHandler` 不检查返回值、不重试，对端可能永远不知道该用户已异地登录（master 版 `ChatGrpcClient.cpp:177-204` 且无 deadline；Season_2 版 `ChatGrpcClient.cpp:122-137` 已加 3s deadline）。

**推荐的三层方案（可背）**
1. **同步确认（快）**：踢人 gRPC 带 deadline（1–2s），检查 `rsp.error()`；失败最多重试 1 次。注意重试要在锁临界区内控制时长。
2. **状态兜底（最终一致，关键）**：登录写 Redis 时以新会话为准；旧连接在**每次心跳应答/发送消息前**读取 `usession_{uid}` 和自己比对，不一致就自我下线。这样即使踢人消息完全丢失，旧连接也会在下一次心跳周期内被收敛（我们客户端 10s 一次心跳）。
3. **离线扫描（可选）**：各 ChatServer 定时任务扫描本机 `uid→session`，和 Redis `usession_` 比对，发现"自己不是最新"就清理。同时清理 redis 中指向已宕机 server 的僵尸状态（配合 TTL 更好）。

**幂等**：`NotifyKickUser` 按 uid + 最新 session_id 判断，重复收到通知时"已经不是本人"直接返回成功即可（当前实现查不到 session 直接返回 OK，天然幂等）。

**当前实现差距**
- master：无 deadline、无重试、无自检兜底；Season_2：已有 3s deadline（`ChatGrpcClient.cpp:132`），但调用方仍不检查返回值、不重试、无自检兜底；`usession_` 比对只在异常清理路径（`DealExceptionSession`）做了，正常心跳路径没做。
- 相关文档：[聊天服务集群与负载均衡](聊天服务集群与负载均衡.md)、[Redis使用与高可用设计](Redis使用与高可用设计.md)。

## 2.10 综合专题六：多端场景扩展（多端同时在线 + 每端游标）

如果要往微信式多端演进，改动清单：

1. **在线态**：`HSET online:{uid} {platform} "{server}|{session_id}|{ts}"`；登录只对 `lock_{uid}_{platform}` 加锁，踢同端。
2. **推送**：`HGETALL online:{uid}` 扇出；每端写一份"已推送到的最新 message_id"游标，失败端靠补拉。
3. **客户端**：每端登录时带 platform；本地 SQLite 按"用户+thread"存消息（当前客户端就是这么做的），多端之间用服务端权威存储对齐。
4. **游标/已读**：新增 `read_cursor(uid, platform, thread_id, last_read_msg_id)`；多端已读同步可选。
5. **互斥语义配置**：把"踢 or 共存"做成按端配置，而不是写死在代码里。

**面试收尾话术**："我们的第一版把在线状态压成一份，所以能做到 uid 级互斥和简单的可靠投递；如果我今天重新设计，会把在线状态设计成 uid+端的二维结构，让互斥粒度和消息扇出都能配置，这不会增加多少复杂度，但能给产品留下多端在线的空间。"

## 3. 小结与行动项

**最值得改的三件事（按性价比排序）**

1. **修死循环隐患 + 提高踢人可靠性（必做）**
   - master `LogicSystem.cpp::LoginHandler`：`acquireLock` 返回空时直接返回错误码，不再继续执行（Season_2 已 fail closed，见 398-402 行）。
   - `ChatGrpcClient::NotifyKickUser` 等 RPC 加 `context.set_deadline(now + 2s)`，并检查返回值；在 LoginHandler 里记录失败日志（Season_2 已给 `NotifyKickUser` 加 3s deadline，待补的是检查返回值 + 重试 + 失败日志）。
   - 关联文件：`server/ChatServer/src/LogicSystem.cpp`、`ChatGrpcClient.cpp`。

2. **给在线态加"自检兜底"（终局一致性）**
   - 在心跳处理（`LogicSystem::HeartBeatHandler` 或发送消息前）读取 `usession_{uid}`，和自己 session_id 不一致就 `NotifyOffline + Close`。
   - 这样跨服踢人丢失也能在 ≤1 个心跳周期（10s）内收敛；对应文档 [断点续传与文件消息](断点续传与文件消息.md) 里的"靠客户端重试兜底"是同一思路。

3. **在线态加 TTL / 版本号（防僵尸）**
   - `uip_/usession_` 目前是普通 SET 无 TTL；chat server 崩溃会留下僵尸在线态。
   - 方案：改 `SET ... EX 90` 并在心跳里续期；或在值里加时间戳，由兜底扫描清理。
