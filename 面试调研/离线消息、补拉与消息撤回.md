## 2. 逐题调研

### 2.1 科大讯飞一面 问5：游标补拉与"每 5 秒拉取"

**面试官原话（转写）**

> "如果已经选了一个聊天服务，聊天服务崩溃了，其中一个用户已发送消息，但聊天服务崩了，怎么处理？"

**当时的回答（压缩要点）**

- 所有聊天服务和用户消息都可靠存储在唯一的 MySQL 上；
- 情况 1：服务写 MySQL 过程中崩溃 → 没落库、不回 ACK → 客户端持续重传直到确认；
- 情况 2：已落库后服务崩溃 → 发送方已认为成功，接收方可能不知道；**接收方维护游标记录最新收到消息序号，如果到 36 而下一个是 38，缺 37 就向服务端补拉 37**；同时客户端**每 5 秒**主动拉取一次。状态：✅ 思路完整，"缺号补拉"是标准答案，比大多数候选人强。风险点：5 秒全量轮询不可辩护，见下。

**考点分析**

1. **崩溃一致性**：写库与回 ACK 的顺序（先落库后 ACK，ACK 丢了靠客户端重试）。
2. **消息序号的作用**：不只是排序，还是**完整性检测工具**（gap detection）。
3. **推 vs 拉**：面试官在引导你承认"纯推送不可靠、需要拉取兜底"。
4. **工程成本**：补拉频率、范围、优先级，是否会把服务端打爆。

**可直接背的参考回答（口语化）**

> 我把"接收方一定拿到消息"拆成两层保证：**推送负责快，拉取负责全**。
>
> 发送方到了服务端先落 MySQL，落库成功才回 ACK；ACK 丢了自己会重试，重试靠 `(sender_id, client_uuid)` 唯一键幂等，这条链路和聊天服务崩不崩没关系，因为权威副本在 MySQL，换个聊天节点照样能读。
>
> 接收方这边，每条消息有一个全局递增的 `message_id`（会话内也递增），客户端为每个会话维护一个"已连续收到的最大序号"游标。正常情况下在线推送会带着序号来；如果收到 38 而本地只连续到 36，说明 37 丢了，立即发一个补拉请求：`WHERE thread_id=? AND message_id > 36 ORDER BY message_id ASC LIMIT 100`，等服务端把 37、38 一起回过来。这里要注意两点：一是"连续"的判断——收到 38 先不要把它当已连续，要等 37 补上再推进游标；二是补拉是按会话的，不要全库扫。
>
> 兜底方面我不会做 5 秒全量轮询那种方案，成本太高。我会做成**事件通知 + 低频兜底**：服务端对离线用户维护待收事件（新消息、撤回、已读回执都算事件），用户上线后按会话游标拉；在线的用户，如果长时间没收到任何推送，再用心跳或低频同步（比如 30~60 秒，指数退避）把各会话的 `max_msg_id` 和本地游标比一次，只对"有差异的会话"发起增量拉取，而且单次拉取限条数限频率。这样 5 秒一轮的全量请求就降成了"心跳里带游标对账 + 按需拉取"。

**技术要点拆解**

- **不丢的边界**：服务端落库成功即"消息不丢"；下发失败只影响"实时性"，由接收方拉取补齐。这与 [消息可靠传输与幂等去重](./消息可靠传输与幂等去重.md) 的 ACK/重试是同一套模型。
- **游标要区分两个含义**：`max_continuous_msg_id`（连续无缺口）和 `max_received_msg_id`（见过的最大号）。gap 检测必须用前者推进；否则收到 38 就推进游标，37 永远不会再补。
- **补拉合并**：缺口区间可能是 `[37,38]`，也可能是"离线一周的 10 万条"；请求要带 `limit`，服务端返回后客户端继续按 `next_cursor` 追，且要做合并去重（按 `message_id` 主键）。
- **为什么不是"服务端持续重发直到 ACK"**：对方断网时发送方内存里会堆满重试任务，实际不可控；正确做法是"事件落库 + 上线拉取"（多益问32 的答案）。
- **每 5 秒 vs 500ms**：OPPO 问16 答的是 500ms，讯飞问5 答的是 5 秒——两次口径不一致，面试官若对比会质疑实现细节。统一说法：**按需拉取（收到不连续消息/点开会话/重连）+ 30~60 秒低频对账兜底**，不要报出两个精确却互相矛盾的轮询周期。

**当前项目实现对照**

- 项目**没有实现**游标补拉：客户端没有本地数据库（无 `QSqlDatabase`，见 [消息存储与分页拉取](./消息存储与分页拉取.md) 2.5），自然没有持久化游标；`ChatThreadData::_last_msg_id` 只存在内存（`client/llfcchat/include/userdata.h` L202+）。
- 项目**没有 5 秒/500ms 轮询**：客户端与网络保活相关的唯一定时器是 10 秒心跳 `ID_HEART_BEAT_REQ`（`client/llfcchat/src/chatdialog.cpp` L155-165；注册/验证码界面另有 UI 倒计时），服务端 20 秒判定超时（`CSession.cpp` L271-279，day35）。面经里说的轮询是思路描述，不是代码事实。
- 服务端 LoadChatMsg 的增量 SQL 方向正确（`message_id > cursor ASC`），但 `load_more/next_cursor` 逻辑缺失、`page_size=10`（见 [消息存储与分页拉取](./消息存储与分页拉取.md) 2.1），**补拉链路目前跑不通**。
- 崩溃后的消息可取回这一点在项目里部分成立：消息落 MySQL，任何 chat 节点都能查；但"接收方如何知道要补"没有实现。

**差距与改进建议**

1. 客户端补 SQLite + `thread_cursor(max_continuous_msg_id, last_read_msg_id)`；服务端修复 LoadChatMsg 后即可支撑"缺号补拉"。
2. 协议新增 `FetchMessages(thread_id, since_id, limit)`，响应带 `next_cursor/has_more`；与 [消息存储与分页拉取](./消息存储与分页拉取.md) 的 `LoadAfter` 合并实现。
3. 会话列表接口返回每个会话的 `max_msg_id`，客户端与本地游标比对，只拉有差异的会话——这就是零成本版"低频对账"。
4. 面试话术统一：不再说"每 5 秒拉一次"，改说"按需 + 低频对账"。

**追问预判**

- 问：怎么判断 37 是真丢了，而不是还在路上（乱序）？→ 答：TCP 内不会乱序，但跨节点/异步处理可能产生处理顺序差异；所以服务端给同一会话的消息**按落库顺序分配 message_id 并顺序推送**，客户端对"缺口"设置一个短等待窗口（如 1 秒），窗口内没等到再补拉，避免网络抖动误判。
- 问：补拉拉回来一堆重复怎么办？→ 答：`message_id` 主键 `INSERT OR IGNORE`，天然幂等；服务端返回时也可按 id 去重。
- 问：用户离线一周，几万条怎么补？→ 答：不要一次拉完；先拉每个会话的摘要（未读数 + 最新一条），点进会话再分页拉最近的；更早的历史按需加载，见 2.2 的洪峰防护。
- 问：多端都在线怎么补？→ 答：每端各自维护游标、各自补拉；已读等跨端状态通过服务端下发，见 2.6。

### 2.2 OPPO二面 问5：离线消息洪峰防护

**面试官原话（转写）**

> "那如果离线发，比如说我们这个用户一直没有上线，那你有另外一个用户给他发送了很大的量的消息，那在这个离线的消息拉取的流程中，如果用户刚上线瞬间的这个并发量特别大，一下子可能几千条的消息历史消息，你是怎么防止它不会把这个图标（注：转写原文如此，按上下文应指"系统/服务"）打坏呢？"

**当时的回答（压缩要点）**

- 客户端自己限流；分页拉取，每次最多 100 条，间隔一会儿再拉；
- 优先拉私聊消息，群聊等用户点进去再拉；
- 上线不拉全量，用户往上翻到当前最旧消息才继续向服务端拉。状态：⚠️ 方向正确，但防护几乎全压在客户端，缺少服务端侧的回答；面试官问"怎么防止把系统打坏"，重点是服务端与存储侧的防护。

**考点分析**

面试官考察的是**系统性思维**：

- 洪峰发生的位置：客户端 UI 卡顿、服务端连接/线程池、MySQL 查询、Redis、网络带宽；
- 防护要分层：客户端节流、服务端限流/降级、存储预计算；
- "不拉全量"的产品设计：未读数、懒加载、摘要优先；
- 群聊扇出的放大效应（项目未实现群聊，但面试官常追问）。

**可直接背的参考回答（口语化）**

> 我会分客户端、服务端、存储三层来防。
>
> **客户端**：上线后不是"把几千条拉下来"，而是先拉会话列表的摘要——每个会话的未读数、最新一条消息、最新序号，这些字段是预计算的，一条 SQL 或一个 Redis 结构就能拿到。用户点开哪个会话，才去拉那个会话最近的一页（比如 100 条）；用户往上翻再按游标继续拉。请求串行化、有间隔、切走就取消；对单会话最多先拉最近 100~200 条。这样几千条离线消息里，真正被加载的只有用户看的那部分。
>
> **服务端**：拉取接口必须能做限流——按 uid 和连接维度的令牌桶，比如每秒最多 2 次拉取请求、每次最多 100 条；超限要么排队要么返回"稍后重试"。同一用户的多台设备共享配额。接口按优先级排：补拉游标 > 点开会话历史 > 翻旧历史；压力大时把"翻旧历史"降级（提示稍后再试），保补拉。
>
> **存储层**：未读数、最新消息不能实时 `COUNT` 或全表扫，用 `(user_id, thread_id, last_read_msg_id)` 的游标表或 Redis hash 预计算；查询只走 `(thread_id, message_id)` 索引的固定页；压力大时历史查询走从库；首屏消息可以缓存在 Redis。
>
> 还有一点：如果是群聊，一个大群的消息是"写一条、读 N 人"的扇出模型，绝不能按成员复制消息行，未读按成员游标算，上线更不可能全量推。这一块我们项目还没做群聊，是设计层面的准备。
>
> 最后是压测和降级预案：像"上线瞬间千人同时拉历史"这种场景，我会专门做压测，确认限流阈值和降级开关——比如只返回未读数和最近一条，历史消息延后加载。

**技术要点拆解**

- **洪峰的真实代价**：一次拉几千条不是一次请求，而是"多条消息 × 序列化 + JSON/Protobuf 解析 + UI 渲染 + 写本地库"，同时几千个用户上线会放大成几百万行查询。所以核心思路是**把"拉全量"变成"拉摘要 + 懒加载"**。
- **限流维度**：uid、连接、接口、全局四级限流；服务端令牌桶比客户端自觉更可靠（客户端不可信）。
- **优先级队列**：拉取请求可以带 priority；服务端线程池按优先级消费，避免翻旧历史的请求占满业务线程。
- **压缩**：一页消息用 Protobuf + gzip（文本压缩率很高），降低带宽；分页响应避免全量 JSON。
- **预计算表**（推荐设计）：

```sql
CREATE TABLE chat_thread_stat (
  user_id           BIGINT UNSIGNED NOT NULL,
  thread_id         BIGINT UNSIGNED NOT NULL,
  last_msg_id       BIGINT UNSIGNED NOT NULL,  -- 会话最新序号
  last_read_msg_id  BIGINT UNSIGNED NOT NULL,  -- 用户已读位置
  last_msg_preview  VARCHAR(128) NOT NULL,     -- 列表预览
  updated_at        DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
  PRIMARY KEY (user_id, thread_id),
  KEY idx_thread (thread_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
-- 未读数 = last_msg_id - last_read_msg_id（还需扣除自己发的，实践上可维护 unread_cnt 计数）
```

**当前项目实现对照**

- 项目客户端也没有做这些防护：登录后 `loadChatList` 拉完会话列表，`slot_load_chat_thread` 会对**每个会话**依次发 `ID_LOAD_CHAT_MSG_REQ`（`chatdialog.cpp` L429-455），全部串行拉完才关闭 loading；没有优先级、没有懒加载。
- 服务端 `LoadChatMsg` 的 `page_size=10`（`LogicSystem.cpp` L889）客观上限制了单次返回量，但没有限流、没有未读预计算、没有摘要接口；`login` 返回好友/申请，不返回会话摘要。
- 群聊表结构存在于 day37/llfc2.sql（`group_chat/group_chat_member`），服务端 `GetUserThreads` 的 SQL 也会返回 group，但客户端 `slot_load_chat_thread` 里 `type == "group"` 直接 continue（`chatdialog.cpp:335`）。
- 压测口径：day30 说单服务 8000 稳定连接、10ms 延迟、极限 8000~2W（看机器），但没有做"离线洪峰"专项压测；面试可说"这块待补压测数据"。

**差距与改进建议**

1. 加 `chat_thread_stat`（或 Redis hash `thread_stat:{uid}`）预计算未读数和最新消息；客户端会话列表只渲染摘要，点开才拉消息。
2. 给拉取接口加"按 uid 令牌桶 + 单页上限 + 优先级"三件套；可以做在 GateServer/ChatServer 的业务线程池前。
3. 把"上线全量拉所有会话"改成"先渲染本地/摘要，后台空闲时再对活跃会话做增量"，并支持取消与退避。
4. 面试演示口径：把"客户端限流 + 分页 + 优先私聊 + 懒加载"讲成客户端部分，主动补服务端与存储部分，才能拿满分。

**追问预判**

- 问：限流把用户正常的补拉也拒了怎么办？→ 答：区分优先级和白名单：登录首屏、游标补拉保底；限流主要限制"翻旧历史"和非活跃设备；同时给用户可见的降级提示。
- 问：怎么知道用户"有几千条"而不查库？→ 答：未读数在会话摘要里就是预计算值，不用现查。
- 问：如果用户就是要一次导出所有消息？→ 答：走异步导出任务+对象存储下载，不参与在线限流，避免占在线资源。
- 问：群聊几千条怎么处理？→ 答：群聊只维护成员游标与未读数，上线只拉已读位置之后的消息；大群默认不推送全量，只更新计数。

### 2.3 OPPO二面 问16：落库成功但下发失败

**面试官原话（转写）**

> "请问在你这个场景会不会出现，比如说我这个服务端落库成功，但是我发给用户失败了，这里有什么补偿机制吗？"

**当时的回答（压缩要点）**

- 服务端只发一次，不给服务端加太重任务；
- 客户端兜底：约每 500ms 向服务端请求"我最新收到的序列号是多少"，对不上就拉本地之后的这些事件；
- 用户点开某个会话时也主动拉一次。状态：⚠️ 思路（拉取兜底）正确，面试官也点头了；但"500ms 轮询序列号"成本高、和讯飞问5 的"5 秒"口径冲突，且没提"服务端如何记录接收方游标/事件"。

**考点分析**

- 推送的语义：**at-least-once 的最终一致**——落库成功 = 消息不会丢，下发失败 = 实时性受损，用接收方拉取补齐；
- 拉取触发点设计：点开会话、收到不连续消息、重连、低频对账；
- 服务端要提供什么：**每个会话的 max_msg_id**（接收方对账）、事件表/收件箱；
- 别把"轮询频率"说成实现细节，它反映系统成本意识。

**可直接背的参考回答（口语化）**

> 会出现，而且这是分布式推送的常态，所以我的定位是：**服务端落库是唯一权威，下发只是尽力而为，接收方用拉取做最终一致**。
>
> 具体补偿分四个触发点，而不是靠高频轮询：
>
> 第一，**点开会话必拉一次**——这是最自然的时机，用户反正要看这个会话，带本地游标做增量拉取；
>
> 第二，**推送序号不连续即补拉**——收到 38 本地只到 36，就补 `(36, 38]`；
>
> 第三，**重连/重新登录时对账**——登录响应里带每个会话的 `max_msg_id`（或客户端调一个轻量接口），和本地游标比较，只拉有差异的会话；这是"补齐离线期间所有消息"的主入口；
>
> 第四，**低频兜底**——比如 30~60 秒做一次轻量对账，或者由心跳响应捎带版本号/序号，客户端发现版本变了才拉。不会用 500ms 这种频率去问"最新序号是多少"，因为在线用户几十万、每 500ms 一次请求，QPS 直接翻倍，而且大部分请求是白跑。
>
> 服务端侧我会维护一个**接收方维度的同步状态**：每个用户每个会话的"已投递到哪个序号/已确认到哪个序号"。在线投递失败的，不需要在内存里无限重试，而是把它当作事件留在存储里，等接收方下次对账/上线时拉走。这样服务端不背重试状态，接收方拿到的一定是全的。

**技术要点拆解**

- **为什么"只发一次 + 拉取兜底"成立**：消息已经持久化，接收方迟早会在某个触发点发现游标落后；只要"发现落后"的机制覆盖所有场景，就不会丢。
- **服务端状态设计**：
  - 方案 A（本项目最简单）：不维护 per-user 投递状态，客户端拿会话 `max_msg_id` 与本地游标对账；
  - 方案 B（完整）：`user_thread_cursor(user_id, thread_id, delivered_seq, read_seq, synced_seq)`，投递时尽量推进，失败留给拉取；
  - 方案 C（事件表）：见 2.5，适合承载撤回、已读等非消息事件。
- **"最大序号对账"的数据来源**：`chat_thread_stat.last_msg_id`（见 2.2）或 `SELECT MAX(message_id) FROM chat_message WHERE thread_id=?`（有 `(thread_id, message_id)` 索引，代价小但要限流）。
- **顺序问题**：拉取回来的消息与在线推送可能交错，统一按 `message_id` 排序/去重，不能按到达顺序渲染。

**当前项目实现对照**

- **服务端确实"只发一次"**：`DealChatTextMsg` 落库后，若接收方不在线（`UserMgr::GetSession(touid)` 为空）直接 return（`LogicSystem.cpp` L543-552）；跨节点时 `ChatServiceImpl::NotifyTextChatMsg` 找不到 session 也直接返回（`ChatServiceImpl.cpp` L92-130 附近）。没有任何重试/事件记录。
- **客户端没有 500ms 对账**：只有 10 秒心跳（`chatdialog.cpp` L155-165）；心跳响应里也没有携带会话 seq（`LogicSystem::HeartBeatHandler` 只回 error，`LogicSystem.cpp` L572-581）。所以"兜底"在当前代码里不存在，只有"点开会话拉取"部分（且 load_more 有缺陷）。
- day30 L133 也承认"未完整实现用户离线后数据清空操作"——离线链路整体是半成品。

**差距与改进建议**

1. 登录响应增加每个会话的 `max_msg_id`（读 `chat_thread_stat`），客户端与本地游标比对后按需拉取——最小成本实现"登录对账"。
2. 心跳响应捎带全局/会话版本号（如各会话 max_msg_id 的哈希或最近变更时间），变化才触发对账，成本远低于 500ms 轮询。
3. 补"服务端投递失败不影响正确性"的测试用例：模拟接收方不在线/断连，验证上线后通过 `LoadAfter` 补齐。
4. 面试口径统一：**取消"500ms 轮询"表述**，改为"登录对账 + 点开会话拉取 + 序号缺口补拉 + 低频兜底"四触发点。

**追问预判**

- 问：服务端不重试，用户永远不上线怎么办？→ 答：消息在库，永远是"待拉取"状态，不上线就不投递是合理的；同时离线通知/推送通道（APNs 等）可以兜一层。
- 问：对账接口被刷怎么办？→ 答：登录对账每设备每次登录限一次，日常对账合并到心跳，接口限流。
- 问：怎么知道"每条都拉到了"？→ 答：会话游标连续推进 + `max_msg_id` 对齐；两者相等即认为该会话同步完成。
- 问：消息顺序会不会乱？→ 答：渲染按 `message_id` 排序，落本地也按主键；到达顺序不重要。

### 2.4 多益网络一面 问31：消息撤回流程设计

**面试官原话（转写）**

> "像我们微信嘛，微信通常都有个功能叫做消息撤回，如果让你去设计实现这么一个消息撤回功能，你会怎么去做实现？比如说你觉得像消息的一个撤回流程是怎么样的……以及可以给一些发散之类的。"

**当时的回答（压缩要点）**

- 消息副本：客户端有、服务端权威、对方也有；
- 撤回：先标记消息状态 → 撤回请求到服务端 → 服务端通知对方客户端 → **对方从本地数据库删除该消息、界面撤掉** → 对方回 ACK → 服务端没收到 ACK 就持续重发 → 服务端收到 ACK 后再回执撤回方。状态：⚠️ 骨架正确（状态标记 + 转发 + ACK），但有三个会被追问打穿的点：
  1. "从本地删除"——标准做法是**标记撤回（tombstone）**，不是物理删除；删除后多端同步、审计、消息 ID 连续性维护都成问题；
  2. 没有**超时撤回**（微信 2 分钟）和服务端时间校验；
  3. "没收到 ACK 持续重发"在对方断网时不可控——面试官下一问（问32）其实就是在引导你改这个。

**考点分析**

- 撤回是一条"控制消息/事件"，不是数据删除；
- 状态模型：原消息 + 撤回事件；
- 幂等、超时、权限（只能撤回自己的消息）、窗口期；
- 多端/离线投递：撤回事件也要能补拉；
- 与"消息可靠性"的关系：撤回应复用同一套投递通道。

**可直接背的参考回答（口语化）**

> 我会把撤回设计成"**状态变更事件**"，而不是删除消息。
>
> 流程：用户长按自己发的消息点撤回 → 客户端发 `RevokeMessage(thread_id, message_id, op_seq)` 到服务端 → 服务端做四件事：
>
> 1. 校验权限和时机：只能撤回自己发的、且 `now - created_at <= 2 分钟`；时间以服务端为准，客户端时间不可信。企业/管理员场景可以有例外。
> 2. **幂等更新**：`UPDATE chat_message SET status = 1, content = '', revoked_at = NOW() WHERE message_id = ? AND sender_id = ? AND status = 0`；如果影响行数是 0，说明已经撤回过或不是本人，直接按成功返回（或者按业务返回"不可撤回"）。
> 3. **生成撤回事件并投递**：给会话内所有接收方（单聊是对端，群聊是全员）发 `MESSAGE_REVOKED { thread_id, message_id, op_user, server_time }`，在线走长连接推送。
> 4. 撤回方自己收到成功响应后，本地把消息渲染成"你撤回了一条消息"。
>
> 接收方收到撤回事件后，在本地库里把对应消息标记为撤回（保留行、清空或保留内容），界面替换成"对方撤回了一条消息"；**不要物理删除**，否则消息序号断档、多端对不上、也没有审计记录。
>
> 离线怎么办？撤回事件和普通消息一样落"事件表/收件箱"，用户上线后按事件序号拉取并应用。这样服务端就不需要"没收到 ACK 就一直发"——推送失败就等拉取，和消息同一套最终一致模型。
>
> 另外可以做两个加分项：一是**多端同步撤回**——同一个人手机撤回，PC 也要撤掉，把"自己其它端"也当作接收方投递事件；二是**超时边界**——2 分钟是产品定义，服务端是最终裁判，防止客户端改时间。

**技术要点拆解**

- **状态 vs 删除**：物理删除会破坏 `message_id` 的连续性（gap 检测、对账都依赖它），也不利于多端同步；标准做法是 tombstone。
- **内容置空与否**：产品上显示"撤回"就不该再看到内容；但合规/审计场景可保留原文在单独表或加密列，接口层不返回。面试时说出这个取舍是加分项。
- **幂等**：重复撤回请求必须无害；`status=0` 的条件更新天然幂等。
- **撤回窗口**：微信 2 分钟；服务端校验。也可以做"无痕撤回 vs 留痕撤回"的扩展。
- **与消息可靠性的关系**：撤回事件要有自己的序号（或复用 message_id + 事件类型），客户端按序应用；重复事件靠事件 ID 去重，见 2.6。
- **删除消息（delete）和撤回（revoke）要分开**：用户"删除聊天记录"是**本地私有操作**（只影响本端视图，多端可同步也可不同步）；撤回是**双方可见的状态变更**。面试官问"撤回"时别答成"删除"。

**当前项目实现对照**

- **代码里完全没有撤回功能**：全仓 grep `撤回/revoke/recall` 只命中 `sql备份/llfc2.sql` L32 的注释 `status tinyint ... COMMENT '0=未读 1=已读 2=撤回'`。
- 而且 `status` 语义是三处打架的：
  - DDL 注释：`0=未读 1=已读 2=撤回`；
  - 服务端 `DealChatTextMsg`：所有文本消息写 `status=2`（`LogicSystem.cpp` L506）→ 按 DDL 等于"全都被撤回"；
  - 客户端 `global.h` L163-167：`0=对方未读 1=发送失败 2=对方已读`，服务端 ACK 后 `MoveMsg` 直接 `SetStatus(2)` → 显示"已读"。
  这是一个必须在面试前修掉的硬伤：面试官只要看一眼代码/表结构就会发现"状态字段自己都对不上"。
- "持续重发直到 ACK"的实现在项目里也不存在（没有重试队列/outbox，grep 无 outbox/retry），属于设计描述。

**差距与改进建议**

1. 重定义状态：`status` 只表示消息本身（0正常/1撤回/2删除），`revoked_at/revoked_by` 可选；客户端发送状态（发送中/已落库/已送达/已读）放本地 outbox 和消息本地状态，不写入服务端 `status`。
2. 实现最小撤回闭环：协议加 `ID_REVOKE_MSG_REQ/RSP` 与 `ID_NOTIFY_REVOKE_MSG_REQ`；服务端按 2.4 流程做权限 + 2 分钟窗口 + 幂等 UPDATE；在线推送、离线交给上线拉取（与补拉共用事件表）。
3. 客户端会话内消息渲染支持"撤回态"（`ChatItemBase::setStatus` 可扩展一个 REVOKED 图标/文案）。
4. 补一条测试：A 撤回时 B 离线，B 上线后事件表补拉，验证 B 端显示撤回。

**追问预判**

- 问：撤回后对方已经读了，内容还算不算泄露？→ 答：技术上无法回收已读内容，产品上只能声明"撤回可能被看到"；合规链路可保留审计副本但不对外返回。
- 问：群聊撤回要发多少条事件？→ 答：一条事件发给会话，由服务端扇出给在线成员；离线成员上线按会话事件表拉取，不要按成员存多份。
- 问：撤回的消息能不能恢复？→ 答：标记撤回时保留原内容（或加密留存），产品不接受恢复就清空；两种都行，说出取舍即可。
- 问：对方老版本客户端不认撤回事件？→ 答：协议加版本号/能力位，旧端至少不显示错误；服务端对拉取接口做兼容（返回 `revoke` 字段）。

### 2.5 多益网络一面 问32：对方断网时的"事件表"处理

**面试官原话（转写）**

> "你刚才有提到说，比如说我点击撤回的时候，对方的网络如果断了嘛……那你觉得除了这种持续发送，还有什么其他的一些更好的处理方式吗？"

**当时的回答（压缩要点）**

- 在服务端建一个**事件表**，记录每个用户待收的事件；
- 撤回事件写到对方的事件表里；
- 对方一上线就拉取离线期间没收到的事件，然后清理本地数据。状态：✅ 完全答到面试官想听的点（这正是引导方向）。可以继续补完整：事件的序号、幂等、与消息表的关系、清理策略。

**考点分析**

- "持续重发 until ACK"的内存/可靠性缺陷；
- 事件表（离线收件箱）模型：写一次、拉一次、可审计；
- 消息与事件的关系（消息也可以看作事件的一种）；
- 上线拉取、幂等、清理与过期。

**可直接背的参考回答（口语化）**

> 更好的做法就是**服务端持久化"待收事件"，把推送降级为通知，拉取作为唯一可靠通路**。
>
> 我会建一张 `user_event`（离线收件箱/事件表）：
>
> ```sql
> CREATE TABLE user_event (
>   event_id   BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
>   user_id    BIGINT UNSIGNED NOT NULL,
>   event_type TINYINT NOT NULL,        -- 1新消息 2撤回 3已读回执 4会话变更
>   thread_id  BIGINT UNSIGNED NOT NULL,
>   msg_id     BIGINT UNSIGNED NOT NULL,
>   payload    BLOB NULL,               -- 事件附加数据（撤回者、原因等）
>   created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
>   PRIMARY KEY (event_id),
>   KEY idx_user_event (user_id, event_id)
> );
> ```
>
> 撤回时：服务端更新消息为撤回态，然后往会话每个接收方的 `user_event` 插一条事件（单聊就一条，群聊按成员扇出或按会话存一份+成员游标）。在线的话顺手推一条通知；对方断网的话什么也不做，事件躺在表里。
>
> 对方上线后拿本地 `event_id` 游标请求 `event_id > last_event_id ORDER BY event_id ASC LIMIT N`，把离线期间的所有事件拉齐，按 `event_id` 顺序应用，应用完推进游标。事件的消费必须幂等：按 `event_id` 去重，重复应用撤回只是把状态再标一次。
>
> 清理方面：事件应用成功后客户端回报已消费位置（或者服务端按时间归档已消费事件），服务端可以定期删除/归档旧事件；保留窗口一般和离线消息窗口一致，比如 7~30 天。
>
> 这样做的好处是：服务端没有"发给断网用户直到 ACK"这种不可控状态；消息和事件都持久化，重启不丢；客户端上线游标一拉，离线期间发生的一切（新消息、撤回、已读）按序补齐。

**技术要点拆解**

- **消息表 vs 事件表**：可以合并（消息即事件，`event_type=new_message` 带消息 id），也可以分开（消息表存内容，事件表存操作）。分开的好处是消息表保持"内容不可变"，事件表承载操作流；合并的好处是顺序天然统一。面试推荐说"分开存储、统一序号体系"。
- **扇出方式**：
  - 写扩散（fan-out on write）：给每个成员插事件行，读便宜写贵，适合小群/单聊；
  - 读扩散（fan-out on read）：事件按会话存一份，成员各自用游标读，写便宜读贵，适合大群。
  - 单聊无所谓；群聊按规模选。
- **事件序号**：per-user 自增 `event_id`（收件箱）或 per-thread 序号；关键是单调 + 连续（和 message_id 同思路），支撑 gap 检测。
- **幂等与顺序**：应用事件要能重复执行；顺序按服务端序号，不按到达顺序。
- **保留与清理**：事件是"操作流"，不是"永久历史"；消费确认后归档。撤回这种操作如果用户真的离线太久（超过保留窗口），可以在会话同步时用消息行的 `status` 兜底——即消息表本身就是最终状态的快照。

**当前项目实现对照**

- **项目没有事件表**：`sql备份` 与 server 代码中都没有 `user_event`/`offline` 相关表；离线用户没有任何待办存储。
- 项目里唯一的"离线"语义是**被踢下线通知**：`CSession::NotifyOffline` 发 `ID_NOTIFY_OFF_LINE_REQ`（`CSession.cpp` L252-263），客户端收到后 `emit sig_notify_offline()` 并断开（`tcpmgr.cpp` L478-510）。这是多端登录互斥的踢人逻辑（`ChatServiceImpl::NotifyKickUser`，`ChatServiceImpl.cpp` L189-207），**不是离线消息机制**，别在面试里混淆。
- 现有可复用的基础：消息落 MySQL 且有序号；`(thread_id, message_id)` 索引可支撑"上线拉取"；缺的是事件表、游标、拉取协议。

**差距与改进建议**

1. 建 `user_event` 表，先把**撤回事件**接进去（消息本身已经能靠 `LoadAfter` 补拉，不急着复制消息行）。
2. 客户端本地加 `event_cursor(user_id, last_event_id)` 与 `events` 表（表结构见 [消息存储与分页拉取](./消息存储与分页拉取.md) 2.7.6）。
3. 上线流程：登录 → 拉会话摘要对账（消息）→ 拉事件（撤回/已读）→ 应用 → 渲染。
4. 面试叙事：把问31 的"ACK 重发"主动改成"事件表 + 上线拉取"，并说明理由（不受对方网络状态影响、服务端无内存重试状态、可审计）。

**追问预判**

- 问：事件表会不会无限增长？→ 答：按用户保留窗口归档/删除；消息的最终状态在 `chat_message.status` 里兜底，事件过期不应用也能通过全量同步纠正。
- 问：每个事件都写一行，群聊岂不是写放大？→ 答：大群用读扩散（按会话存一份事件 + 成员游标），小群/单聊写扩散，按规模选。
- 问：已消费的事件怎么标记？→ 答：客户端回报 `consumed_event_id`（低水位），服务端据此归档；不追求逐条 ACK，和拉取模型一致。
- 问：和消息可靠传输是什么关系？→ 答：事件是"控制面"，消息是"数据面"，统一用"服务端持久化 + 客户端游标 + 幂等应用"的模型，见 [消息可靠传输与幂等去重](./消息可靠传输与幂等去重.md)。

### 2.6 跨题专题：离线投递、上线同步、未读数与已读回执

> 这一节把文件 2 的必含模型沉淀成可直接使用的方案。

#### 2.6.1 投递模型：推 vs 拉、推拉结合

| 模型 | 优点 | 缺点 | 适用 |
|---|---|---|---|
| 纯推 | 实时、延迟低 | 对方不在线/连接抖动就丢；发送侧重试状态不可控 | 不单独使用 |
| 纯拉 | 实现简单、状态少 | 延迟取决于轮询；高频轮询浪费 | 早期 demo |
| **推拉结合（推荐）** | 在线快、离线全、服务端轻 | 需要序号/游标体系 | 生产 IM |

推拉结合的完整语义：

1. **消息先落权威存储（MySQL）**，成功才 ACK 发送方；这是"不丢"的根。
2. **在线**：服务端定位接收方所在 chat 节点（Redis 登录态，见 [多端登录互斥与在线状态](./多端登录互斥与在线状态.md)），长连接推送；推送只保证"尽快知道"，不保证必达。
3. **离线/推送失败**：不重试，消息留在存储；用户上线/重连/点开会话时按会话游标增量拉取。
4. **客户端收到任何消息都按 `message_id` 去重、按序渲染、推进连续游标**；发现缺口触发补拉。
5. 本项目现状：落库 + 在线推送 + 点开会话拉取已有雏形；缺离线事件、缺客户端持久化游标（见 2.1）。

#### 2.6.2 上线全量同步与增量同步

- **判定**：客户端本地有库且游标有效 → 增量；新设备/本地库损坏/游标过期 → 全量。
- **全量同步（新设备）**：
  1. 拉会话列表（分页，项目已有 `GetUserThreads` 游标分页）；
  2. 每个会话只拉"最近一页"（50~100 条）用于首屏；
  3. 用户点开某会话再拉更早历史；
  4. 不必在登录时同步全部历史——这是洪峰防护的核心（见 2.2）。
- **增量同步（老设备）**：
  1. 登录响应带每个会话的 `max_msg_id`（或变更版本）；
  2. 客户端逐个比较本地 `last_synced_msg_id`，只拉落后会话；
  3. 客户端本地无机会话（离线期间新建立的会话）也要能从会话列表增量拉到；
  4. 拉取分页、限速、可取消。
- **同步完成的判据**：每个会话 `last_synced_msg_id == max_msg_id`，且事件游标追平。
- 项目对照：day37 L311-335 已经写了"客户端发本地最大 message_id + thread_id、服务端按会话分页返回"的设计，但客户端本地库未实现（day37 L14），实际登录时从 0 开始拉、每个会话 10 条（见 [消息存储与分页拉取](./消息存储与分页拉取.md) 2.1）；全量/增量两种路径都还没有真正跑通。

#### 2.6.3 未读数

- **推荐模型**：每个 `(user_id, thread_id)` 维护 `last_read_msg_id` 和 `last_msg_id`，未读 = 区间内对方发的消息数；为了免去每次统计，再维护一个 `unread_cnt` 计数（收到消息时 +1，已读时清零/按游标重算）。
- 存储：权威在 MySQL（`chat_thread_stat`，见 2.2）；Redis 做缓存/加速（`HINCRBY unread:{uid} thread_id 1`）。
- 一致性：Redis 计数和权威游标可能短暂不一致，用"游标重算式"定期校准；Redis 丢了也能恢复。
- 客户端：会话列表只展示未读数（预计算），点开会话时上报 `read(thread_id, last_read_msg_id)`，服务端更新游标并清零计数，同时可通知对方"已读"。
- 项目对照：当前未做未读数，客户端只在收到消息时更新会话列表的预览（`slot_text_chat_msg`），没有红点计数；`message_read` 表只在 day37 文档里提过（L107），未建表。

#### 2.6.4 撤回：普通撤回 vs 消息删除 vs 超时撤回

| 类型 | 语义 | 权限 | 实现 |
|---|---|---|---|
| 普通撤回 | 双方可见"已撤回" | 仅发送者，限 2 分钟 | `status=1` + 撤回事件；内容可清空；不删行 |
| 消息删除 | 仅操作者自己不可见（多端可同步） | 任何人，任意时间 | per-user `deleted` 标记/游标表，**不影响对方** |
| 超时撤回 | 超过窗口不允许；管理员场景例外 | 服务端时间裁判 | 校验 `now - created_at <= 2min`，否则拒绝 |
| 服务端物理删除 | 合规删除 | 运营/合规 | 独立审计流程，不混入用户撤回 |

- 通用原则：**撤回是状态变更事件，不是删除**；保留 `message_id` 连续性；幂等更新；离线靠事件表/拉取补齐。
- 多端同步：撤回方自己的其它设备也是接收方，要收到 `MESSAGE_REVOKED`；"消息删除"如果要跨端，同样用事件同步（或 per-device 本地操作，由产品决定）。
- 项目对照：完全没有实现；`status` 语义三方冲突（见 2.4），需要先统一。

#### 2.6.5 多端已读回执扩展思路

- 数据模型：`message_read_cursor(user_id, thread_id, device_id?, last_read_msg_id, updated_at)`。
  - 简化为 `(user_id, thread_id)` 一条：多端已读取 max 合并；
  - 要区分设备就加 `device_id`，多端各自游标；
- 单聊流程：A 已读到 seq=100 → 服务端收到 `read(thread, 100)` → 推送 B `READ_RECEIPT(thread, reader=A, last_read=100)` → B 把 ≤100 的自己发的消息标为已读（UI 显示"已读"）。
- 群聊：只保存每个成员的 `last_read_msg_id`，需要展示已读数时聚合（"3/10 人已读"）；不要逐条消息维护回执（写放大）。
- 弱化策略（现实产品）：微信单聊不显示已读，避免社交压力；面试可以说"支持但可产品化关闭"。
- 项目对照：无回执；客户端把服务端 ACK 当"已读"（2.4 所述），**必须先拆分语义**：0=发送中，1=服务端已落库，2=对方端已送达，3=对方已读。当前客户端 `MsgStatus`（global.h L163-167）应重命名/重定义。

#### 2.6.6 离线洪峰防护清单（速查）

- **客户端**：首屏摘要渲染；仅拉活跃会话最近一页；串行/限速/退避；请求可取消（切会话）；群聊点开才拉；渲染分帧/虚拟列表。
- **服务端**：令牌桶限流（uid/连接/接口）；单页条数上限；优先级队列；接口降级开关（只回摘要）；读从库；首屏缓存。
- **存储**：`chat_thread_stat` 预计算未读/最新；只走 `(thread_id, message_id)` 索引；归档旧消息；事件/收件箱按窗口保留。
- **协议**：Protobuf + gzip；响应带 `next_cursor/has_more`；对账接口轻量化（只回 seq）。
- **兜底**：监控上线拉取 QPS/耗时；压测"大量用户同时上线"；降级时保补拉、舍翻历史。

## 3. 小结与行动项

**最值得注意的三个结论**

1. **"5 秒轮询"和"500ms 轮询"是两份面经里互相冲突的口径**（讯飞问5 vs OPPO 问16），而且项目代码里根本没有这类定时器（只有 10 秒心跳）。面试前必须统一成"推拉结合：点开会话 + 序号缺口 + 登录对账 + 低频兜底"，否则被交叉追问会露馅。
2. **撤回和离线事件的正确答案都是"事件表 + 上线拉取"**（多益问32 面试官就是在引导），而项目里连事件表、撤回代码、本地库都没有；好在消息表有序号、有索引，补最小闭环的成本不高，补完这两篇文档里的方案就能直接演示。
3. **`status` 三处语义打架是当前最容易被拆穿的硬伤**：DDL 说 2=撤回、服务端所有消息写 2、客户端把 2 当"已读"。撤回、已读回执、发送状态三个需求全部依赖这个字段，必须先重构语义再谈功能。

**行动项（可在项目中动手改的 1-3 条）**

1. **统一状态语义 + 最小撤回闭环**（1 天）：
   - `status` 改为 0=正常/1=已撤回/2=已删除；新增 `revoked_at`；
   - 协议加 `ID_REVOKE_MSG_REQ/RSP + ID_NOTIFY_REVOKE_MSG_REQ`；
   - 服务端做"归属校验 + 2 分钟窗口 + 幂等 UPDATE + 在线推送"，离线由后续事件表兜底。
2. **建 `user_event` 事件表 + 客户端本地 `events/event_cursor`**（1 天）：
   - 先把撤回事件接进去，登录后客户端按 `last_event_id` 拉取并幂等应用；
   - 与 [消息存储与分页拉取](./消息存储与分页拉取.md) 行动项 3 的 SQLite 方案共用一次改造。
3. **登录对账 + 会话摘要**（半天~1 天）：
   - `chat_thread_stat` 或在登录响应里带各会话 `max_msg_id` 与未读数；
   - 客户端与本地游标比对，只拉落后会话；把"登录后全量拉所有会话"替换成"摘要 + 按需"；
   - 顺带产出"离线洪峰"压测数据，补齐 OPPO 问5 缺失的服务端视角。
