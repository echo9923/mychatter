### 2.1 虾皮一面 问6：点击会话拉取 100 条消息，SQL 怎么写（重点）

**面试官原话（转写）**

> "用户点击一个会话时，需要拉取 100 条消息，是如何实现的？对应的 SQL 语句是怎么写的？"

**当时的回答**

- 答：**（未记录）**——面经原文标注"未记录"，结合复盘备注第 2 条"待补的知识点：拉取最近 100 条消息的 SQL 写法"，判断为当时没答上来或答得很含糊。状态：❌。

**考点分析**

面试官其实在一道题里塞了 4 个考点：

1. **方向性**：进入会话默认要看"最近"的消息，SQL 是倒序 + LIMIT，还是正序 + 子查询？很多候选人会写 `ORDER BY message_id ASC LIMIT 100`，结果拉到了这个会话最古老的 100 条。
2. **分页方式**：`LIMIT offset, 100` 还是游标（keyset）分页？深分页时 offset 的性能怎么解释。
3. **索引**：WHERE + ORDER BY 能不能命中联合索引，避免 filesort。
4. **后续翻页**:向上翻历史的 SQL（`message_id < 当前最旧一条`），以及登录后增量补拉（`message_id > 本地最大`）。

**可直接背的参考回答（口语化）**

> 点开会话拉 100 条消息，我分三种场景来实现，SQL 都用游标分页，不用 offset。
>
> 第一种，**首次进入会话看最近 100 条**。MySQL 里这样写：
>
> ```sql
> SELECT message_id, thread_id, sender_id, recv_id, msg_type, content, status, created_at
> FROM chat_message
> WHERE thread_id = ?
> ORDER BY message_id DESC
> LIMIT 100;
> ```
>
> 因为走的是 `(thread_id, message_id)` 联合索引，`thread_id` 等值 + `message_id` 有序，直接取索引最后一段就行，没有 filesort。取出后客户端按 `message_id` 倒序反转成升序渲染。为什么不在 SQL 里再做子查询转序？数据量小的时候无所谓，但子查询 + 排序会破坏索引有序性，不如把反转放到应用层。
>
> 第二种，**用户往上翻历史**，我会把当前本地最旧那条的 `message_id` 作为游标：
>
> ```sql
> SELECT ...
> FROM chat_message
> WHERE thread_id = ? AND message_id < ?
> ORDER BY message_id DESC
> LIMIT 20;
> ```
>
> 每次翻页只取"比游标更旧"的 20 条，天然走索引范围扫描，翻到第几页性能都一样。返回时多取一条（`LIMIT 21`）用于判断 `has_more`，实现方式和我们项目里拉会话列表的 `GetUserThreads` 一样。
>
> 第三种，**断线重连/登录后的增量补拉**，拿每个会话的本地最大 `message_id` 做游标：
>
> ```sql
> SELECT ...
> FROM chat_message
> WHERE thread_id = ? AND message_id > ?
> ORDER BY message_id ASC
> LIMIT 100;
> ```
>
> 这个方向是"从旧到新"追平，和翻历史正好相反。三条 SQL 的共同点是：**都只依赖 `(thread_id, message_id)` 复合索引 + 游标，不碰 offset**。

**技术要点拆解**

1. **为什么不用 `LIMIT offset, N` 做深分页**
   - `offset` 不是"跳过索引"，而是"先按顺序取出 offset+N 行，再丢掉前 offset 行"。翻到第 1 万条时，第 1 万零 1 条和第一条的代价一样吗？不是——前面 1 万条全都要从索引/回表读出来再丢弃，越翻越慢；同时若有新消息插入，offset 会整体后移，出现重复或漏读。
   - 游标分页的代价：不支持"跳到第 k 页"；只能上一页/下一页。IM 的历史消息天然是"往上滚"，这个限制可接受。
   - 如果非要 offset 且有深分页需求，常用"延迟关联"：先用覆盖索引子查询拿到主键，再回表，减少回表量；但这只是缓解，不如游标。
2. **索引与排序方向**
   - `KEY idx_thread_message (thread_id, message_id)`：等值列在前、排序列在后，`ORDER BY message_id DESC` 可以直接倒序扫描该索引（MySQL 8 支持索引正反双向扫描），所以 DESC 不产生额外排序。
   - 不需要单独为 `created_at` 再建一个会话索引：排序权威用 `message_id`（服务端分配、单调），时间只是展示字段。day37 里同时建了 `(thread_id, created_at)` 和 `(thread_id, message_id)` 两个索引，前者在单一查询模式下是冗余的，可以只保留后者或按实际查询保留。
3. **`LIMIT N+1` 判断 has_more**：比 `COUNT(*)` 便宜得多，项目里拉会话列表已经这么做了（`MysqlDao.cpp` 的 `GetUserThreads` 取 `pageSize+1` 后 `pop_back`）。
4. **查询要带 `thread_id` 的权限校验**：SQL 只靠 `thread_id` 过滤，进入前必须校验当前 uid 是该会话成员（`private_chat.user1_id/user2_id` 或 `group_chat_member`），否则是越权漏洞。这一点面试里主动说出来是加分项。

**当前项目实现对照**

- 表结构（`sql备份/llfc2.sql` L24-36）：
  - `message_id BIGINT UNSIGNED AUTO_INCREMENT` 主键；`thread_id/sender_id/recv_id/content/created_at/updated_at/status`。
  - 索引：`idx_thread_created(thread_id, created_at)`、`idx_thread_message(thread_id, message_id)`。
- 服务端 SQL（`server/ChatServer/src/MysqlDao.cpp` L800-860 `LoadChatMsg`）：
  - 实际执行的是**增量方向**：`WHERE thread_id = ? AND message_id > ? ORDER BY message_id ASC LIMIT page_size+1`，`page_size` 在 `LogicSystem.cpp` L889 写死为 **10**（不是面经里的 100）。
  - **已发现的实现缺陷**：SQL 取了 `page_size+1` 条，但函数里没有"多取一条则 `load_more=true` 并丢回最后一条"的逻辑，`next_cursor` 也始终等于入参 `last_message_id`（L813-815、L839-849）。参照同文件 `GetUserThreads` L642-720 的写法可以修复。因此客户端 `slot_load_chat_msg` 里 `load_more` 永远为 false，实际上每个会话只加载了 10 条，**向上翻历史的能力目前是缺失的**。
  - 结果结构里 `ChatMessage::message_id/next_cursor` 是 `int`（`include/data.h` L41-57），而 DB 是 `BIGINT UNSIGNED`；读出来是 `getUInt64` 再截断进 `int`。这正是问34 里"溢出"隐患的真实来源，见 2.3。
- 客户端（`client/llfcchat/src/chatdialog.cpp` L226、L429-455）：登录后按会话列表逐个请求 `ID_LOAD_CHAT_MSG_REQ`，每个会话从 `message_id=0` 开始拉，即**从最旧往新拉一页**，没有"先拉最新 100 条"的实现。
- day37 文档 L14-18 明确写着"客户端本地数据库缓存已经接受的消息（以后再做）""客户端目前只发送消息 id 为 0"。与代码一致：**本地持久化和差异化加载尚未落地**。

**差距与改进建议**

1. **先把缺陷修掉**（工作量小、收益大）：给 `LoadChatMsg` 补上 `LIMIT N+1` 的 `load_more/next_cursor` 处理；`page_size` 从 10 调整为 50~100（与服务端限流口径一致）。
2. **补"最近 N 条"入口**：进入会话时先发 `ORDER BY message_id DESC LIMIT 100`（或先拉会话摘要 + 最近一屏），而不是从 `message_id=0` 正序拉。这是与面经口径对齐的关键。
3. **客户端补 gap 检测**：内存里按会话记录 `max_continuous_msg_id`，收到推送的 `message_id` 不连续时主动走增量拉取。见 [离线消息、补拉与消息撤回](./离线消息、补拉与消息撤回.md) 2.1。
4. **口径统一**：面经里"100 条"与代码"10 条"不一致。要么改代码，要么回答时说"当前 demo 是 10 条一页，生产上按一屏 50~100 条设计"——不能两头对不上。

**追问预判**

- 问：`ORDER BY message_id DESC LIMIT 100` 会不会把整个会话的数据都排一遍？→ 答：不会，`(thread_id, message_id)` 索引上 `thread_id` 等值定位后，`message_id` 在索引内有序，优化器可以从范围尾部反向扫描 100 条就停（`LIMIT` 下推），没有 filesort 和全量排序。可以用 `EXPLAIN` 验证 `key=idx_thread_message, Extra` 里没有 `Using filesort`。
- 问：如果分库分表了，全局自增 id 还有吗？→ 答：没有了，换雪花 ID 或号段模式，客户端排序和服务端一致（雪花高位时间有序）；会话内再补一个 `thread_seq`，见 2.7。
- 问：两个人同时发消息，谁在前？→ 答：以服务端落库分配的 `message_id` 为准，不信任客户端时间；客户端本地先用临时消息展示，收到 ACK 后按权威 id 归位。
- 问：分页拉取时来了新消息会不会乱？→ 答：不会，增量用 `> cursor` 向上追平，历史用 `< cursor` 向下翻，两个方向都不会被新消息顶偏；offset 才会。

### 2.2 多益网络一面 问33：消息表怎么设计、主键是什么

**面试官原话（转写）**

> "你觉得比如说消息表在数据库里面，你会怎么去做设计呢？比如说它的主键你觉得是什么？"

**当时的回答（压缩要点）**

- 主键用**自增消息 id**，让它持续增长；
- 表里要有发送者 id、接收者 id、会话 id、消息内容、消息状态、消息时间。状态：⚠️ 方向正确但太浅——没有索引、没有幂等唯一键、没有状态枚举说明、没有冷热考虑。

**考点分析**

这是"消息表全家桶"的入口题，面试官想确认：

- 主键选型依据（单调、聚簇索引顺序写）；
- 必备字段与可选字段（哪些字段该进主表、哪些该拆表）；
- 索引设计（按会话+序号查询、未读统计）；
- 幂等键（防重）和查询性能（消息表是增长最快的表）。

**可直接背的参考回答（口语化）**

> 消息表我会设计成"一个会话的主存储 + 几个辅助表"。
>
> 主表 `chat_message` 的核心字段是：自增主键 `message_id`、会话 `thread_id`、发送者 `sender_id`、接收者 `recv_id`、消息类型 `msg_type`、内容 `content`、状态 `status`、创建/更新时间。主键用 `BIGINT UNSIGNED AUTO_INCREMENT`，原因是 InnoDB 聚簇索引按主键顺序插入，自增能保证顺序写、页分裂少；而且它天然单调，可以直接当"会话内排序游标"和"增量同步游标"用。
>
> 但只有自增行情还不够，我会补三样东西：
>
> 第一，`UNIQUE KEY (sender_id, client_uuid)` 做幂等。客户端发消息前生成 UUID，重试发送时同一个 UUID 落库会命中唯一键，服务端 `INSERT ... ON DUPLICATE KEY UPDATE` 或捕获冲突后查回原消息，保证"同一条消息只落一次"。面试时 OPPO 问17/18 我讲过 `on duplicate key`，但项目里其实还没加这个唯一索引，这是我后面要补的。
>
> 第二，`KEY (thread_id, message_id)` 复合索引，所有"拉某个会话的消息"的查询都靠它：等值 `thread_id` + `message_id` 范围/排序，避免回表和 filesort。
>
> 第三，状态字段语义要定死。建议 0=正常、1=已撤回、2=已删除，或者用独立的 `revoked_at` 字段；"已读"不要放在消息行上，用独立的已读游标表，否则每个成员读一次就更新一次消息行，写放大严重——群聊尤其致命。
>
> 附件类消息不把二进制塞进主表，存 `message_attachment`（message_id、file_url、file_type、file_size），主表 content 存摘要或缩略信息。
>
> 长期还要考虑冷热分层：热表保留近 3 个月，旧消息归档到历史表/按月分区，见 2.7。

**技术要点拆解**

| 设计点 | 推荐做法 | 理由 |
|---|---|---|
| 主键 | `BIGINT UNSIGNED AUTO_INCREMENT`（单库） | 顺序写、单调、可当游标；注意不要在应用层用 32 位 int 接 |
| 幂等 | `UNIQUE(sender_id, client_uuid)` | 客户端重试、网络重发去重；与 [消息可靠传输与幂等去重](./消息可靠传输与幂等去重.md) 打通 |
| 查询索引 | `(thread_id, message_id)` | 等值+范围+排序一条索引全包 |
| 时间字段 | `created_at DATETIME(3)` | 毫秒级，用于展示与冷热归档；排序权威仍是 message_id |
| 状态 | `status` + 独立 `message_read_cursor` | 撤回/删除是低频更新；已读是高频、按人维度，不应更新消息行 |
| 附件 | 拆 `message_attachment` | 主表瘦身，TEXT/blob 分离 |
| 群聊 | `group_chat_member` + `recv_id=0`，投递靠成员表扇出 | 当前项目未实现群聊（day37 有表结构，客户端 `slot_load_chat_thread` 跳过 group，`chatdialog.cpp:335`） |

**当前项目实现对照**

- 实际 DDL（`sql备份/llfc2.sql` L24-36）与 day37 文档 L67-80 一致，主键、双索引都在；**但没有 `client_uuid`/`unique_id` 列，也没有唯一索引**——`unique_id` 只存在于内存结构 `ChatMessage`（`data.h` L46）和协议 JSON 中，落库时被丢弃。所以 OPPO 面试里说的 `on duplicate key` 在服务端目前**没有实现**（`MysqlDao::AddChatMsg` L863-923 是普通 INSERT）。
- `status` 语义混乱：DDL 注释是 `0=未读 1=已读 2=撤回`（llfc2.sql L32），服务端 `DealChatTextMsg` 对**所有**文本消息写 `status=2`（`LogicSystem.cpp` L506），而客户端 `global.h` L163-167 的 `MsgStatus` 是 `0=对方未读 1=发送失败 2=对方已读`。结果是"服务端刚 ACK 的消息"在客户端显示成"已读"（`MoveMsg` 里直接 `SetStatus(2)`），和 DDL 注释的"撤回"也对不上。这是必须修的语义债。
- day37 文档还有"可选扩展"：`message_attachment`、`message_read` 表都只停留在文档里，代码未建表。状态：⚠️ 设计有雏形，落地不完整。

**差距与改进建议**

1. 给 `chat_message` 加 `client_uuid VARCHAR(36)` + `UNIQUE(sender_id, client_uuid)`，客户端发送时已经生成了 `QUuid`（master `client/llfcchat/src/chatpage.cpp` L158 生成、L186 写入协议；Season_2 在 `chat/chatpage.cpp` L492 生成 client_message_id），只差落库。
2. 统一 status 语义：建议服务端存 `status=0` 正常，撤回用 `revoked_at`；客户端发送状态（发送中/已落库/已送达/已读）放本地表，不混用一个字段。
3. 群聊消息的 `recv_id` 约定要写清楚（建议 0 或群 id），否则后续未读/已读统计全乱。

**追问预判**

- 问：为什么不用消息内容做哈希当主键？→ 内容可重复、可修改，不能做唯一键；用发送者 + 客户端 UUID 更稳。
- 问：消息表大了怎么办？→ 先按 `thread_id` 聚集查询保持不变，再按时间归档/分区；跨库时全局 ID 换雪花，热点会话单分片，见 2.7。
- 问：一条消息两万人群发怎么落库？→ 消息主表只落一条（群维度），用户维度的收件箱/未读用异步扇出或读时计算，不能一行复制两万份。
- 问：删除是物理删还是标记删？→ 标记 `status/deleted_at`，保留行便于多端同步与审计；物理清理靠归档任务。

### 2.3 多益网络一面 问34：除自增外的 id 设计、自增的问题

**面试官原话（转写）**

> "那你觉得消息 id 为例，除了自增之外还有什么其他的一些设计吗？或者说自增 id，你们可能会遇到一些问题？"

**当时的回答（压缩要点）**

- 先答"发送者 id + 会话 id 当主键"→自己当场否掉；
- 然后说自增是 **uint32，32 位会溢出，超了要删旧消息**；
- 最后改成"客户端生成 UUID + 发送者 id 联合主键"。状态：⚠️ 临场自我纠正成功，但**"uint32 溢出"这个理由是错的**（MySQL 自增常用 BIGINT UNSIGNED，上限约 1.8×10^19；uint32 上限约 42.9 亿，是应用层类型选择问题，不是自增机制本身的问题）。这个回答会让面试官觉得对 ID 体系理解不牢。

**考点分析**

- 自增 id 的真实优缺点（单库有序 vs 分库分表不可用、暴露业务量、迁移困难）；
- 分布式 ID 备选：UUID、雪花、号段、Redis INCR、数据库多实例步长；
- 消息唯一键（幂等键）和消息主键是**两回事**：主键可以用自增，唯一键用 `(sender_id, client_uuid)`——两者不冲突。

**可直接背的参考回答（口语化）**

> 自增 id 的优点是简单、单调、写入快，单库单表场景是最优解，我们项目现在就是 `BIGINT UNSIGNED AUTO_INCREMENT`。
>
> 它真正的问题有三个，不是"32 位溢出"：第一，**分库分表后各库自增会撞**，全局不再唯一，跨库也拿不到全局单调顺序；第二，**会暴露业务量**，竞对看到 id 能估算订单/消息规模；第三，**数据迁移和合并多实例时容易冲突**，历史数据导入要么重排要么改映射。
>
> 所以分布式场景我会换成三种方案之一：一是**雪花 ID**，64 位里放时间戳 + 机器号 + 序列号，全局唯一且大体按时间有序，缺点是依赖时钟，时钟回拨要做保护；二是**号段模式**，用一张表或 Redis 按段发号，批量取 1000 个缓存在内存，减少数据库交互；三是 **UUID/ULID**，本地生成不依赖中心，但无序、占空间，做 MySQL 主键会导致页分裂。
>
> 但更重要的认知是：**消息主键和幂等键要分开**。主键用自增（或雪花）保证存储友好；幂等键用客户端 UUID + 发送者 id 建唯一索引，保证重试不重复。我当时面试说"UUID + 发送者 id 做联合主键"，方向对了一半——它应该是唯一索引，不是主键。另外注意：MySQL 的 `BIGINT` 是 64 位，我们项目真正有点风险的是**应用层把 `message_id` 声明成了 `int`**（32 位），读 `BIGINT` 时会截断，这个要改成 `uint64_t`。

**技术要点拆解**

- 各方案对比：

| 方案 | 有序性 | 唯一性保证 | 缺点 | 适用 |
|---|---|---|---|---|
| 单库自增 | 强（单库） | 数据库 | 分库失效、暴露业务量 | 单库/早期 |
| 雪花 ID | 时间趋势有序 | 机器号+序列 | 时钟回拨、机器号分配 | 分库分表主流 |
| 号段模式 | 段内有序 | 中心发号 | 中心依赖、段浪费 | 高 QPS 发号 |
| Redis INCR | 单分片有序 | Redis | 持久化/重启、集群分片 | 轻量发号 |
| UUIDv4 | 无序 | 概率唯一 | 主键页分裂、占 36 字节 | 幂等键 |
| UUIDv7/ULID | 时间前缀有序 | 概率唯一 | 生态支持待观察 | 新系统幂等键 |

- 面试延伸：为什么 MySQL 主键要短且有序？InnoDB 聚簇索引叶子就是数据行，主键无序会随机插入造成页分裂、缓存命中率差；二级索引叶子存主键，主键越长所有二级索引越大。
- "溢出"的正确定位：如果存储用 `INT UNSIGNED`，42.9 亿条消息确实会溢出，**那说明选型时就该用 BIGINT**；自增机制本身不会溢出（会报 `1467: Failed to read auto-increment value`），更不需要删旧消息——旧消息是归档，不是删除。

**当前项目实现对照**

- DB：`message_id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT`（llfc2.sql L25），选型没问题。
- 应用层：`server/ChatServer/include/data.h` L42 `int message_id;`、L56 `int next_cursor;`；`MysqlDao.cpp` L841 `rs->getUInt64("message_id")` 塞进 `int`；JSON 传输 `chat_msg["message_id"] = chat_data->message_id`（`LogicSystem.cpp` L517）。链路里全是 32 位，**存在真实截断风险**。这就是"uint32 溢出"焦虑的来源，但答案不是换 UUID，而是把类型改对。
- 客户端 `chatpage.cpp` 用 `QUuid` 生成 `unique_id` 并随消息发送；服务端 `DealChatTextMsg` 接收后放进内存结构，但 `AddChatMsg` 落库时没有该列。幂等键"有输入、没落地"。

**差距与改进建议**

1. `ChatMessage` 的 `message_id/thread_id/sender_id/recv_id/next_cursor` 全部改 `uint64_t/int64_t`，JSON 也统一按 64 位处理。
2. 落库 `client_uuid` 并加唯一索引，把"幂等"从面试话术变成可演示功能。
3. 面试话术修正：主动说"自增的问题主要是分库分表、业务量暴露、迁移，而不是位数；位数是我应用层类型没选对"。展示自我修正能力比背诵更强。

**追问预判**

- 问：雪花 ID 时钟回拨怎么办？→ 答：回拨小（毫秒级）就等待追平；回拨大就拒绝发号或切备用机器号，并告警；机器号用 etcd/Redis 分配。
- 问：为什么不用 UUID 做 MySQL 主键？→ 答：无序 + 36 字节，插入随机导致页分裂，二级索引膨胀。
- 问：64 位 ID 前端（JSON/JS）精度丢失？→ 答：这个坑真实存在，雪花 ID 超过 2^53 时 JS Number 会丢精度，所以协议里要用 string 传。
- 问：自增 id 连续会不会被爬？→ 答：会有遍历风险，接口加权限校验；也可以对展示 ID 做混淆，但内部主键保持有序。

### 2.4 OPPO二面 问6：分页按什么分页

**面试官原话（转写）**

> "对我们一次不全拉你，你这个分页是按什么分页的？"

**当时的回答（压缩要点）**

- "按消息的数量，每条消息有一个标准的序列号，按序列号去拉，先拉最新的 100 条。"状态：✅ 方向正确，但**与项目实现矛盾**：实际代码是 `message_id > cursor ASC` 从旧往新拉，而且每次 10 条；"先拉最新"目前没有实现。

**考点分析**

- 分页键的选择：数量分页（`LIMIT N`）其实必然附带一个排序键；面试官真正问的是**"用什么游标"**；
- 游标 vs offset（已在 2.1 展开）；
- 增量和历史两个方向的区分；
- 服务端返回 `has_more` 和 `next_cursor` 的工程约定。

**可直接背的参考回答（口语化）**

> 按"会话内消息序号 + 数量"分页，本质是游标分页，不是 offset。
>
> 具体来说，每条消息有服务端分配的全局自增 `message_id`，它在同一个会话里也是严格递增的，所以我把它当游标。三类请求：
>
> - 首次进入：`WHERE thread_id=? ORDER BY message_id DESC LIMIT 100`，拿最近 100 条，客户端反转成升序；
> - 向上翻历史：带当前最旧的 `message_id`，`message_id < cursor ORDER BY message_id DESC LIMIT 20`；
> - 断线补拉：带本地最大的 `message_id`，`message_id > cursor ORDER BY message_id ASC LIMIT 100`。
>
> 服务端每次多取一条判断 `has_more`，同时返回 `next_cursor`。这样无论消息怎么新增、会话里有多少条，单次查询的代价都是固定的，不会随页码变深而变慢。

**技术要点拆解**

- "按数量分页"和"按游标分页"不冲突：`LIMIT` 是数量，`WHERE message_id > ?` 是游标；面试时最好主动区分，避免被"你这不就是 limit 吗"追问打穿。
- 页面大小：一屏消息约 20 条，首次可以预取 50~100；翻页 20~50。项目现在固定 10 条太小，一屏要多次请求。
- 会话内序号：单库自增全局 `message_id` 在会话内天然递增，可以直接当会话序号；分库分表时要加 `thread_seq`，见 2.7。
- 顺序权威在服务端：即使客户端本地时间乱，落库顺序就是最终顺序；两人同时发消息，先落库的 `message_id` 小。

**当前项目实现对照**

- 服务端只有"增量"这一种 SQL（`MysqlDao.cpp` L818-826），`page_size=10`（`LogicSystem.cpp` L889）；没有"最近 N 条"和"向上翻页"入口。day37 文档 L434-444 的"游标模式 vs OFFSET"讲解和 `GetUserThreads` 的 `N+1` 实现都说明作者知道正确做法，但消息分页没跟上。
- 客户端 `chatdialog.cpp` L429-455：`load_more` 为 true 时继续用当前 `last_msg_id` 请求——由于服务端从来不返回 true，这一段是死代码。
- 结论：面试口径（先拉最新 100、翻页继续拉）目前属于"设计"，不是"已实现"。要么尽快实现，要么回答时明确说"当前 demo 是全量按序拉一页，生产方案是游标三分法"。

**差距与改进建议**

1. 服务端新增/改造接口：`LoadLatest(thread, 100)`、`LoadBefore(thread, cursor, 20)`、`LoadAfter(thread, cursor, 100)` 三个方向，或一个接口带 `direction` 参数。
2. 用 day37 `GetUserThreads` 的写法修复 `LoadChatMsg` 的 `load_more` 逻辑（这是现成的正确模板）。
3. 页面大小配置化：会话首次 100、翻页 20、补拉 100，避免硬编码 10。

**追问预判**

- 问：为什么不按时间分页？→ 答：时间可能重复、可能被客户端伪造，且时间不在联合索引的查询前缀里；`message_id` 唯一且有序。时间只用于展示。
- 问：如果用户要跳转到某一天？→ 答：先用 `created_at` 索引定位那天的最小 `message_id`，再转成游标查询。
- 问：多人同时在一个会话发消息，会话内顺序怎么保证？→ 答：全部以服务端落库分配的 `message_id` 为准；服务端单库自增保证全序，客户端只做展示排序。

### 2.5 OPPO二面 问7：本地存储按用户分类还是全局序列号

**面试官原话（转写）**

> "那你这个消息在本地存储在客户端的时候，你是按用户分类存的呢，还是说全部按序列号顺序存在一起的？"

**当时的回答（压缩要点）**

- "每一个用户会单独维护他自己的消息内容，不同的用户之间不共享序列号。"状态：⚠️ 方向对但概念不精确：把"会话"说成了"用户"，把"游标"说成了"序列号"。

**考点分析**

面试官在问客户端本地存储的分区策略：

- 消息在本地按什么维度组织（会话 / 时间线 / 混合）；
- 服务端全局 ID 和本地序号的映射关系；
- 多会话并发下拉取/去重/排序怎么做；
- 离线消息、撤回、已读状态如何落到本地。

**可直接背的参考回答（口语化）**

> 客户端本地我用 SQLite，消息表按**会话**组织，而不是按人。表结构大概是 `messages(message_id PRIMARY KEY, thread_id, sender_id, msg_type, content, status, created_at)`，再加 `INDEX(thread_id, message_id)`。因为"用户"只是会话的一个参与者，群聊里一条消息会关联很多人，用用户维度会重复存储。
>
> 全局 `message_id` 是服务端分配的、全局唯一的，所有会话共用同一套 ID 空间；本地额外给每个会话维护一个**同步游标**：`thread_cursor(thread_id PRIMARY KEY, last_synced_msg_id, last_read_msg_id)`。这样：
>
> - 增量同步时遍历游标表，只拉 `message_id > last_synced_msg_id` 的消息，天然按会话并行、互不干扰；
> - 未读数 = 会话最新 `message_id` 与 `last_read_msg_id` 之间的差值；
> - 去重直接用 `message_id` 主键 `INSERT OR IGNORE`；
> - 撤回等操作事件也带上 `message_id`，按同一套顺序应用。
>
> 所以结论是：**服务端全局一套 ID，客户端按会话分区存、按会话维护游标**。我当时说"每个用户单独维护、不共享序列号"，意思接近，但表述成"会话 + 游标"更准确，也不容易被追问绕晕。

**技术要点拆解**

- 为什么全局 ID 好：跨会话唯一、跨端一致、天然去重；如果客户端自己按会话造序列号，换设备/重装后与服务端对不上。
- 为什么本地按会话分区好：查询总是"打开某个会话的历史"，`(thread_id, message_id)` 是唯一高频访问路径；按时间全局排序本地无意义。
- 游标表是本地和服务器对齐的"账本"：登录同步、gap 补拉、未读统计都读它。
- 多端场景：每台设备各是一份本地库，服务端才是权威；设备之间靠各自游标补拉保持一致，见 [多端登录互斥与在线状态](./多端登录互斥与在线状态.md)。

**当前项目实现对照**

- **客户端没有本地数据库**：全仓 grep 无 `QSqlDatabase/QSqlite`；消息只存在内存 `ChatThreadData::_msg_map`（`client/llfcchat/include/userdata.h` L202-234），进程退出即丢。day37 文档 L14 也写着本地库"以后再做"。
- 客户端已有会话内"最后一条消息 id"的概念：`ChatThreadData::_last_msg_id` 和 `UserMgr::GetLastChatThreadId`（day37 L2443 起为 GetCurLoadData 增量加载逻辑、L893 为 GetLastChatThreadId），但它是从 0 开始拉、拉完即用，没有落盘。
- 服务端全局 ID 已存在（自增），但 `next_cursor` 更新缺失（见 2.1），"增量"链路还不完整。

**差距与改进建议**

1. 引入 SQLite 本地库（Qt 的 `QSqlDatabase`），先落三张表：`messages`、`thread_cursor`、`outbox`（待发/待重试），本地库设计见 2.7。
2. 登录流程改为"本地渲染 + 会话游标增量补拉"，替换现在"内存全量重建"的做法。
3. 明确未读字段 `last_read_msg_id`，为后续未读数/已读回执打基础，见 [离线消息、补拉与消息撤回](./离线消息、补拉与消息撤回.md) 2.6。

**追问预判**

- 问：两个会话的消息在本地怎么排序展示？→ 答：本地只服务单个会话窗口；会话列表按各会话最后一条消息的 `message_id`/时间排。跨会话全局时间线不是 IM 的查询模式。
- 问：本地库和服务端不一致怎么办？→ 答：服务端权威，本地只是缓存；对账时用会话游标向上/向下拉齐，冲突以服务端行覆盖本地行（`INSERT OR REPLACE` 或按字段合并）。
- 问：消息多了本地库会爆吗？→ 答：按会话保留最近 N 条或按时间裁剪，图片视频只存缩略图和路径；也可加 TTL 清理任务。

### 2.6 科大讯飞一面 问10：相对大型 IM 的优化方向（存储侧压力与架构取舍）

**面试官原话（转写）**

> "相对大型 IM 系统，你还有哪些要优化？"

**当时的回答（压缩要点）**

- 微信消息主存客户端，服务端不是消息内容的完全可靠存储，服务器存储压力小很多；
- 我的系统所有客户端消息的权威存储都在服务端，这是压力点；
- 目前只做了聊天服务水平扩展，负载均衡还很简单。状态：✅ 认知正确、取舍说得清楚；但只点了"压力点"，没给出"怎么减压"的系统方案，停留在现象层。

**考点分析**

这是一道开放题，面试官想听的是**架构判断力**：

- 存储权威放在客户端还是服务端的取舍（一致性/可靠性 vs 成本/压力）；
- 消息存储容量与写入放大（fan-out）的关系；
- 大型 IM 真正的手段：分层存储、多级缓存、收件箱/写扩散、读写分离、冷热分离、端云协同。

**可直接背的参考回答（口语化）**

> 我认为核心取舍是**"服务端权威存储 + 客户端缓存"还是"端存为主"**。微信选择消息主存端上，服务端只保留短期的可靠投递能力和有限的漫游，好处是存储成本和隐私压力大幅下降，代价是换设备/漫游依赖同步链路，端上丢数据就丢了。我的系统选择服务端权威存储，好处是可靠、可漫游、可审计，坏处就是面试官听到的：**所有消息的写入和查询压力都压在 MySQL 上**。
>
> 如果继续优化，我会分四层做：
>
> 第一层，**写入减压**：消息落库只落一条主记录，群聊不要按成员复制行；写路径少做事务、少做跨表更新；幂等唯一键让重试不产生重复写。热点会话可以异步批量落库，但每条消息要有明确的"已持久化"点才回 ACK。
>
> 第二层，**读取减压**：会话列表和未读数走 Redis 或预计算表，不实时 `COUNT`；历史消息走 `(thread_id, message_id)` 索引游标，只读必要的页；服务端读接口做限流和缓存首屏。
>
> 第三层，**冷热分层**：热表只保留近 3 个月，老消息按月归档/分区，查询冷数据走归档表；媒体文件本来就在资源服务/对象存储，不进消息表。
>
> 第四层，**端云协同**：客户端本地 SQLite 缓存全部历史，服务端只做增量和近端历史；这样大部分历史查询根本不打服务端——这其实就是在向"微信模式"靠拢，但服务端仍然是权威副本，兼顾可靠性和减压。
>
> 另外要承认现状：我们只做了同构聊天服务的水平扩展，负载均衡是最小连接数，存储层还是单 MySQL，没有分库分表、没有读写分离，这些是下一步的瓶颈点。

**技术要点拆解**

| 压力来源 | 现象 | 对策 |
|---|---|---|
| 单表无限增长 | 消息表几亿行，索引变大 | 按月分区 + 热表/归档表，`created_at` 归档任务 |
| 写放大 | 群聊按成员复制、每读一次更新 status | 主表只落一条；已读用游标表，不更新消息行 |
| 读放大 | 每次会话列表 COUNT 未读、深分页 | 未读预计算/Redis；游标分页；首屏缓存 |
| 高可用 | 单 MySQL/单 Redis 是单点 | 主从 + 读写分离；Redis 哨兵/集群（OPPO 问8-10 已答过） |
| 冷数据 | 老消息查询少但占空间 | 归档到历史表/对象存储，按需加载 |

- 关于"端存为主 vs 服务端权威"：不是非黑即白。工业界常见的是"服务端保存有限时段 + 端上长期保存"，服务端可靠性用来保证投递，端上负责长期记忆。面试里主动给出这个折中点是加分项。

**当前项目实现对照**

- 服务端权威存储的设计意图已实现：文本消息统一落 `chat_message`（`LogicSystem.cpp` L511-512、`MysqlDao.cpp` L863-923）；但 master 代码未检查 `AddChatMsg` 返回值（`LogicSystem.cpp:512`），落库失败也会回 ACK——"先落库再 ACK"目前只对 Season_2 成立（详见《消息可靠传输与幂等去重》2.2）。
- 无冷热分层、无归档、无分区；无未读预计算；会话列表查询 `GetUserThreads` 已经是游标分页（好）。
- 客户端无本地持久化（见 2.5）→ 意味着当前架构是"纯服务端权威"，压力最大的一种形态。
- 资源（文件）消息在 master 只有 day31/day38 课程文档与设计，**没有 ResourceServer 代码**；Season_2 才实现 ResourceServer + 断点续传，做到"媒体不进消息表"，方向正确；见 [断点续传与文件消息](./断点续传与文件消息.md)。
- 单机 8000 稳定连接是 day30/讯飞问1 的口径；注意这与虾皮追问的"8.3 万 QPS"是不同项目的数据，别混用。

**差距与改进建议**

1. **先解决"每次登录全量拉消息"**：目前客户端每次登录都为每个会话拉消息（day37 L468 说"默认每次用户登录都请求所有 thread_id"，消息同理），没有本地库和增量游标。补上本地 SQLite + 游标增量后，服务端读压力会数量级下降。
2. **未读预计算**：新建 `chat_thread_stat(thread_id, user_id, last_read_msg_id, last_msg_id)` 或 Redis hash，登录只返回计数，点开才拉消息体。
3. **加一个归档脚本/表**作为项目亮点：把 `created_at < 3 个月前` 的消息迁移到 `chat_message_archive`，演示冷热分离。
4. 面试时把"微信端存为主"从"别人的做法"讲成"我的下一步"：本地 SQLite 已列计划 + 服务端仍保权威，形成完整取舍叙事。

**追问预判**

- 问：端上存了消息，多端怎么同步？→ 答：每端有自己的本地游标，服务端保留足够时长的消息和操作事件，新设备走全量分页同步、老设备走增量补拉；服务端的权威窗口可以按业务定（如 30 天）。
- 问：服务端只保存 30 天，用户要查更早的记录怎么办？→ 答：归档层/对象存储 + 按需异步加载，前端显示"加载更早消息"；或者像微信一样提示端上已有。
- 问：为什么不直接上分库分表？→ 答：先测量再分层。当前单表量和 QPS 未到瓶颈，分库分表会引入全局 ID、跨分片查询、分布式事务成本；先做冷热分层和读写分离，性价比更高。
- 问：Redis 挂了未读数怎么恢复？→ 答：Redis 只是加速层，权威 `last_read_msg_id` 定期落库，重启后从库重算，见 [Redis使用与高可用设计](./Redis使用与高可用设计.md)。

#### 2.7.1 推荐消息表 DDL（含索引）

```sql
CREATE TABLE `chat_message` (
  `message_id`  BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '全局唯一、单调递增，兼作会话内排序与增量游标',
  `thread_id`   BIGINT UNSIGNED NOT NULL COMMENT '会话ID（私聊/群聊统一）',
  `thread_seq`  BIGINT UNSIGNED NULL DEFAULT NULL COMMENT '会话内序号（分库分表时才需要；单库可空）',
  `sender_id`   BIGINT UNSIGNED NOT NULL,
  `recv_id`     BIGINT UNSIGNED NOT NULL DEFAULT 0 COMMENT '单聊=对端uid；群聊=0或群id，按约定',
  `client_uuid` CHAR(36) NOT NULL COMMENT '发送端生成的幂等ID',
  `msg_type`    TINYINT NOT NULL DEFAULT 0 COMMENT '0文本 1图片 2文件 3语音',
  `content`     TEXT NOT NULL,
  `status`      TINYINT NOT NULL DEFAULT 0 COMMENT '0正常 1已撤回 2已删除',
  `created_at`  DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  `updated_at`  DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
  PRIMARY KEY (`message_id`),
  UNIQUE KEY `uniq_sender_uuid` (`sender_id`, `client_uuid`),
  UNIQUE KEY `uniq_thread_seq` (`thread_id`, `thread_seq`),
  KEY `idx_thread_msg` (`thread_id`, `message_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

说明：

- 单库阶段：`message_id` 全局自增，会话内天然递增，`thread_seq` 保持 NULL，`uniq_thread_seq` 对 NULL 不生效。
- 分库分表阶段：`message_id` 换雪花（保证大体时间有序）；`thread_seq` 由服务端按会话发号（Redis INCR 或号段），排序权威切到 `(thread_id, thread_seq)`。
- 附件表与已读表：

```sql
CREATE TABLE `message_attachment` (
```

#### 2.7.2 三类拉取 SQL 示例（可直接背）

```sql
-- ① 进入会话：最近 100 条（客户端反转成升序展示）
SELECT message_id, thread_id, sender_id, recv_id, msg_type, content, status, created_at
FROM chat_message
WHERE thread_id = ?
ORDER BY message_id DESC
LIMIT 100;

-- ② 向上翻历史：取比"当前最旧"更旧的 20 条；多取一条判断 has_more
SELECT ...
FROM chat_message
WHERE thread_id = ? AND message_id < :oldest_msg_id
ORDER BY message_id DESC
LIMIT 21;                       -- 应用层：若 21 条 → has_more=true，丢弃最后一条

-- ③ 登录/断线补拉：从本地游标往后追平
SELECT ...
FROM chat_message
WHERE thread_id = ? AND message_id > :local_max_msg_id
ORDER BY message_id ASC
LIMIT 100;

-- ④（可选）未读总数：用游标差值，不 COUNT
SELECT MAX(message_id) AS max_msg_id
FROM chat_message WHERE thread_id = ?;
-- unread = max_msg_id - last_read_msg_id 的区间内还需要扣除自己发的，简单场景可用计数表
```

> 项目现状模板：`MysqlDao::GetUserThreads`（L642-720）已经实现了 ② 的 `N+1 + pop_back + next_cursor` 逻辑，把同一套代码复制到 `LoadChatMsg` 即可修复当前缺陷。

#### 2.7.3 会话内序号 vs 全局序号

| 维度 | 全局序号（message_id） | 会话内序号（thread_seq） |
|---|---|---|
| 谁分配 | 数据库自增 / 雪花 | 服务端按会话发号（Redis INCR/号段） |
| 保证 | 全局唯一、全库有序 | 同一会话内连续递增 |
| 用途 | 主键、幂等参照、跨会话增量同步 | 会话内排序、未读区间、消息 gap 检测、客户端按序渲染 |
| 单库阶段 | 可直接兼任会话内序号（全局递增 ⇒ 会话内递增） | 可不建 |
| 分库分表 | 自增失效，换雪花后仅时间趋势有序 | 必需，业务排序/未读全靠它 |

- **实践建议**：当前单 MySQL 项目用"全局 `message_id` 兼具会话内序号"就够了，面试时说明"分库分表引入雪花 + thread_seq"的演进路径即可，不要一上来堆复杂度。
- **排序权威**：永远以服务端落库分配的序号为准；客户端本地时间是展示字段，不作为排序依据（讯飞问11/12 踩过这个坑）。

#### 2.7.4 深分页问题与优化

- `LIMIT 100000, 20` 的问题：先扫描并丢弃前 10 万行，还要回表；页码越深越慢；期间有新消息插入会导致分页漂移（重复/漏读）。
- 优化手段排序（面试按这个顺序讲）：
  1. **游标分页（首选）**：`WHERE message_id < :cursor ORDER BY message_id DESC LIMIT 20`，每页成本恒定。
  2. **延迟关联**（必须用 offset 时）：`SELECT m.* FROM chat_message m JOIN (SELECT message_id FROM chat_message WHERE thread_id=? ORDER BY message_id DESC LIMIT 100000,20) t USING(message_id)`，让子查询走覆盖索引，减少回表。
  3. **禁止跨页跳转**：IM 场景产品上就没有"跳到第几页"，天然适合游标。
  4. **业务降级**：超过 N 页只允许按时间/关键字检索（走归档或搜索服务）。
- 追问"为什么 `OFFSET` 不能靠加索引解决"：索引只是让扫描变快，但被丢弃的行数没变；游标才是把复杂度从 O(offset) 降到 O(page)。

#### 2.7.5 冷热数据分层与归档

- 分级模型：
  - **热**：最近 1~3 个月，单表控制在千万级以内；`chat_message` 只存热数据；
  - **温**：`chat_message_archive` 按 `created_at` 月分区或按月独立表；
  - **冷**：对象存储/导出文件，仅合规审计或按需异步加载。
- 归档任务：定时（如每天凌晨）`INSERT INTO archive SELECT ... WHERE created_at < ? LIMIT 批量`，再删热表数据；用 `message_id` 游标分批，避免大事务。
- 查询路由：拉历史时先查热表；不足一页再查归档表，对上层透明（或由服务端拼页）。
- 分库分表演进：先按 `thread_id` 哈希分片（保证单会话查询落单分片），再考虑时间分片；热点群聊单独分片/降级。
- 面试话术："我不是先上分库分表，而是先把冷热分离做掉，因为 90% 的查询只碰最近的数据，归档的成本远低于分布式改造。"

#### 2.7.6 客户端本地存储方案（SQLite 表设计建议）

```sql
-- 本地消息表：服务端 message_id 做主键，天然去重
CREATE TABLE IF NOT EXISTS messages (
  message_id  INTEGER PRIMARY KEY,          -- 服务端全局ID（SQLite 用 64 位 INTEGER）
  thread_id   INTEGER NOT NULL,
  sender_id   INTEGER NOT NULL,
  msg_type    INTEGER NOT NULL DEFAULT 0,
  content     TEXT NOT NULL,
  status      INTEGER NOT NULL DEFAULT 0,   -- 0正常 1撤回 2删除（与服务端对齐）
  created_at  INTEGER NOT NULL,             -- 毫秒时间戳，仅展示
  sent_by_me  INTEGER NOT NULL DEFAULT 0
);
CREATE INDEX IF NOT EXISTS idx_messages_thread ON messages(thread_id, message_id);
CREATE INDEX IF NOT EXISTS idx_messages_sender ON messages(sender_id, message_id);

-- 会话游标：增量同步、未读数、gap 检测的账本
CREATE TABLE IF NOT EXISTS thread_cursor (
  thread_id          INTEGER PRIMARY KEY,
  last_synced_msg_id INTEGER NOT NULL DEFAULT 0,  -- 已连续同步到的最大ID
  last_read_msg_id   INTEGER NOT NULL DEFAULT 0,  -- 已读到的位置
  updated_at         INTEGER NOT NULL
);

-- 本地待发队列（outbox）：发送可靠性兜底
CREATE TABLE IF NOT EXISTS outbox (
  client_uuid TEXT PRIMARY KEY,             -- 与服务端幂等键一致
  thread_id   INTEGER NOT NULL,
  content     TEXT NOT NULL,
  state       INTEGER NOT NULL DEFAULT 0,   -- 0待发 1已发未ACK 2已ACK 3失败
  retry_cnt   INTEGER NOT NULL DEFAULT 0,
  next_retry_at INTEGER NOT NULL,
  created_at  INTEGER NOT NULL
);

-- 操作事件（取撤回）：上线后按事件流应用
CREATE TABLE IF NOT EXISTS events (
  event_id   INTEGER PRIMARY KEY,           -- 服务端事件序号
  thread_id  INTEGER NOT NULL,
  type       INTEGER NOT NULL,              -- 1=撤回 2=已读回执 3=删除
  payload    TEXT NOT NULL,
  applied    INTEGER NOT NULL DEFAULT 0
);
```

- 写入约定：收到消息/事件一律 `INSERT OR IGNORE`（message_id 主键去重）；更新游标用 `UPDATE thread_cursor SET last_synced_msg_id=? WHERE thread_id=? AND last_synced_msg_id<?` 防回退。
- 渲染约定：打开会话先读本地（秒开），再触发后台增量补拉；拉到的数据按 `message_id` 插入后局部刷新。
- 清理策略：按会话保留最近 N 条/最近 M 个月；媒体只留缩略图和本地路径。

## 3. 小结与行动项

**最值得注意的三个结论**

1. **虾皮问6 是纯硬伤**：项目里 `LoadChatMsg` 已有正确的索引与关键字，但缺 `load_more/next_cursor` 收尾、`page_size=10` 且没有"最近 N 条/向上翻页"入口——面试时按 2.1 的三段 SQL 背熟，能立刻把"未记录"变成强项。
2. **类型与语义债要主动认领**：`message_id` 链路 32 位 `int` 是真实隐患；`status` 在 DDL/服务端/客户端三处语义不一致（甚至把 ACK 当已读）。改掉它们比背更多八股更能体现工程严谨性（回应多益问34、OPPO 追问）。
3. **架构叙事要闭环**：讯飞问10 的"服务端权威存储压力大"必须接上"本地 SQLite + 会话游标增量 + 冷热分层 + 未读预计算"的解法，否则只描述问题不给方案，容易被判定为"项目是抄的、理解不深"。
