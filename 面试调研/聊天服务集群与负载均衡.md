### 2.1 讯飞一面·问1：单机支持多少用户？

**面试官原话（转写）**
> 问1：分布式即时通信系统有没有测过单机能支持多少用户？

**你当时的回答**
> 答1：之前因为后面又改了一次；之前测试过，两个聊天服务可以支持 8000 个用户稳定在线连接。

**状态：✅ 基本可以，但口径有硬伤。**

**考点分析**
- 面试官想听的不是一个数字，而是「数字 + 测试方法 + 瓶颈认知」三件套：怎么压的、压的是什么指标（连接数？QPS？延迟？）、瓶颈在哪里、怎么继续扩。
- 你的数字不够精确：只说「两个服务 8000」，没说单机/单进程、没说消息速率、没说延迟。而 `day30` 里写的是「单服务器支持 8000 连接，多服务器分布部署可支持 1W~2W 活跃用户」，9.20 华为主管面你说的又是「稳定 8000 用户、每秒 1K 消息」——三个口径互相矛盾，被追问就露馅。
- 「单机」这个词有歧义：是一个 ChatServer 进程，还是一台物理机上跑两个进程？面试官通常会追着这个点问。

**可直接背的参考回答**
> ⚠️ 口径提醒：下面这段 8000 的说法来自 day30 教程口径与面经记录，三处数字（单机 8000 / 双服务 8000 / 8000+1K msg/s）未统一，master 也没有当时的压测脚本（Season_2 的 `bench_run/` 没有 8000 档记录）；引用前请先按 [性能压测与容量扩展](性能压测与容量扩展.md) 的 Season_2 数据卡改造，或自己重测留证。
>
> 我们压测的口径是：**单台机器上一个 ChatServer 进程，稳定维持 8000 条长连接**；所有连接保持心跳、每秒互发一条文本消息（合计约 1K msg/s），收发延迟稳定、无掉线。当时两个 ChatServer 部署在同一台开发机上，双节点同时跑过，也没有掉线；理论上双节点是 1.6 万连接的容量，但我们没有把第二轮压满，所以对外我一般说「单机 8000、双机按 1.6 万规划」。
> 压测方式是自研的多线程压测客户端：定时建连 + ping-pong 心跳 + 统计收发时延和掉线率；服务端是 asio 异步模型，`io_context` 池按 CPU 核数起线程，所有连接异步读写，没有为每条连接开线程。
> 8000 不是连接数上限本身，这个量级的瓶颈主要是三块：**每连接的内存缓冲、fd 上限（要调 ulimit）、以及 IO/逻辑线程池的处理能力**。再往上扩就要分片、多进程、多机，所以我们做了 ChatServer 多节点 + StatusServer 调度，而不是死磕单机。

**技术要点拆解**
- asio Proactor 模型：每连接一个 `CSession`（shared_ptr 保活），异步读写 + 逻辑队列；线程池 `AsioIOServicePool` 按核数分配 `io_context`，连接按轮询分配线程。
- 每连接资源：socket fd + 头/包缓冲区 + session 对象 + 心跳时间戳；8000 连接的内存和 fd 占用要在面试里能估算（大致几 MB～几十 MB 级别，取决于缓冲大小；fd 需要 `ulimit -n` 调到 1w+）。
- 容量测试的三个维度（day30）：①连接上限；②固定连接数下的收发稳定性（P99 延迟）；③固定延迟下的连接数上限。**8000 属于「保证稳定收发」的口径，不是「压到崩」的口径**，这句话能显著提升可信度。
- 与水平扩展衔接：单机 8000 → 双节点 1.6 万 → 调度层按连接数/负载分配 → 这就是 day27 的设计动机。

**当前项目实现对照**
- 测试口径：`开发文档/day30-项目难点和面试技巧.md` 「如何测试性能」一节：单服务器 8000 连接、多服务器 1W~2W 活跃用户、10ms 延迟目标；华为主管面问27 补充了「每秒 1K 消息」。

### 2.2 讯飞一面·问5：已选聊天服务崩溃后，已发消息怎么处理？

**面试官原话（转写）**
> 问5：如果已经选了一个聊天服务，聊天服务崩溃了，其中一个用户已发送消息，但聊天服务崩了，怎么处理？

**你当时的回答（压缩要点）**
> 所有聊天服务和用户消息都可靠存储在唯一 MySQL 上，所有 ChatServer 都连这个 MySQL。分两种情况：
> 1）服务写 MySQL 过程中崩溃：写入未成功，不会回 ACK；客户端发现没收到 ACK 会持续重传，直到服务端确认。
> 2）消息已可靠写入 MySQL 后服务崩溃：发送方已认为成功；接收方如果不在这个服务上，可能不知道有这条消息。但接收方维护一个游标记录最新收到的消息序号，发现序号跳变（比如 36 → 38 缺 37）就向服务端补拉；同时客户端每 5 秒主动拉一次。

**状态：⚠️ 半对——框架正确，细节被 OPPO 二面继续追问（问3 事务、问4 重试上限、问16 补偿、问17 重复投递、问18 幂等）。**

**考点分析**
- 这题考的是「消息可靠性的完整闭环」：发送端 outbox、服务端事务落库、ACK、接收端游标补拉、去重，缺一环都会被追问。
- 你答对了主干：**MySQL 权威 + 无 ACK 重传 + 序号缺口补拉 + 定时兜底拉取**。但有几个点没有主动说：
  - 崩溃发生在「落库成功、ACK 已发、但推送给接收方失败」时，靠的是**接收方兜底拉取**而不是服务端重推（OPPO 问16 你补充过：服务端只发一次）。
  - 客户端重传的消息怎么去重？—— `unique_id + sender_uid` 作为唯一键做幂等插入（OPPO 问18 你答的是 `INSERT ... ON DUPLICATE KEY UPDATE`；代码实际情况见「当前项目实现对照」：master 没有这个唯一键，Season_2 是唯一键 + 事务内先查后插，不是 upsert）。
  - 重试次数没有上限（OPPO 问4 你自己承认了），应该说明「客户端 outbox 需要最大重试次数 + 失败标记 + 用户手动重发」。
  - 崩溃节点的连接迁移：节点心跳过期后不再被调度（问7），已连用户重连到新节点（问13），新节点从 MySQL 补数据。

**可直接背的参考回答**
> 这个链路里 MySQL 是唯一权威存储，ChatServer 全部无状态化——连接是状态，消息内容不是。所以分两条时间线：
> **第一条：崩溃发生在写 MySQL 的过程中。** 事务回滚，服务端不会回 ACK；客户端本地 SQLite 有 outbox，没收到 ACK 就按退避重发。重发可能重复到达，服务端用消息的唯一标识（发送者 uid + 消息唯一 ID）做**幂等插入**保证只落库一次，所以重复发送是幂等的。客户端 outbox 应该有最大重试次数（比如 3 次或一段时间），超了标记发送失败让用户手动发，不能无限重试。
> **第二条：消息已经落库，ACK 已发，但服务崩溃没推给接收方。** 发送方认为成功了；接收方靠自己的兜底机制发现：它本地维护每个会话的最新消息序号游标，发现自己拿到的序号不连续（36 后直接 38），就按缺口向任意一个在线的 ChatServer 补拉；另外还有兜底补拉（讯飞面说每 5 秒、OPPO 面说每 500ms 查一次最新序列号，两处口径不一致；代码里 Season_2 是事件序号增量同步 + 打开会话时拉取，没有定时轮询）。补拉回来的消息同样按唯一键去重。
> 还有两点：**崩溃节点上已建连的用户**由客户端断线重连处理——重新申请健康节点、重新鉴权、按游标补拉；**新消息的分配**因为节点心跳过期（2s 续期/6s TTL）自动从调度里摘掉，不会再有人被分过去。整个设计里服务端推送是「尽力而为只发一次」，可靠性的兜底放在接收端拉取，所以服务端不会因为要保证送达而积压大量重推任务。

**技术要点拆解**
- 可靠投递的两条经典路线：①服务端重推（Push 为主，需要 ack/重试队列/在线状态）；②服务端尽力推送 + 客户端定时/缺口补拉（Pull 兜底，即微信/本项目路线）。取舍：前者实时性更好但服务端要维护「待确认队列」和状态机；后者服务端轻，但要保证**消息序号严格单调 + 客户端有持久化游标**。
- 游标设计：如果按会话维度存 `last_seq`，补拉是 `seq > last_seq` 的增量；如果是全局单序列号，每用户一条单调递增序列（本项目是每个用户维护自己的消息序列，见 OPPO 问7 你的回答），缺口检测更简单。
- ACK 语义：ACK 应该对应「服务端落库成功」而不是「对方已读」，否则可靠性语义和业务语义会混。
- 崩溃恢复的边界：ACK 发出后服务崩溃 → 发送方不必重试；ACK 未发出 → 重试幂等；两者都靠唯一键兜底。**最危险的是「半持久化」**（比如写 MySQL 成功但 binlog 未刷盘），单机 MySQL 下用事务一致性解决，多分片时要考虑分布式事务或本地消息表。

**当前项目实现对照**

### 2.3 讯飞一面·问6：负载均衡算法用的什么？

**面试官原话（转写）**
> 问6：负载均衡算法用的什么？

**你当时的回答**
> 答6：最简单用最小连接数/最小节点；还有打分方法，根据机器容量和节点数写函数打分，选得分最优的节点。

**状态：✅ 可以。**

**考点分析**
- 期望听到：算法名（最小连接数 / 加权最小连接 / 轮询 / 一致性哈希）、**为什么长连接场景适合最小连接数**、以及工程细节（负载数据怎么来、多久更新一次、节点故障怎么过滤）。
- 你的回答方向正确，但「最小节点」是口误（最小负载/最小连接数），而且没有提「健康过滤」——如果节点 A 假死但连接数统计是 0，最小连接数反而会把所有人塞给它，这是面试官在 OPPO 问12 追击的点。

**可直接背的参考回答**
> 长连接场景我用的是**最小连接数（least connections）+ 按容量打分**的组合：调度服务从 Redis 读每个 ChatServer 当前已认证连接数，再结合节点容量权重归一化打分，取分数最优的节点返回给网关。选择最小连接数而不是轮询，是因为 IM 长连接的会话时长差异很大，轮询会让空闲节点和热点节点收到一样多的新用户，容易把某个节点压满；连接数直接反映这个节点「还要背多少存量连接」，是更准的负载信号。
> 工程上还有几个补丁：**第一，先做健康过滤**——只从 lease 未过期（6 秒内上报过）的节点里选，否则坏节点连接数可能是 0，反而被优先选中；**第二，连接数上报有滞后**（2s 周期），所以打分要留一点随机扰动/轮询，避免所有调度实例在同一时刻把新用户全塞给同一个「当前最小」节点，也就是防惊群；**第三，节点容量不等时用权重**，比如 4 核节点权重 1、8 核权重 2，用 `连接数/权重` 排序。
> 如果要进一步优化，可以上**一致性哈希做 UID 亲和**，或者用 EWMA 延迟这类实时指标替代静态连接数，但那是第二阶段的事。

**技术要点拆解**
- 算法对比（面试可展开）：

| 算法 | 原理 | 优点 | 缺点 | 长连接 IM 适用性 |
| --- | --- | --- | --- | --- |
| 轮询 / 加权轮询 | 依次分配 | 简单、均匀 | 无视会话时长和实时负载 | 一般，适合短连接 |
| 随机 / 加权随机 | 随机选择 | 无需状态、天然打散 | 小集群方差大 | 可作为兜底 |
| 最小连接数 | 选当前活动连接最少 | 反映存量负载，长连接友好 | 依赖上报实时性；慢节点可能被反复选中 | 首选 |
| 最小响应时间 / EWMA | 选延迟最低 | 反映服务质量 | 需要请求级采样，长连接难定义 | 辅助指标 |
| 一致性哈希 | key 映射节点 | 亲和性、缓存命中 | 负载可能倾斜、故障要重映射 | 可选，需虚拟节点 |

- 打分模型：`score = w1 * (conn / capacity) + w2 * cpu + w3 * queue_watermark`，越小越优；容量权重按核数/内存配置。
- 防惊群：并列时随机 / 轮询（Season_2 代码正是「最小负载节点集合内轮询」）；或上报数据加抖动。
- 健康过滤优先级永远高于负载：坏节点负载再低也不能选。

**当前项目实现对照**
- **Season_2**：`server/StatusServer/src/StatusServiceImpl.cpp` 的 `getChatServer()`：`HGetAll chatserver:registry` → 逐节点读 `chatserver:lease:<name>`，**读不到 lease 直接跳过**（过期即下线）→ 取 `load` 最小 → 并列节点内 `_rr.fetch_add` 轮询。即「健康过滤 + 最小负载 + 防惊群」三件套都在。
- **工作区 master**：`StatusServer` 的 `getChatServer()` 最小连接数逻辑被注释掉（`StatusServiceImpl.cpp:61-89`），当前直接返回配置里的第一个节点——这是调试遗留，**面试讲课时要用 Season_2 版本，并注意别让面试官看到 master 这行注释**（或提前把它恢复）。
- 节点列表：master 在 `StatusServer/config/config.ini` 的 `[chatservers]` 静态配置；Season_2 改为 Redis 注册表动态发现。

**差距与改进建议**
1. 把 master 里被注释的最小连接数逻辑恢复（`StatusServiceImpl.cpp:61-89`），或合入 Season_2 的注册表版本，别让「说的」和「代码里」不一致。

3. 准备一句话说清「为什么不用一致性哈希做负载均衡」（见 2.5 / 2.10）。

**追问预判**
- 连接数上报延迟 2s，这 2s 内涌入 1 万个新用户会怎样？——全压到同一个最小节点；要靠并列轮询/随机扰动、网关限流、以及节点侧过载保护（拒绝新连或让调度降权）缓解。

### 2.4 讯飞一面·问7：调度怎么知道服务活跃可用？

**面试官原话（转写）**
> 问7：调度怎么知道有几个服务活跃可用？

**你当时的回答（压缩）**
> 聊天服务每 2 秒向 Redis 写当前节点数；Redis 同时维护一个哈希结构，记录聊天节点 IP、端口等。每次调度遍历该哈希查询节点信息，并查看哪些服务仍有节点记录。因为每 2 秒写 Redis 时设置 6 秒过期时间，一段时间没更新会自动删除，相当于下线。

**状态：✅ 可以**，Season_2 代码逐条对得上；但你有个口误（写成「节点数」，实际是「连接数」）和两个没准备的追问点（TTL 抖动、Redis 本身挂了怎么办）。

**考点分析**
- 这题本质是「服务注册与发现」的简化版：注册（写 IP/端口）、续约（心跳/lease）、剔除（TTL 过期）、消费（调度读取）。
- 2s 上报 + 6s TTL 是典型 **lease（租约）** 设计：TTL = 3 × 上报周期，容忍 2 次连续丢包/卡顿。这个「为什么是 3 倍」要能解释。
- 面试官顺着这题在 OPPO 问11/12 挖了「假死」和「摘除」——说明他对这个机制并不完全满意：TTL 只能防「进程/网络整个挂掉」，防不了「进程活着但不能服务」。

**可直接背的参考回答**
> 我们用的是 Redis 上的 **租约（lease）注册机制**，可以理解为一个轻量的注册中心：
> - 每个 ChatServer 启动后把自己的信息以 JSON 写进 `chatserver:registry` 哈希，字段有服务名、TCP 的 host/port、gRPC 的 host/port；
> - 同时每 2 秒刷新一次自己的 lease：`SET chatserver:lease:<name> <当前已认证连接数> EX 6`，TTL 6 秒；
> - 调度服务（StatusServer）被网关问「给这个用户分哪个节点」时，先 `HGETALL` 拿到所有注册节点，再逐个查 lease：**查不到 lease 的说明 6 秒没续约，视为下线，直接跳过**；剩下的按连接数最少选一个返回。
> 为什么 TTL 取 2 秒上报、6 秒过期？因为 TTL 是续约周期的 3 倍，允许节点连续丢两次上报、或者被 GC/调度卡顿一下而不被误杀；再短会误判，再长故障发现就慢。进程正常退出时我们会主动删掉自己的 lease 和注册字段，这是优雅下线的快路径；如果进程崩溃/机器断电，就走 TTL 过期这条慢路径，最多 6 秒摘除。
> 这个机制的边界我也很清楚：**它只能证明「进程还在按时上报」，不能证明「进程还能处理业务」**——所以假死场景还需要业务级健康检查，这也是我们在第二季度要补的。

**技术要点拆解**
- 注册发现机制对比（必含专题，完整版见 2.10）：Redis TTL lease / 应用心跳 + 监控 / etcd / Consul / ZooKeeper / gRPC health / K8s probe。
- **Redis TTL 细节**：TTL 由 Redis 服务端时钟掌握，客户端时钟漂移不影响过期判定（这是相对「本地时间戳判活」的优势）；但 `HSET registry` 和 `SET lease` 是两条命令，不是原子操作——若 HSET 成功、SET lease 失败，注册表里会有节点但无 lease，所以调度的权威判断必须放在 lease 上（Season_2 正是这么做的：无 lease 就跳过，天然安全）。
- **优雅下线 vs 异常下线**：正常退出 `HDel registry + Del lease`（秒级摘除）；异常走 TTL（6s）；两者都要保证「摘除期间不再接新流量」，因为连接数上报可能还在。
- **消费侧缓存**：每次调度都 `HGETALL + N 次 GET`，节点多了会放大 Redis 读压力；可以本地缓存 + 订阅变更（Redis pub/sub 或轮询缓存）优化（当前项目规模小，未做）。
- **注册中心本身的可用性**：注册表在 Redis 上，Redis 挂了调度就瞎了——这正是 [Redis使用与高可用设计](Redis使用与高可用设计.md) 要解决的强依赖问题。

**当前项目实现对照**
- Season_2：`server/ChatServer/src/ChatServer.cpp` 的 `report_lease`（2s/6s 默认值、`HSet` registry、`SetEx` lease、优雅退出 `HDel+Del`）；`server/common/include/ChatServerRegistry.h`；`server/StatusServer/src/StatusServiceImpl.cpp` 的 `getChatServer()`（无 lease 跳过）。
- 工作区 master：没有 TTL 注册表，节点列表在 `StatusServer/config/config.ini` 静态配置；连接数由 ChatServer 每 60s `HSet(logincount, name, count)`（`CServer.cpp:106`）写入，无过期；`RedisMgr::IncreaseCount/DecreaseCount` 早期版本用 `lockcount` 全局锁更新，day35 已改为心跳统一写（`CServer.cpp`），避免频繁加锁。
- **两套机制别混**：注册 lease（2s/6s，判活）≠ 连接心跳（客户端 10s 发心跳、服务端 20s/60s 判超时，判连接）。面试各归各讲。

**差距与改进建议**
1. 面试话术里把「节点数」改成「已认证连接数」，并把「3 倍 TTL」的理由背下来。
2. 增加「上报失败则自摘除」：连续 N 次 lease 续约失败时，节点应主动停止接受新连接（置 not-ready），避免调度继续分配。
3. 注册读写加缓存/原子化优化：`HSET + SETEX` 可以用 Lua 或 pipeline 合并，减少半写状态（虽然当前以 lease 为准已经安全）。

**追问预判**
- 节点上报写到一半（registry 成功、lease 失败）会怎样？——调度以 lease 为准，无 lease 跳过，安全；下次周期重写。
- Redis 挂了，调度怎么办？——降级用静态配置/本地缓存节点列表 + 保守调度，并靠 [Redis 高可用](Redis使用与高可用设计.md) 的哨兵/集群恢复；不能假设 Redis 永远在。
- 为什么不用 etcd/Consul？——项目规模小、已经依赖 Redis，用 Redis lease 成本最低；如果做大规模或需要 watch/配置管理，etcd/Consul 更合适（能答出取舍即可，见 2.10）。
- TTL 设成 6 秒，节点被 kill -9 后多久不再收新用户？——最长 6 秒（加上调度缓存可能是下一个周期）；已在线的用户不受影响，直到连接断开触发重连。

### 2.5 讯飞一面·问9：一致性哈希了解吗？

**面试官原话（转写）**
> 问9：这个场景里一致性哈希了解吗？

**你当时的回答**
> 答9：不太了解。尽量让同一 UID 路由到同一个聊天服务节点；若服务内有缓存或需要亲和性，就不要调度到其他节点。

**状态：❌ 答不上（这是本场最不该丢的分）。**

**考点分析**
- 面试官问这个，是因为你说「尽量让同一 UID 路由到同一个节点」——他立刻想到一致性哈希是标准解法，而你直接说「不太了解」，非常可惜。
- 需要回答三层：①原理（哈希环、顺时针、虚拟节点）；②在你场景里能解决什么（UID → 节点亲和）；③在你场景里的局限（长连接场景「路由」和「连接」是两回事，故障时必须重映射）。
- 注意区分：一致性哈希解决的是「哈希空间变化时尽量少搬数据」，而不是「负载均衡」本身；它和最小连接数是互补的。

**可直接背的参考回答**
> 一致性哈希就是把哈希值空间看成一个环：对每个服务节点的地址取哈希放到环上；对一个 key（比如 UID）取哈希，顺时针找到的第一个节点就是归属节点。它的好处是增删节点时只影响环上相邻的一段数据，平均只迁移 1/N 的数据，而不是像 `hash % N` 那样全量重映射。
> 基础版有两个问题：**数据倾斜**（节点少的时候，环上分布不均，有的节点扛大半）和**负载不均**。解决办法是**虚拟节点**：给每个物理节点分配 100~200 个虚拟节点散列到环上，key 落到虚拟节点再映射回物理节点，分布就均匀了；还可以按机器容量给不同数量的虚拟节点做加权。
> 在我的系统里，这个思路可以用于 **UID → ChatServer 的会话亲和**：同一个用户固定路由到同一个节点，节点本地的用户缓存、最近会话上下文命中率更高，多端也能落到同一节点方便状态管理。但我很清楚它的边界：**长连接的「连接归属」不等同于「数据归属」**，连接断了以后必须允许重映射到其他健康节点，否则故障时这个用户就永远上不了线。所以真要做，我会做成「健康时优先哈希、不健康时回退最小连接数」的软亲和，而不是强绑定。另外我们消息的权威数据在 MySQL、用户缓存也在 Redis，节点本地没有不可替代的状态，所以第一阶段没有引入一致性哈希，收益有限。

**技术要点拆解**
- 原理：`node = first node clockwise from hash(key)`；虚拟节点 `hash(node#i)`；一致性哈希的「单调性」：新增节点只把相邻区间接管过来，其余 key 不动。
- 迁移量：从 N 节点扩到 N+1，平均迁移 1/(N+1) 的数据；对比取模哈希的几乎全量迁移。
- 数据倾斜的量化：标准一致性哈希在无虚拟节点时，最大节点负载可能是均值的 O(log N) 倍；100+ 虚拟节点后方差显著收敛。
- 在本场景的两种用法：
  1. **连接路由**：调度时优先把 UID 分到 `hash(uid)` 对应节点（软亲和），节点故障时 fallback。
  2. **数据分片**：如果以后消息分库分表/Redis 分片，按 UID 哈希分片，保证同一用户的消息/缓存落在同一分片（更常见、更有价值）。
- 与本项目的替代方案对比：当前用「最小连接数 + 无状态 ChatServer」，实现简单、故障无状态迁移；一致性哈希的收益（本地缓存亲和）目前很小，因为缓存已经放在 Redis。**能说清「为什么暂时不用」比硬套更重要。**
- 如果面试官继续问「Redis Cluster 的 slot 是不是一致性哈希？」——不是，是固定 16384 个槽的哈希分片（`CRC16(key) % 16384`），槽固定、节点认领槽，迁移以槽为单位；一致性哈希的环形空间是动态的。详见 [Redis使用与高可用设计](Redis使用与高可用设计.md) 的 Cluster 小节。

**当前项目实现对照**
- 未实现（已核对：master 与 `origin/Season_2` 的 server/client 代码中均无一致性哈希/虚拟节点）。调度只有最小负载（连接数）逻辑（Season_2）。
- 但「同一 UID 尽量同节点」在**多端互斥**上已经部分实现：`uip_<uid>` 记录用户当前所在 ChatServer，异地登录时能精确找到旧节点踢人（`LogicSystem.cpp:198-246`）——这不是哈希路由，是「状态表查询」，面试时可以拿来呼应「亲和」的诉求，但不能说成一致性哈希。

**差距与改进建议**
1. 把上面这段「原理 + 虚拟节点 + 场景适用性 + 为什么暂不做」完整背下来，下次这题就是加分题。
2. 想动手：在调度里加「上次登录节点优先」规则——Redis 存 `last_node_<uid>`，如果该节点健康且没超载就优先返回，否则最小连接数。这比重构一致性哈希的学习成本低、收益直观，也能在面试里讲成「软亲和」。
3. 顺带准备 Redis Cluster 槽分片与一致性哈希的区别。

**追问预判**
- 虚拟节点解决什么问题？——数据倾斜 + 节点权重（容量大的多放虚节点）。
- 一致性哈希和最小连接数冲突吗？——不冲突，健康 + 负载过滤后用哈希做亲和，哈希节点超载/故障时回退。
- 节点故障后哈希环缩容，用户重映射了，缓存怎么办？——缓存本来就在 Redis/MySQL，重映射只影响本地缓存命中率；如果做本地缓存要能接受这段回源。

### 2.7 OPPO 二面·问11：聊天服务「假死」怎么识别？

**面试官原话（转写）**
> 问11：比如说我们这个服务，这个聊天服务是注册在这个 Redis 上面。这个服务可能会出现一些假死的情况，那虽然它是存活的，但实际上它无法提供服务，那我们在这个系统下面是怎么识别这些假死的节点？有办法识别吗？

**你当时的回答（压缩）**
> 当前是没有设计。但如果让我想，用户请求一个服务失败次数过多，就向网关重新申请一个别的节点。

**状态：❌ 未设计（对面给了台阶「如果是你会怎么想」，你只答了客户端侧被动重试，没答服务端识别）。**

**考点分析**
- 假死（hang/limp mode）的定义：进程还在、TCP 端口还在监听、甚至 lease 还在续，但业务线程池打满 / 死锁 / 依赖（MySQL/Redis）超时 / 事件循环被阻塞，导致请求超时或处理极慢。
- 面试官想听的是**判定信号 + 判定方（自检/他检）+ 处置动作**，而不是客户端重试。
- 这个追问直接把你引到了问12（摘除）和问13（迁移），是一整条故障处理链。

**可直接背的参考回答**
> 假死的本质是「存活 ≠ 可服务」，TCP 层和进程层的心跳都识别不了，必须加**业务级健康检查**。我会分三块做：
> **第一，节点自检 + 自摘除。** ChatServer 内部周期性检查：业务线程池/逻辑队列的水位（积压超过阈值）、事件循环的定时器漂移（比如本该 100ms 跑一次的检查晚了 2s 说明被阻塞）、关键依赖（MySQL/Redis）的连通性和超时率、关键操作 P99。任何一项不健康，节点就把自己标记为 not-ready，**主动停止 lease 续约、甚至立刻删掉 lease**，并拒绝新连接接入（或返回「服务繁忙」），让调度在下一个周期不再分新用户过来。自摘除是最快的路径，因为它不需要别人探测。
> **第二，调度/监控侧主动探测。** StatusServer 或独立的健康检查组件对注册节点发起**业务级探针**，不是 ping TCP，而是走 gRPC 调一个轻量 RPC（比如 `Echo/GetStats`），检查返回时延、返回内容里的负载水位。连续 N 次超时或失败就把节点标记 suspect，从候选集剔除。用 gRPC 的话可以复用标准的 `grpc.health.v1.Health` 协议，实现 SERVING/NOT_SERVING 和 Watch；K8s 环境则用 readinessProbe（readiness 失败会摘流量，liveness 失败才重启）。
> **第三，客户端侧被动信号。** 网关/客户端统计按节点维度的请求失败率和超时率，连续失败超过阈值就上报给调度，调度把节点临时降权/拉黑一段时间（熔断）。客户端侧信号是兜底，不能作为第一手段，因为它反应最慢，而且用户已经受影响了。
> 处置要分级：suspect → 停发新连接（权重 0）；确认故障 → 摘除 + 已连用户走断线重连；恢复 → 渐进放量。这样避免「刚恢复又被压满」的抖动。

**技术要点拆解**
- 假死的典型成因：业务线程池被慢查询/锁占满、gRPC 同步调用阻塞、死锁（项目里 day35/day41 就有两类锁死锁的真实案例）、事件循环被 CPU 密集型任务阻塞、内存泄漏导致频繁 GC/swap、fd/连接泄漏。
- 判定指标：队列长度、队列等待时间、定时器漂移、依赖超时率、活跃连接数 vs 处理速率、CPU 100% 但吞吐为 0。
- 自检 vs 他检：
  - 自检（进程内 watcher 线程）→ 快，但进程完全 hang 时 watcher 也没了（所以 watcher 要用独立线程/看门狗）。
  - 他检（外部探针）→ 客观，但引入探测流量和网络开销。
  - 两者结合：自检负责「主动摘除」，他检负责「发现完全无响应的进程」。
- gRPC health checking protocol：`grpc.health.v1.Health/Check` 返回 `SERVING/NOT_SERVING`，支持 `Watch` 流式订阅；gRPC 客户端可结合 health-aware LB。注意：只实现 health 服务不等于业务健康，要把它和业务指标绑定。
- gRPC 自带 keepalive 只能检测连接存活（HTTP/2 PING），**同样识别不了业务假死**。

**当前项目实现对照**
- 现状没有业务级健康检查：ChatServer 的 lease（Season_2）只证明「上报线程活着」；`CSession` 心跳（`CSession.cpp:271`，20s 阈值 / 60s 扫描）只管客户端连接超时。
- 真实踩坑可引用：`day35心跳逻辑` 里「线程锁 + 分布式锁交叉加锁」的死锁分析、`day41-分布式死锁解决方案` 里 MySQL 死锁分析——说明你对「活锁/死锁导致进程还能跑但不能服务」有实际认知，可以当作假死的典型案例讲。
- 推荐从 Season_2 的 lease 机制上加：`report_lease` 前先做一次自检，不通过就跳过续约/主动 `Del lease`。

**差距与改进建议**
1. 实现一个最小版本：ChatServer 暴露 `GetStats` gRPC（返回队列水位、在线数、最近处理耗时），StatusServer 调度时或定时探测；连续 3 次失败剔除。
2. lease 续约前加白检逻辑（队列水位 → 不续约），这就把「假死节点 6 秒内自摘除」变成可讲的亮点。
3. 准备一句话回答「为什么 TCP/心跳识别不了假死」。

**追问预判**
- 节点完全 hang 了连 lease 也不续，多久摘除？——TTL 6s 内；这与问12 的摘除衔接。
- 你怎么区分网络抖动和节点假死？——单次失败不算，连续 N 次 + 多来源（调度探针 + 客户端上报）确认；恢复也要连续成功才放量。

- 多实例调度怎么共享健康状态？——健康状态写 Redis（带 TTL），所有调度实例读同一份；避免各自为政。

### 2.8 OPPO 二面·问12：大量用户路由到故障节点的摘除机制？

**面试官原话（转写）**
> 问12：那如果是这样的话，那我大量的用户只要路由到这台节点上都会做一个重试，那我们有没有一些什么比较好的摘除机制吗？

**你当时的回答（压缩）**
> 目前是没有。因为用户是跟对应聊天节点建立稳定的 TCP 长连接，要换到其他节点都要断开 TCP 再重建，所以都要经历一个重连的过程。

**状态：❌ 没有（你只解释了「为什么难」，没有回答「怎么做」）。**

**考点分析**
- 面试官要的是**摘除机制**：谁判定、怎么摘（注册表/权重/黑名单）、摘除后流量怎么导、已连用户怎么办。
- 你的回答把「摘除」和「连接迁移」混在一起了：摘除是调度侧不再分配新用户（对象是注册表/权重），迁移是已连用户的处理（对象是连接）。要分开答。
- 注意「摘除」有两层含义：①软摘除（降权、停发新流量、老连接自然消化）②硬摘除（强制断开/驱逐）。生产上优先软摘除，避免惊群。

**可直接背的参考回答**
> 摘除我分「被动」和「主动」两条路，并且优先软摘除：
> **被动摘除（已经出了问题）：** ①调度侧兜底：探测/客户端上报发现节点连续失败，直接把它从候选集剔除（Redis 里置 `not-ready` 或删除 lease），这是最快的止血；②注册机制兜底：节点崩溃/挂起导致 lease 6 秒不续期，TTL 过期自动摘除，不需要人干预。
> **主动摘除（还没出问题，但已经不健康）：** 节点自检发现线程池积压、依赖超时，就主动不续 lease / 上报 weight=0，让流量平滑流出；监控侧也可以配置熔断策略（错误率超过阈值自动降权）。
> **软摘除的动作要分级：** 第一步权重降到 0，不再接新用户；第二步观察已有连接，如果不健康再考虑主动断连；如果想加速迁移，可以给节点发「优雅下线」指令：停止 accept、给客户端发一个「建议重连」的通知，客户端随机退避后重连到新节点——注意一定要加**随机退避**，否则同一秒几千个客户端同时重连会把新节点打挂，也就是惊群。
> **摘除后的恢复也要管：** 节点恢复后不能瞬间放全量流量，先放 1% 观察，再逐步加权重，防止「刚恢复又被压死」。
> 至于你说的 TCP 长连接问题，它只影响「已连用户」——那部分确实是断线重连（问13），但摘除机制本身在调度层就能完成，不依赖断开连接。

**技术要点拆解**
- 摘除状态机：`healthy → suspect（降权，仍收探测）→ draining（权重 0，不发新连接，通知老连接迁移）→ removed（删除注册）→ recovering（小流量恢复）`。
- 实现载体：Redis 注册表字段加 `weight/status`；或单独 `chatserver:status:<name>` 带 TTL；调度读取时过滤 `status != ready`。
- 惊群控制：随机退避（Season_2 客户端是 2s/4s/8s 固定退避，多客户端需要加抖动）、网关限流、新节点预热/权重爬坡。
- 一致性：多个 StatusServer 实例的摘除状态共享在 Redis；探测结果也写 Redis（TTL 短，避免状态残留）。
- 监控告警配套：摘除动作要有日志和指标，否则「为什么只剩一个节点」没人知道。

**当前项目实现对照**
- Season_2 有被动摘除的一半：lease 过期即跳过，且进程优雅退出时主动 `HDel + Del`（`ChatServer.cpp`）；但没有 `weight/status` 分级、没有探测、没有恢复放量。
- 工作区 master 无 TTL/无摘除（静态配置 + 连接数）。
- 客户端断线重连机制（问13 的实现）在 Season_2 的 `mainwindow.cpp`：3 次、2s/4s/8s 退避——**没有抖动**，多人同时掉线会窄窗口重连，可作为改进点。

**差距与改进建议**
1. 在注册字段里加 `weight`（默认 100），调度按 `load/weight` 选；摘除=置 weight 0。
2. 客户端重连退避加随机抖动（例如 base×2^n + rand(0, 1s)），并给重连速率加客户端侧限流。
3. 写一个「优雅下线」流程：收到 SIGTERM → 停 accept → 注册置 draining → 等待老连接自然迁移或通知 → 退出；面试可讲成「无损发布」。

**追问预判**
- 节点被摘除后，已经连上去的用户什么时候切走？——分主动/被动：主动下线时发通知让客户端尽快迁移；崩溃时等客户端检测到断线（心跳超时/写失败）后重连。
- 摘除会不会造成剩余节点过载？——会，所以摘除要和容量水位联动：剩余节点接近上限时，宁可限流新登录，也不要雪崩式全压过去。
- 摘除的判定谁来拍板？——单点探测容易误判，要求「连续失败 + 至少两个来源」；StatusServer 多实例共享状态。
- 怎么避免频繁抖动摘除/恢复？——滞回（hysteresis）：摘除阈值比恢复阈值更严；恢复要连续 N 次健康 + 渐进放量。

### 2.9 OPPO 二面·问13：已建连用户如何处理？

**面试官原话（转写）**
> 问13：比如说你刚刚提到，新建连的用户可能已经连不上了，申请去重试了，那这时候已经建连的用户应该如何处理？

**你当时的回答（压缩）**
> 设计了断线重连机制：重新向网关申请一个好的节点，然后去连好的节点建立 TCP 连接，自己把旧连接断开，申请节点和新的建立连接。

**状态：⚠️ 半对——机制存在且能自洽，但没有讲「重连期间的消息补拉」和「旧节点的状态清理」，也没讲惊群防护。**

**考点分析**
- 对长连接 IM 来说，连接迁移 = 断线 + 重连 + 会话恢复。面试官想看：
  1) 重连的触发（客户端如何发现）；
  2) 重连的地址从哪来（调度/网关重新分配，token 复用）；
  3) 重连后状态怎么恢复（鉴权、消息补拉、多端状态）；
  4) 旧节点/旧会话怎么清理（防止双登、僵尸会话）；
  5) 大批量迁移怎么不把系统打崩。

**可直接背的参考回答**
> 已建连用户只能走**断线重连**，因为 TCP 连接是节点上的状态，没法像无状态服务那样平滑迁移。完整流程是：
> **发现**：客户端心跳超时、写失败、或者收到服务端「建议重连」的通知，就知道连接不可用了。
> **重连**：客户端带着 UID 和未过期的 token 调网关的重新分配接口（我们实现是 `/reassign_chat`），StatusServer 校验 token 后按健康 + 最小负载返回新节点；客户端退避重试——我们用 2s/4s/8s 三次退避，失败回登录页。
> **鉴权与互斥**：到新节点后走标准登录：ChatServer 校验 token，加分布式锁检查 `uip_<uid>`（用户当前在哪个节点）和 `usession_<uid>`（当前会话 ID），如果旧记录还在就通过 gRPC 让旧节点把旧连接踢掉，然后写入新的节点和 session 记录——保证同一用户只有一个活跃连接，不会双端收到消息。
> **状态恢复**：重连前连接是断的，这段时间的消息会缺。客户端本地有每个会话的游标，重连成功后按游标补拉缺失区间；同时好友列表、申请列表这些登录时都会重新同步。所以**消息不依赖「连接不断」，依赖的是「可补拉」**。
> **清理**：旧节点发现连接断开/心跳超时后，会加分布式锁再校验 `usession_` 是否还是自己这条，是才清理，避免把用户在新节点上的状态误删——这是跨服踢人逻辑的一部分（day34/day35）。
> **防惊群**：节点故障时几百上千个客户端会同时重连，我们当前退避没有抖动，这是要改的点——正确做法是 base×2ⁿ + 随机抖动、重连请求网关侧限流、新节点确认健康后才放量接收。

**技术要点拆解**
- 会话恢复的两个层次：
  - **连接状态**：TCP、session、订阅关系——丢了要重建，无法迁移。
  - **业务状态**：token、用户资料、消息游标——必须持久化在 Redis/MySQL/客户端，重连后重建。
- 「旧连接断开」的两种触发：客户端主动断（重连前）；服务端心跳超时/写错误被动断（`DealExceptionSession`）。两者都要幂等。
- 多端状态：本项目是单端互斥（收到新登录踢旧端），所以迁移后只要保证新 session 生效即可；如果做多端，需要按 `uid + device` 维度记录。
- 重连风暴的量级：1000 客户端同时重连（含 TLS/登录/补拉 3 个往返），对新节点可能是数倍日常 QPS——这就是惊群，必须退避 + 限流 + 预热。
- 与「一致性哈希软亲和」的关系：重连时优先回原节点（`last_node` 记录），原节点不健康才换，能减少补拉量和缓存冷启动。

**当前项目实现对照**
- Season_2：
  - 客户端 `client/llfcchat/src/app/mainwindow.cpp`：`attemptReconnect` → `POST /reassign_chat`（带 uid+token）→ `TcpMgr::ReconnectChat(host, port)`；退避数组 `{2000, 4000, 8000}`，最多 3 次。
  - 网关 `GateServer/src/LogicSystem.cpp` 的 `/reassign_chat`；StatusServer `GetChatServer` 的 reassignment 分支（token 非空则校验 Redis token 后复用，不重新生成）；token 有效期 `SetEx(utoken_, 86400, token)`。
  - 服务端登录互斥与清理：`ChatServer/src/LogicSystem.cpp:194-246`（锁 + `uip_` 判断 + 同服踢/跨服 `NotifyKickUser`）、`CSession.cpp:282-318`（`DealExceptionSession` 校验 `usession_` 再清理）。
- 工作区 master：客户端断线只弹「心跳超时或临界异常，该终端下线」然后回登录页（`mainwindow.cpp:123-129`），**没有自动重连**——面试讲 Season_2。
- 消息补拉：见 [离线消息、补拉与消息撤回](离线消息、补拉与消息撤回.md)。

**差距与改进建议**
1. 给重连退避加随机抖动，并在网关 `/reassign_chat` 加限流（令牌桶）。
2. 补「重连后补拉」的完整话术：先鉴权，再拉好友/会话列表，再按会话游标补消息，最后开始心跳。
3. 加「优先回原节点」策略（Redis `last_node_<uid>` + 健康检查），减少迁移成本，这个可以直接在 Season_2 调度里加。
4. 把「旧节点清理」的分布式锁逻辑背熟（day34/day35），这是面试官很可能继续追的点。

**追问预判**
- 客户端怎么知道旧连接真的断了，而不是网络抖动？——心跳超时 + 重试写失败 + 服务端通知，多重信号；重连前不需要确认旧连接已断，靠服务端互斥兜底。
- 重连时 token 过期了怎么办？——回到登录流程；token 有效期 24h，正常重连窗口远小于它。
- 旧节点还活着但已经不可用（假死），互斥逻辑会怎样？——新节点写 `uip_` 后，旧节点后续清理时会校验 `usession_` 不一致而跳过，不会误删；但旧节点上的连接会变成僵尸，靠心跳超时/摘除清理。
- 大量用户同时重连，网关扛不住怎么办？——客户端抖动退避 + 网关限流 + 按节点分批放量；实在不行先排队（返回稍后重试），保证不雪崩。

### 2.10 专题 A：服务注册/发现与健康检查（面试深水区）

#### 2.10.1 四种机制对比

| 机制 | 原理 | 故障发现 | 一致性 | 运维成本 | 适用 |
| --- | --- | --- | --- | --- | --- |
| **Redis TTL lease（本项目）** | 服务写 key/field + TTL，周期续期；消费方读注册表 | 一个 TTL 周期（6s） | 最终一致（AP） | 低（复用 Redis） | 中小规模、已有 Redis、只要「活着」信号 |
| **应用层心跳 + 监控判断** | 服务打点上报，Prometheus/自研监控判定 | 取决于判定窗口 | 最终一致 | 中（要建监控/告警） | 需要观测 + 告警，不解决调度 |
| **etcd** | Raft + lease + watch，key 绑定租约 | 秒级 | CP（强一致） | 中高（Raft 集群） | 需要强一致、watch 通知、配置中心、选主 |
| **Consul** | Serf gossip + 健康检查（TCP/HTTP/gRPC/脚本）+ 多数据中心 | 秒级 | AP/CP 可选 | 中高 | 多云/多 DC、服务网格 |
| **ZooKeeper** | 临时节点 + watch，session 超时即删 | session 超时（秒级） | CP | 高 | 老牌选主/协调，生态重 |
| **gRPC health + 客户端 LB** | `grpc.health.v1.Health` 标准探活；客户端 round_robin/least_request | 探测周期 | 取决于注册层 | 低（库自带） | 补充「业务健康」维度，不替代注册中心 |
| **K8s readinessProbe** | 容器探针失败自动从 Endpoints 摘流量 | 探测周期 | 由 K8s 保证 | 低（平台） | 云原生部署首选 |

**结论话术**：注册中心解决「实例在哪、是否活着」（liveness），健康检查解决「实例能不能干活」（readiness），两者互补；小项目用 Redis lease 性价比最高，但要知道它不能判定业务假死，也没有 watch 语义（要轮询）。

#### 2.10.2 TTL 续期的时钟与网络抖动问题

- **周期关系**：`TTL ≥ 3 × 上报周期`（本项目 6s = 3×2s），容忍连续 2 次丢失。TTL 太短 → 网络抖动误摘 → 用户被断线重连；TTL 太长 → 故障发现慢。
- **时钟**：Redis TTL 由服务端时钟计算，客户端时钟漂移不影响判活——这是相比「本地时间戳」的优势。但注意：
  - Redis 主从切换/RDB 恢复后 TTL 的绝对过期时间语义要确认（Redis 4.0+ 主从全量同步对过期键有明确处理；失效时间来自服务端，跨机器时钟要 NTP 同步）。
  - 极端情况下机器时钟回拨可能让 TTL 提前/延后，运维层要保证 NTP。
- **网络抖动**：`HSET registry` 与 `SET lease EX` 是两条命令，不是原子的——半写状态（有注册无 lease）由「以 lease 为准」兜住；更稳的做法是 Lua/pipeline 原子化，或让续期只做 `EXPIRE`（值变化频率低时）。
- **上报线程被阻塞**：C++ 服务里如果上报定时器和业务共用一个 `io_context`，业务卡住时上报也停，反而「正确地」暴露故障；但如果用了独立线程，业务假死时 lease 照常续——这就是 2.10.3 要解决的问题。
- **抖动与恢复滞回**：摘除/恢复都要有滞回策略（连续 N 次失败才摘、连续 M 次成功才恢复），否则节点在临界状态反复横跳。

#### 2.10.3 健康检查与假死判定（TCP 存活 ≠ 可服务）

| 判定层次 | 手段 | 能发现 | 发现不了 |
| --- | --- | --- | --- |
| TCP 层 | accept 成功、keepalive | 进程消失、端口关闭 | 业务假死 |
| 应用心跳 | 上报线程写 Redis | 进程卡死（若同线程）、网络断 | 业务线程假死（心跳线程独立时） |
| 业务健康 | 队列水位、定时器漂移、依赖超时率 | 假死、过载 | 需要自研指标 |
| 标准探针 | gRPC health / K8s probe | 依赖健康服务实现 | 同上（依赖实现质量） |
| 端到端 | 探针 RPC 的 P99 | 真实可用性 | 成本高、可能扰民 |

- 假死判定要**组合信号**：队列积压 + 定时器漂移 + 探针延迟 + 客户端失败率，任一异常先降权，多个异常才摘除。
- 自检要放在**独立看门狗线程**（不能和业务线程共池），否则假死时自检也停摆。
- 判定动作要幂等、状态要共享（Redis 状态带 TTL）。

#### 2.10.4 被动摘除 + 主动探测

- **被动**：lease 过期（崩溃）、客户端/网关错误率上报（熔断）、依赖失败（自摘除）。
- **主动**：调度侧定时对注册节点做轻量业务探针（gRPC `GetStats` 或标准 health），连续失败 → suspect → 权重 0 → 摘除。
- **恢复**：探针连续成功 → 小权重试跑 → 逐步放量（不要一步回满）。
- **状态机**：`ready / suspect(降权) / draining(权重0+通知迁移) / removed / recovering(爬坡)`。
- **面试收尾话术**：「摘除的本质是让调度不再往这个节点分人，而不是去断开已经连上的人；已连的人交给重连机制和消息补拉。两条线解耦，才能做到既快又不惊群。」

### 2.11 专题 B：一致性哈希与 UID 路由（面试深水区）

#### 2.11.1 原理与虚拟节点

- 哈希环：`hash(node)` 放置节点，`hash(key)` 顺时针找节点；增删节点只影响相邻区间（平均迁移 1/N）。
- 虚拟节点：每个物理节点映射 100~200 个 `hash(node#i)`，解决数据倾斜；按容量加权 = 给大机器更多虚节点。
- 与普通取模：`hash % N` 在 N 变化时几乎全量迁移，哈希环只迁移一小段。
- 典型应用：分布式缓存分片（Memcached 客户端）、分库分表路由、CDN 节点选择。

#### 2.11.2 在本场景的适用性

| 维度 | UID 哈希亲和 | 最小连接数 |
| --- | --- | --- |
| 负载均衡 | 可能倾斜（要靠虚节点） | 动态均衡，直接反映存量 |
| 缓存亲和 | 高（本地缓存/会话上下文命中高） | 无 |
| 故障处理 | 需重映射 + fallback | 直接换节点 |
| 实现复杂度 | 中（环 + 虚节点 + 权重） | 低 |

- 本项目 ChatServer 无状态（消息在 MySQL、缓存主要在 Redis），哈希亲和收益有限；**连接归属本来就不适合哈希强绑定**（故障必须允许漂移）。
- 可选落地方案：`软亲和`——调度优先返回该 UID 上次所在节点（Redis `last_node_<uid>`），节点不健康/超载时回退最小连接数；这能减少重连补拉和缓存冷启动，改动却很小。
- 真正的哈希分片价值在**消息存储/缓存分片**：按 UID（或 thread_id）分片，保证同一用户的消息、会话、离线队列落同一分片，便于批量拉取和顺序保证。

#### 2.11.3 面试话术要点

1. 先讲原理 + 虚拟节点（30 秒）。
2. 再讲「为什么要虚拟节点 / 不加会怎样」（倾斜、扩缩容迁移量）。
3. 最后落到本项目：「连接层做软亲和可以，强绑定不行；如果做存储分片，按 UID 哈希分片比连接路由更有价值」。
4. 顺手区分 Redis Cluster 的 slot（固定 16384）不是一致性哈希。

## 3. 小结与行动项

### 3.1 最值得注意的三条结论

1. **问7 是你最强的题，问9/OPPO 11/12 是你最弱的题**：注册续约机制有真实代码支撑，一致性哈希和假死/摘除直接暴露了「只做了 happy path」。

3. **master 与 Season_2 的差异要心里有数**：面试讲 Season_2 的注册中心 + 重连 + 优雅下线，但要知道 master 里最小连接数被注释、客户端不自动重连这些旧状态。
