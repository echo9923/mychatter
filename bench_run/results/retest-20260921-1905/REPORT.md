- Windows 11，Intel Core i5-14600KF，14 核 / 20 逻辑处理器，约 32 GiB 内存。
- 原生 Release 服务端与 Python 3.13.14 压测端同机；MySQL 8.0.46、Redis 7.4.10 运行于同机 Docker Desktop Linux VM。
- 使用专用 llfc_validation 数据库及 13308 / 16380 端口；保留已有测试数据，每次通过唯一测试 tag 隔离核对，不清空日常业务数据库。
- ChatServer 单实例，4 个逻辑工作线程和 4 个投递工作线程。源码 MySQL 连接池为 5、Redis 连接池为 10。
- MySQL innodb_flush_log_at_trx_commit=1，sync_binlog=1，max_connections=500。
- 当前 HEAD：c5de106ddbb75c796f16362fd3e2bf7843e9c9fe，包含用户原有未提交修改。以 verified-snapshot/manifest.json 的源文件和可执行程序 SHA-256 为准，不能仅用 Git HEAD 复现。
- 20% 在线用户作为发送方，每 10 秒发送一条 256 字节文本；发送人与接收人按账号成对，所有连接每约 5 秒有心跳。256 字节是文本负载，不包括 JSON 和帧开销。
- 批量连接使用预置 token 进行真实 TCP 认证；账号密码登录另有冒烟检查，因此不代表账号密码登录 QPS。
- 发送采用预定时间安排，统计调度滞后；一档持续 60 秒或 600 秒，结束后允许最多 30 秒排空，再观察 1 秒、核对数据库。
- 通过条件：全部用户认证，全部计划消息成功确认并收到，逐 ID 数据库对账成功，无异常断连、错误及重复，ACK 和接收 P99 都不超过 1000 ms，发送调度 P99 不超过 100 ms。
- ACK 延迟从发送计时到读到成功回包；接收延迟到无界面接收端读到通知，未包含 Qt 界面渲染。延迟分位数仅覆盖完成的消息，必须与错误数量同时解读。

## 可以直接口述的面试回答

### 单机支持多少用户

测过，我把在线连接数和指定负载下的业务容量分开统计。测试环境是 i5-14600KF、32GB 内存的 Windows 机器，Release 构建，单 ChatServer；压测程序和数据库依赖也在这台机器上。

我验证过 3000 用户同时在线，20% 的用户每 10 秒发一条 256 字节文本，对应每秒 60 条业务消息，同时所有连接保持心跳，持续发压 10 分钟。36000 条消息最终全部收到成功回包和接收通知，数据库逐条对账一致，没有观察到异常断连和重复。成功回包 P99 约 769 毫秒，接收 P99 约 783 毫秒。

5000 用户档也测了，连接全部建立，但 6000 条消息中有 14 条返回持久化失败，接收 P99 上升到约 2.11 秒。日志和 InnoDB 诊断观察到了事务死锁，所以这一档不达标。

因此目前能给出的是这套环境和负载下通过了 3000 用户的 10 分钟验证，不能直接说单机最大容量就是 3000，也不能外推成长期生产保证。

### 消息丢失、重复有没有测试

测过，我重点模拟了两种结果不确定的情况：服务端已落库但发送成功回包丢失，以及接收端漏掉实时通知。

我通过代理主动丢弃 100 条业务消息的首次成功回包和全部实时通知，再使用原来的消息唯一标识重发，总计 200 次请求。最后 100 次重试成功，接收端通过 4 页增量同步补齐 100 条消息；数据库只有 100 条消息和 100 条接收事件，没有重复，内容和服务端消息 ID 逐条一致。

机制上，发送任务先进入本地 SQLite outbox，提交后再发送；服务端通过发送者 ID 与客户端消息 ID 做事务内幂等；接收端通过事件序号补拉，并把业务数据和同步游标一起提交。还做了离线、跨服异常后重启恢复、资源断点续传等测试，最终现有完整回归 29 项全部通过。

协议故障测试使用无界面客户端，本地 SQLite 与 Outbox 另有组件测试。我不会把这些结果说成完整 GUI 已验证所有故障，或任意故障下端到端 exactly-once。
