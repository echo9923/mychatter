# 即时通讯项目面试追问训练

本稿依据本轮代码检查编写。具体容量数值、完整回归状态与可靠性结果以同目录 REPORT.md 为准。机制说明、组件测试、真实服务端协议测试、完整 GUI 验证是不同证据层级。

## 回答方法

每次先给一句结论，再给两项证据，最后说明边界。不要一开始就展开整套架构；面试官问测试，就先讲测试怎么构造、结果怎么判断。

容量题记住五项：部署环境、在线人数、业务负载、测试时长、成功率及 P99。可靠性题记住四项：故障点、重试标识、恢复路径、最终对账。

## 容量相关追问

### 1. 你说的用户数，是注册用户、在线用户还是活跃用户？

可以说：这里指已经完成 TCP 认证并保持心跳的在线连接数。活跃发送用户是其中的 20%，每人每 10 秒发一条消息。注册用户数只是数据库里的账号量，和同时在线的承载能力不同。

自己必须会算：业务消息速率 = 在线人数 x 活跃发送比例 / 发送间隔。例如 1000 x 20% / 10 = 20 条/秒。接收方也在线；这个模型测的是成对单聊，不代表群聊扇出。

### 2. 通过某一档，就证明这是单机最大容量吗？

可以说：这证明一个指定负载点通过了测试。最大容量需要逐档探索，而且必须给出延迟和错误率要求。更高档失败时，还要区分登录准入、持续消息负载和压测机调度问题，不能只用成功建立的连接数替代容量结论。

进一步追问时：不要把失败档里成功建立的部分连接说成完整通过；也不要在相邻两档之间做没有实验支持的精确插值。

### 3. 为什么测了这么多在线用户，每秒消息数看起来不高？

可以说：这是带明确活跃比例的混合在线模型，同时还包含心跳。它回答这类用户行为下能否正常服务。若要测纯消息吞吐上限，需要固定连接数、提高发送频率，单独做吞吐与长尾延迟曲线；目前不能把这一档发送速率称为系统峰值 TPS。

本脚本每条连接约每 5 秒发送一次心跳，心跳不计入业务消息 TPS。例如 1000 在线用户除了 20 条/秒业务消息，还会产生约 200 次/秒心跳请求。

### 4. P99 是什么意思？为什么不只说平均延迟？

可以说：P99 表示这个样本里约 99% 的延迟不超过该值，能反映长尾。平均数可能把少量很慢的请求掩盖掉。我分别统计发送到成功回包、发送到接收端收到通知的延迟。

注意：这里的接收延迟截止于无界面接收程序读到消息；没有包含真实 Qt 界面渲染时间。P99 只在成功完成的消息上计算，所以还必须同时报告失败和缺失数量。

### 5. 压测机与服务器同机，结果可靠吗？

可以说：它能作为可复现的本机基线，但共享 CPU、内存和 Docker 环境，而且走回环网络，会影响外推。我记录了主机、服务进程和压测进程的资源占用与发送调度延迟；更正式的容量测试应把压测机独立出来。

不能说“同机必然更保守”或者“生产环境一定更快”。资源争用可能拉低结果，回环网络也可能让结果偏好，影响方向需要实验确认。

### 6. 测 60 秒或 10 分钟，能说明长期稳定吗？

可以说：60 秒用于分档探索，延长运行用于检查该档位持续收发、心跳和对账结果。10 分钟依然不能替代数小时或更长时间的稳定性测试，也没有覆盖长期数据增长、全天流量波动和频繁重连。

### 7. 吞吐或延迟不理想，你怎么定位瓶颈？

可以说：先确定是哪一阶段变慢，然后分解排队、业务执行、数据库与网络时间。检查工作线程队列长度与等待、MySQL 连接等待、锁等待和事务耗时、Redis 操作，以及压测端调度延迟。拿到证据后再优化，并用同样负载做前后对照。

源码中 ChatServer 当前配置有逻辑分片线程，MySQL 连接池创建参数为 5，Redis 连接池为 10；这些是排查线索，不是已经证明的瓶颈。整机 CPU 低也不能排除单线程、锁或同步 I/O 限制。

本轮 5000 用户档已有更具体证据：14 条请求返回 2014，服务端记录 AddChatMsg 死锁；InnoDB 诊断显示 uk_chat_messages_client 索引上的间隙锁与插入意向锁等待。可以说“本轮观察到了数据库事务并发冲突”，不要只说“机器不够快”。后续可评估幂等插入/查询的锁策略，以及事务整体的有界死锁重试，再用相同负载验证；本轮没有实施这些性能修改。

5986 条成功确认的消息、接收消息与数据库 ID 集合一致，14 条失败均未落库。因此这一档是请求成功率与延迟不达标；没有证据把它描述成 14 条已确认消息丢失。容量脚本不自动重试业务失败，重试能力由独立可靠性场景验证。

### 8. 加 ChatServer 实例就能线性扩容吗？

可以说：可以分摊连接与部分业务处理，但容量不一定线性增长。还要考虑共享 MySQL、Redis、跨服 RPC、用户路由和热点会话。需要做相同负载下的单实例与多实例对照，不能直接把单实例结果乘实例数。

### 9. 你测的是登录接口 QPS 吗？

可以说：容量脚本先做真实账号密码登录冒烟检查，批量连接阶段使用预置 token 做真实 TCP 认证。它测聊天在线与收发能力，没有测全量账号密码验证的峰值 QPS；密码哈希计算还会引入不同的 CPU 负载。

## 丢失和重复相关追问

### 10. TCP 已经可靠，为什么还需要重试和幂等？

可以说：TCP 不等于应用事务成功。数据库提交后成功回包丢了，发送端不知道是否成功；服务端提交后在实时转发前退出，接收端也可能暂时收不到。业务层必须处理这种结果不确定性。

### 11. 收到 ACK 就表示对方收到了吗？

可以说：本项目文本发送的成功回包表示服务端持久化成功，或者幂等重试命中了原来的成功结果。它不代表接收端已落库，更不代表对方已读。实时通知 1701 本身不要求接收端回 ACK，遗漏由增量同步补齐。

### 12. 服务端保存成功，但 ACK 丢了怎么办？

可以说：客户端保留原来的 client_message_id 重试。服务端用 sender_user_id 与 client_message_id 的唯一约束和事务检查识别同一业务消息，返回已有 message_id，不新增消息记录和接收事件。

不要说每次重试生成一个新 UUID。唯一标识在创建业务消息时生成，重试复用；用户主动发送第二条相同文本才是新的业务消息。

### 13. 两个请求并发到达，仅仅先查再插安全吗？

可以说：单纯先查再插会有竞争，所以最终必须由数据库唯一约束兜底。本项目还在事务里锁定相关私聊记录并检查原消息。相同标识但内容不同返回冲突，不能悄悄覆盖原消息。

### 14. 你是不是实现了 exactly-once？

可以说：我使用持久化重试、增量恢复和幂等应用。请求和通知在传输中可以重复，业务记录通过唯一标识去重。在已测试场景中观察到了最终补齐且没有重复业务记录，但不能把它扩大成任意故障下的端到端 exactly-once 保证。

永久业务错误会使消息进入明确失败状态；网络或服务一直不可用时，也不能承诺有限时间内必达。

### 15. 最后一条实时通知丢了，后面没有序号缺口，你怎么发现？

可以说：不能只靠下一条消息暴露缺口。客户端除了登录、重连、发现缺口时同步，还会每 30 至 60 秒随机触发周期同步。本轮代理测试把所有实时通知都丢掉，包括最后一条，然后主动调用增量同步验证全部补回。

证据边界：代理测试证明同步接口能够补齐，没有驱动完整 Qt 客户端的随机定时器。周期触发行为属于当前源码机制说明。

### 16. event_seq 和 message_id 为什么都要有？

可以说：message_id 标识一条业务消息；event_seq 表示某个接收用户事件流里的顺序。不同用户收到的事件集合不同，而且事件还包括好友申请与处理结果，因此用每用户事件序号推进同步游标更合适。

不能说 message_id 连续无空洞就代表某个用户没漏消息，也不要把单聊的已验证顺序推广到群聊全局顺序。

### 17. 消息写进本地了，游标没推进就崩溃怎么办？反过来呢？

可以说：业务投影和同步游标在同一个 SQLite 事务里提交。提交前失败，两者都不生效，下次从旧游标再拉；提交成功，两者一起生效。重复消息按 message_id 去重，避免出现游标已前进但本地数据未写入的情况。

本轮本地库测试检查了幂等插入、业务状态与游标提交、拒绝序号缺口等行为；没有做操作系统断电注入，不能把事务测试称为断电验证。

### 18. 客户端进程退出，内存重试队列丢了怎么办？

可以说：SQLite outbox 是待发送任务的持久化来源，内存只是运行时登记。入队事务提交后才允许网络发送；确认结果也要完成本地事务后才移除运行时条目。登录恢复会加载待发送任务，已有业务消息继续复用原 ID。

本轮 Outbox 测试通过公开信号模拟登录与回包，验证了恢复、确认和重复回包处理；没有执行完整 GUI 进程在任意指令点被强杀的测试。

### 19. 怎样证明没丢、没重复？只看 100 条收到 100 条够不够？

可以说：不够。需要按业务消息唯一标识核对预期发送集合、成功回包集合、同步恢复集合及数据库记录，并检查每个 ID 的次数、内容、canonical message_id、接收事件和 event_seq 增量。数量相同可能是遗漏一条又重复另一条。

本轮故障代理记录实际截获次数，确认故障真的发生，再验证恢复结果。这里丢的是应用层帧，不能说成把 IP 丢包率设置成 100%。

### 20. 图片和文件怎么防止重复写入、断点损坏？

可以说：资源按 message_id、offset 和分片哈希上传，重复分片不能再次追加；恢复时核对磁盘进度并回退不可信尾部，完成后还要验证整文件 SHA-256 才发布。测试会重启 ResourceServer，构造半片或损坏尾片，续传后下载并逐字节比较。

### 21. 你能保证消息永远不会丢吗？

可以说：我能说明设计依赖和验证过的故障场景。恢复依赖持久化数据仍然可用、网络与服务恢复、客户端继续执行重试或同步。磁盘损坏、数据库备份恢复、长期网络分区等要有额外方案和测试，不能用这轮样本推出所有故障下零丢失。

## 现场练习

按下面四个故障点，每个用 20 秒解释恢复路径：

| 故障时刻 | 核心回答 |
| --- | --- |
| 本地入队提交后，网络发送前退出 | outbox 保留任务，恢复后仍用原 ID 发送 |
| 服务端落库后，发送成功回包丢失 | 原 ID 重试，返回原记录，不产生第二条业务消息 |
| 服务端落库后，实时通知丢失 | 接收事件仍可增量拉取，最后一条遗漏依靠周期同步等触发 |
| 接收端应用一页数据时退出 | 业务数据与游标同事务，重新拉取可幂等应用 |

第一遍练习只讲测试事实，控制在一分钟；第二遍让对方追问机制，再展开数据库唯一约束、Outbox 与事件游标；第三遍故意追问“最高多少”“绝对不丢”“所有场景测过吗”，练习准确说明验证边界。

## 避免使用的说法

- “压测程序发出去了，所以消息没有丢。”
- “ACK 到了，说明对方已经收到了、已经读了。”
- “TCP 可靠，所以业务不需要考虑丢失和重复。”
- “测到了多少连接，单机上限就是多少用户。”
- “所有用户在线，就相当于所有用户同时高频发送。”
- “没有观察到错误，所以生产环境永远不会失败。”
- “增加几个节点，容量一定按倍数增长。”
- “把失败项跳过后，全部测试通过。”

遇到没有测过的追问，直接说明未验证，再给出具体实验方法。能解释测试怎么补齐，比给出没有证据的肯定答案更可靠。
