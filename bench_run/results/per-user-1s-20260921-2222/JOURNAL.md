# 每人每秒一条消息：实验过程

## 固定口径

- 每个用户一个真实 TCP 连接并通过 ChatServer 登录认证；全部用户持续发送，不再使用 20% 活跃比例。
- 用户两两配对、双向私聊；每个用户每秒一条，错开到达时间。N 用户 = N 条业务消息/秒；每条还产生发送回包、接收通知以及数据库消息/事件记录。
- 正文 256 字节 ASCII，不是 256KB；协议 JSON 和 TCP 头另计。先保持消息大小不变，避免同时改多个变量。
- 心跳每 5 秒。先用 60 秒档位找边界，再用 600 秒验证候选档位。
- 暂定验收：计划消息全部发出、全部成功回包、全部收到、数据库逐 ID 一致、零异常断连/重复；回包和接收 P99 <= 1000ms；压测调度 P99 <= 100ms。观察积压是否持续增长。
- 压测端、单个 Release ChatServer、Gate/Status、Docker MySQL/Redis 同机运行。仅使用已有的隔离验证容器和测试账号，不操作业务数据库。
- 保留 MySQL 持久化设置，不以关闭事务刷盘换取容量数字。每个实验独立目录保存参数、日志、每秒采样、逐条消息时间和数据库状态。

## 实验记录

1. 原压测脚本只允许半数以下用户单向发送；新增双向模式，按 uid 相邻异或 1 配对；保留旧模式。新增实时连接数、积压、心跳、错误计数、每用户发送数量、MySQL 状态/SQL 摘要前后快照。
2. 基线配置：LogicWorkers=4，DeliveryWorkers=4，MySQL pool=5（原程序硬编码）。初始源码和二进制哈希见 baseline-snapshot。
3. baseline-100-60s 运行中观察：100 人全在线但待处理数增长，出现 2014 失败。MySQL COMMIT 4083 次、累计约 129.9 秒，均值约 31.8ms；ChatServer CPU 低。Docker 数据目录使用 Linux volume，并非 Windows bind mount；当时 MySQL CPU 约 14.61%。这些是诊断线索，不单独构成根因结论。

4. baseline-100-60s：6000 条中 5999 条成功，1 条死锁失败；接收 P99=9872.173ms。baseline-60-60s：3600/3600 成功，接收 P99=374.182ms。原二进制仅把 LogicWorkers 从 4 调为 8、pool 仍为 5，100 人档 6000/6000 成功但接收 P99=4543.082ms，仍失败。
5. 增加 MysqlPoolSize 配置（默认 5，范围 1..64）和 MysqlDeadlockRetries（默认 2，范围 0..5）。只对 SQL 错误 1213 完整回滚后重试整个 AddChatMsg 事务；1/2ms 退避；唯一键及事务原子性不变；未知提交结果不作自动重试。
6. 首次增量构建只编译 MysqlDao.cpp 并链接，但新增类成员影响 MysqlMgr 对象布局。workers8-pool12-retry0-100-60s 虽通过，随后 workers8-pool12-retry2-200-60s 在登录阶段退出，Windows Event 1000 记录 0xc0000374（堆损坏）。检查发现构建目录缓存的 MSVC showIncludes 前缀为乱码，头文件依赖可能未正确跟踪。以上两个优化版阶段均不用于正式容量比较。保留原始输出，执行全部目标 clean-first 重编，后续重测。不能把该登录阶段异常误判为 200 人容量上限。
7. 压测脚本新增 admission.json，登录人数不完整立即终止，避免继续发送后生成误导性吞吐结果。增加按每分钟统计 P99 的验收，防止整体分位数掩盖某一分钟过载。

后续实验结果、参数调整和最终结论将在本目录 REPORT.md 汇总；失败实验原样保留。
