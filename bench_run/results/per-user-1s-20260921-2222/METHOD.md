# 测试方法与指标解释

## 1. 这次的一个用户是什么

Python asyncio 压测程序为每个测试账号创建独立 TCP socket，连接 127.0.0.1:28090，发送 1101 并验证 1102 登录成功。全部连接保持打开，发送 1103 心跳并读取 1104 回包。它模拟真实协议客户端，不启动成百上千个 Qt 窗口。

单台主机上的连接通过 TCP 四元组区分：客户端 IP、客户端临时端口、服务端 IP、服务端端口。服务端监听端口都相同，但每个连接的客户端临时端口不同。一个 Python 进程可以异步管理多个 socket，不需要一个用户对应一个操作系统线程。

账号及好友关系预先存在于隔离验证数据库；Redis 预置这些测试账号的 token。真实执行 ChatServer token 认证。Gate 密码登录另做单次 smoke，不把批量注册或密码登录吞吐混进消息处理容量。

## 2. 每人每秒一条如何做到

全部 N 个用户参与发送，用户 0 与 1、2 与 3 等配对，每对双向发消息。每秒依次轮到 N 个用户，所以 N 用户的目标输入速率为 N 条消息/秒；轮到同一个用户的间隔为 1 秒。相邻配对用户的发送时间也相邻，存在会话行锁竞争，这是本次固定工作负载的特征。

压测按预定时间发送，不等待上一条消息回包后再发下一条。否则服务端越慢，压测端也越慢，可能把过载藏起来。脚本单独记录实际发送时间偏离计划时间的程度；调度 P99 超过 100ms 时，该轮不能作为服务端容量通过证据。

正文固定为 256 个 ASCII 字节，是 256B，不是 256KB。实际 TCP 帧还包含 client_message_id、用户 ID、会话 ID、JSON 标点和四字节应用帧头。消息正文流量不等于整个系统网络流量。256B 用作可复现的短文本样本；不声称它是生产聊天记录的统计分布。

连续发送 60 秒用于探索，候选档位再持续 600 秒。每轮先登录、等待 3 秒，再开始计时；这 3 秒不是业务消息预热。结束后最多等待 30 秒收尾，收尾完成数量与测量窗口内完成数量分开记录，不能将排空队列所需的额外时间隐藏掉。

## 3. 时间怎样得到

同一 Python 进程同时模拟发送方和接收方，共用 time.perf_counter 单调时钟，不存在两台压测机器的时钟偏差。

- t0：即将序列化并发送 1301 前，记录发送端时间。
- t1：完整读取并解析发送方收到的成功 1302 后，记录回包时间。
- t2：完整读取并解析接收方收到的 1701 后，记录接收时间。
- 回包延迟 = t1 - t0；接收延迟 = t2 - t0。

用唯一 client_message_id 关联三个时间及数据库记录。延迟包括发送编码、客户端/服务器排队、TCP 传输、数据库事务以及接收解析，覆盖协议客户端之间的端到端过程；不包含 Qt 界面渲染、接收方 SQLite 落盘或用户已读。

P99：把有效延迟从小到大排序，取 ceil(样本数 * 0.99) 对应的值。例如 P99=200ms，表示约 99% 的观测样本不超过 200ms。失败、未收到的消息不能因为没有延迟样本就忽略，所以成功率、缺失数与 P99 同时验收。

## 4. 稳定的验收标准

这次预先采用测试阈值，而非宣称这些阈值是行业统一标准：

- 全部 N 个用户完成认证，整个业务阶段无异常断连。
- 计划的 N * 秒数条消息全部发送；每用户发送数量相同。
- 所有消息取得成功回包、接收通知，零重复通知和重复回包。
- chat_messages 和 user_events 按每条 client_message_id 对账；正文、接收者、状态与 canonical message_id 一致。
- 整场及每一分钟的回包 P99、接收 P99 都不超过 1000ms；最终必须无未处理消息。
- 发送调度 P99 不超过 100ms；结合每秒积压曲线，确认负载没有被压测端自动降速，系统没有持续堆积。

测试“通过”表示该负载在本次持续时间及环境中通过。60 秒通过只是候选档位，600 秒通过才用于此次持续容量结论。它们都不能替代数小时测试、生产容量规划或线上 SLA。

## 5. 如何观察瓶颈

samples.jsonl/samples.json 每秒记录实时连接数、发送/成功回包/接收数量、待回包/待接收数量、心跳回包数、错误数、ChatServer RSS、进程 CPU、压测端 CPU、整机 CPU 和可用内存。

pending_ack 是尚未取得成功或明确错误回包的数量；pending_receive 包含未收到通知的消息，因此明确失败的消息也会计入。分析失败轮积压时，应同时看 ack_error_count，不能把所有 pending_receive 都叫做排队中的消息。

进程 CPU 按单个逻辑核心的 100% 表示：20% 意味着约占一个核心的 0.2，不是整台 20 逻辑核机器的 20%。整机 CPU 使用独立指标。RSS 是驻留内存，不等于每个用户独占内存，也不包含 MySQL/Redis/压测程序。

database-before.json / database-after.json 保存 MySQL 状态、SQL 摘要、文件 I/O 累计耗时和最新死锁。分析时取前后差值，避免把上一轮的累计量归给本轮。COMMIT 平均耗时 = 两快照之间累计 COMMIT 耗时 / 次数。不同线程的等待时间可以重叠，不能把累计等待直接当成整轮墙钟时间。

同机私聊的实时通知经过接收者业务线程队列；这次没有走跨 ChatServer 的 DeliveryWorkers 路径。因此保持 DeliveryWorkers=4，把实验重点放在 LogicWorkers、MysqlPoolSize 和死锁恢复，避免调整无关参数。

## 6. 重试的边界

服务器新增仅对 MySQL 1213 的有限重试：回滚后重新执行整个消息事务，不只是重发最后一条 INSERT。生产缺省额外重试 2 次，测试可设 0..5 次；间隔 1/2/4/8/16ms。相同 client_message_id 和数据库唯一键不变，消息、用户事件序号和事件引用仍同事务提交。

客户端压测不自动重发失败消息。成功率反映一次业务请求经过服务端内部重试后的最终结果；必须另外披露数据库死锁和内部重试数量，不能说数据库没有发生过死锁。未知提交状态、连接异常等不归为可确认回滚的 1213，不进入此自动重试路径。

完整事务重试符合 [MySQL 8.0 的 InnoDB 错误处理说明](https://dev.mysql.com/doc/refman/8.0/en/innodb-error-handling.html)。这只是死锁恢复措施，不等于消除了间隙锁，也不保证无限次重试后的必达。

## 7. 复现入口

PowerShell，启动已有隔离 MySQL/Redis 后运行。每轮 label 必须唯一，脚本拒绝覆盖证据：

```powershell
python bench_run/bench_capacity.py `
  --output bench_run/results/per-user-1s-20260921-2222 `
  --label my-new-stage --users 100 --seconds 60 `
  --active-fraction 1 --interval 1 --bidirectional `
  --payload-bytes 256 --logic-workers 8 --mysql-pool-size 12 `
  --delivery-workers 4 --deadlock-retries 2
```

命令中的人数和参数仅为示例，最终通过档位见 REPORT.md。主机资源、源文件与二进制哈希、MySQL 持久化配置见各 snapshot 子目录。短测及长测都在普通工作站上运行，未隔离其他宿主机负载；不是独占服务器实验室结果。
